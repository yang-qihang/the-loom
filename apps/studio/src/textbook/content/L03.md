# 岔路与钟声：用分支让同一段程序应对不同夜晚

> 从剧本卡出发，理解布尔值、条件与 if / else if / else

## 0 本章要解决的问题

村口的钟楼、井台与北门都在同一个广场上。散线浓了以后，夜里墙外常有动静，守夜的老法子不够用了。村里准备了三张剧本卡，对应三个不一样的夜晚：第一夜安静无事；第二夜北门有僵尸；第三夜井边有人被困。同一段符文要连跑这三个夜晚，每一夜都守好，村里不伤一人。

写程序的人面对一个时间差问题：写代码的时候，你不知道今晚是哪一夜；程序运行的时候，剧本卡已经摊在桌上。如果要求「每一夜写一份程序」，那就等于把同一段逻辑抄三份，换一张卡就重写一次。这个时间差，正是本章抽象要解决的问题——程序不能在写的时候猜答案，而要在运行的时候读情况、做选择。

具体要做的选择有这几条。有人被困的夜，先去井边救人，再把人带到村口大门；有威胁的夜，去钟楼敲钟报信，再去北门守着；安静的夜不敲钟，免得把全村吵醒。北门如果被撞开了，要用圆石堵上。这四条判断不是并列的清单，而是有优先级的：救人在前，敲钟在后，堵门视情况。优先级一乱，程序可能先跑去堵门，把井边的人丢在危险里。

本章要引入的抽象叫分支（branch）：程序在某个位置看一个条件，条件成立就走一条路，不成立就走另一条路；同一时刻只走其中一条。写成代码就是 `if / else if / else`。条件本身要用布尔值（boolean）表达：一个只有「真」和「假」两种取值的东西，由比较运算算出来。

先看一个反例。下面这段程序完全不读剧本，每一夜都做同一件事。

```ts caption:[错误示例] 每晚都敲钟：安静的夜也会把全村吵醒
const s = world.vars.scenario
golem.moveTo(bell)
golem.place("bell", bell)
```

运行后世界会看到：第一夜钟声大作，村里人被吵醒；第二夜钟声倒是该敲，但程序没有去北门守着；第三夜井边有人被困，程序仍然只敲钟，没有救人。同一个程序在三张卡上表现相同，说明它没有把「今晚是什么夜」这个信息用起来。本章的任务，就是把这个信息读进程序，并让程序在不同取值下走不同的路。

## 1 直觉：岔路口只走一条路

想象从村口出发去广场，路上遇到一个岔路口。左边这条路通向井台，右边这条路通向钟楼。你站在路口看指示牌：如果今晚井边有人被困，就走向井台；否则走向钟楼。指示牌的判断结果只有两种——去井台，或者去钟楼，不会同时走两条路。这就是一个分支的直觉模型：先看条件，再选一条路，另一条路这一次不执行。

岔路模型里有两个容易被忽略的要点。第一，条件必须能给出明确的是或否。如果指示牌上写「如果今晚情况复杂」，你无法判断走哪边；程序里的条件也一样，必须写成能算出真或假的表达式。「今晚是否有人被困」可以判断，「今晚感觉危险吗」不行，因为后者没有客观答案。写条件的工作，首先是把模糊的判断翻译成可计算的比较。

第二，岔路不是简单的「多一条路」。有岔路之后，程序的行为空间变大了：同一段代码在不同的输入下会走不同的路径，产生不同的世界状态。这对程序员提出了新要求——不仅要验证「条件成立时程序对不对」，还要验证「条件不成立时程序对不对」。新手常常只想着一种情况，写出一个只在特定夜晚正确的程序，换个场景就失效。

「否则」这个概念同样重要。写分支时，人们容易只处理自己关心的情况：有威胁就敲钟，写完就结束了。可程序还要在安静的夜晚运行，此时条件不成立，如果没有「否则」分支，程序就什么也不做，灯柱不点、艾拉没有回音。一个完整的判断应当覆盖所有可能：条件成立做什么，不成立做什么。`else` 就是用来兜底的那一句。

剧本卡是本章的输入数据。`world.vars.scenario` 返回一个只读对象，里面装着这一夜的情况：`night` 是第几夜，`threat` 是威胁数量，`trapped` 表示是否有人被困，`gateOpen` 表示北门是否被撞开。程序把它读进一个常量 `s`，后面的条件都从 `s` 上取字段。把剧本一次性读进来，而不是每处都重新写 `world.vars.scenario`，是为了让程序有一个清晰的数据来源。

读数据与做判断要分开。读数据这一步只负责把情况拿到手；判断这一步才决定做什么。这个分离让程序更容易检查：先确认 `s` 里的字段对不对，再确认每一个条件有没有把对应的情况覆盖到。如果两者混在一起写，出了问题就分不清是读错了数据，还是判断错了情况。

:::aside 分支从哪来
早期程序靠无条件的「跳转」指令改变执行顺序，跳转可以向后跳过一段代码，也可以向前回到某一行。无条件跳转让程序可以表达任何控制流，但也让代码极难读懂：读到一个位置，不知道它会被谁跳进来。结构化编程运动提出用三种结构组织控制流——顺序、分支、循环；只要限制在这三种结构里，程序就能被逐段理解。今天语言里的 `if`、`while` 就是这三种结构中的两种。本章学分支，下一章学循环。
:::

## 2 定义与机制

### 2.1 布尔值：只有真与假

布尔值（boolean）是一种只有两个取值的类型：`true` 表示真，`false` 表示假。它专门用来回答「是不是」这类问题：今晚有人被困吗？威胁数量大于零吗？北门开着吗？答案要么是，要么不是，没有第三选项。

布尔值可以直接来自剧本字段。`s.trapped` 本身就是布尔值：有人被困时它是 `true`，否则是 `false`。这种字段不需要再比较，直接放进条件里就行。另一类布尔值由比较算出：`s.threat > 0` 会先读 `s.threat` 的数字，再判断它是否大于 0，结果是一个布尔值。两种写法在条件里等价：前者是「已经知道真假」，后者是「现算一个真假」。

给布尔值起名字，能让程序更可读。`const danger = s.threat > 0` 之后，`if (danger)` 比 `if (s.threat > 0)` 更容易一眼看懂意图，尤其当一个条件由多个比较组合而成时。布尔变量通常以 `is`、`has`、`can` 开头命名，或者用形容词；本章的示例用 `danger`、`hasThreat` 这类名字。

### 2.2 比较运算：把两个值变成布尔值

比较运算（comparison）读两个值，产出一个布尔值。常用的有六个：`>` 大于、`<` 小于、`>=` 大于或等于、`<=` 小于或等于、`===` 严格相等、`!==` 严格不相等。`s.threat > 0` 是「威胁数量大于零」；`s.night === 1` 是「这是第一夜」。

`===` 有三个等号，与赋值 `=` 不是一个东西。`=` 是「把右边存到左边」，`===` 是「问左右是否相等」。为什么不用两个等号？因为在很多语言里两个等号会做类型转换再比较，`"4" == 4` 可能被判定为相等，这种隐式转换容易埋下错误；三个等号要求类型和值都相同，行为更可预测。本课程统一使用 `===` 和 `!==`，不写 `==` 和 `!=`。

比较的结果可以存起来，也可以直接用在条件里。存起来的好处是可以复用、可以命名；直接用的好处是短。两种写法都对，选择的标准是：这个判断只在一个地方用，还是要在多处用？只在一处用，直接写；多处用，存成一个布尔变量，避免复制条件表达式后改一处漏一处。

还需要注意比较的边界。`s.threat > 0` 和 `s.threat >= 1` 在整数世界里等价，但后者写错了就变成 `s.threat > 1`，把 1 个威胁漏掉。写条件时，先想清楚边界上的值算不算：威胁数量为 0 表示没有威胁；为 1 就已经有威胁。因此用 `> 0` 最清楚，不需要读者再换算。凡是涉及边界的条件，都值得停下来确认一次。

### 2.3 条件与 if：走哪条路

条件（condition）是 `if` 后面括号里的表达式，它的值必须是布尔值。`if (条件) { 语句块 }` 的执行过程是：先算条件，条件为 `true` 就执行花括号里的语句，为 `false` 就跳过整块。花括号围起来的这一段叫代码块（code block），它把若干条语句打包成一个整体，要么整体执行，要么整体跳过。

代码块里的语句仍然按顺序执行，与普通语句没有区别；区别只在进入与退出：进入代码块由条件决定，退出之后继续执行 `if` 后面的语句。这个结构让程序有机会跳过一段动作。跳过的意思是那几行「没有发生」，世界不会因为写了但没执行而改变。

`if` 的条件只认布尔值。传入一个数字时，语言会做隐式转换：0 当作假，非 0 当作真。这种转换在真实语言里存在，但本课程不建议依赖它。写 `if (s.threat > 0)` 比写 `if (s.threat)` 更清楚：读者一眼知道判断的是什么，也不会因为字段类型变化产生意外。显式比较是本章的写作规范。

### 2.4 else if 与 else：互斥、短路、兜底

当情况多于两种时，把多个 `if` 串成一条链：`if (条件一) { … } else if (条件二) { … } else { … }`。执行规则是从上往下依次检查：条件一为真就执行第一块，然后跳过整条链；条件一为假才检查条件二；条件二为真就执行第二块；全部为假时执行 `else` 块。

这条规则里有两个关键性质。第一是互斥：整条链最多执行一个分支。哪怕两个条件都成立，也只有排在前面的那个分支会执行，后面的被跳过。第二是短路：一旦命中某个分支，剩余的条件不再求值。互斥保证了「一个夜晚只按一种情况处理」，短路保证了「前面的优先级更高」。

`else` 是可选的，但强烈建议写。`else` 的意思是「以上条件都不成立时做什么」。如果没有 `else`，条件全不成立时程序什么都不做；对于守夜任务，这意味着安静的夜晚没有安排，灯柱不点、人也不巡查。把安静夜的行为写进 `else`，程序才在所有情况下都有完整行为。覆盖完整性是分支正确性的第一要求：先问「所有可能的输入，有没有一条路可走」，再问「每条路走得对不对」。

`else if` 的顺序就是优先级。把「有人被困」放在最前面，是因为它最紧急；把「有威胁」放在中间；把「安静夜」放在最后作为兜底。如果顺序颠倒，安静的夜可能先匹配到某个宽松条件，急救的分支永远轮不到。写多分支时，先按紧急程度或逻辑依赖排序，再写代码。

### 2.5 逻辑与、逻辑或：把条件组合起来

有些情况需要同时满足两个条件，比如「有人被困且北门开着」；有些情况只要满足一个条件，比如「有威胁或者北门开着」。前者用逻辑与 `&&`，后者用逻辑或 `||`。`A && B` 当且仅当 A、B 都为真时为真；`A || B` 只要 A、B 中有一个为真就为真。

`&&` 与 `||` 也有短路行为。`A && B` 里，如果 A 已经为假，整个表达式一定为假，B 不再求值；`A || B` 里，如果 A 已经为真，整个表达式一定为真，B 不再求值。短路不仅是性能优化，它还是写安全条件的手段：`s.night > 0 && s.threat > 0` 里，先检查 night，再检查 threat，读者能按从左到右的顺序理解条件。

多个逻辑运算符混在一起时，优先级容易记错：`&&` 比 `||` 结合得紧。`a || b && c` 等价于 `a || (b && c)`。本章的建议是：只要混用，就加括号。括号不改变语义，但能让读代码的人省去回忆优先级规则。明确表达意图，比依赖优先级规则更可靠。

### 2.6 顺序即优先级：嵌套与合并的选择

同一个优先级问题有两种写法：嵌套和合并。嵌套是把「更紧急的判断」写在外层，把次要判断写进内层；合并是用 `&&` 把多个条件写进同一个 `if`。两种写法都能表达优先级，选择取决于场景。

嵌套适合「先做一类事，再在其中细分」的情况。比如「有人被困」时，先救人，然后如果还有威胁，再敲钟。外层判断 `s.trapped`，内层判断 `s.threat > 0`，读起来与任务描述的层次一致。合并适合「几个条件同时影响同一段动作」的情况，比如「有人被困且北门开着」就一起救人并堵门。

嵌套过深会让代码难读：三层以上的 `if` 需要逐层对应花括号，稍不注意就漏了右括号。遇到多层嵌套，可以先考虑能否用 `&&` 合并条件，或者把某一段动作抽成函数（第 5 章会讲）。本章的程序最多两层嵌套，先把层次关系写清楚，不必急着优化结构。

:::warn 常见误解：分支会「都执行一遍」
有人把 `if / else if / else` 理解成「把所有满足条件的分支都执行」，于是写出了重复动作，或者以为 `else` 里的语句也会执行。执行规则是互斥且短路：整条链只执行第一个命中的分支，其余分支这一轮不会执行。想表达「都要做」，就把这些动作放在链外，顺序执行；想表达「只做最紧急的一件」，才用链。判断分支结构是否正确，先问「这一轮到底应该做几件事」。
:::

## 3 语法与示例

### 3.1 读剧本：把情况拿进程序

第一步是把这一夜的情况读进来。`world.vars.scenario` 返回只读对象，放进常量 `s` 之后，后面的条件都从 `s` 上取字段。

```ts caption:[照抄] 读剧本，并算出一个布尔值
const s = world.vars.scenario
const danger = s.threat > 0
```

运行后世界会看到：什么都没有变化。这两行只读数据、算布尔值，不产生世界动作。`danger` 是一个布尔变量：今晚有威胁时它是 `true`，没有威胁时是 `false`。后续可以用 `if (danger)` 代替 `if (s.threat > 0)`，前提是名字起得清楚。

读数据这一步看似无用，实际决定了后面所有判断的输入。如果 `s` 读错了，后面的分支再工整也没用。写程序时可以先在纸上列出这一夜四个字段的值，再对照程序里用到的条件，检查有没有用错字段：救人的条件应该是 `s.trapped`，不是 `s.gateOpen`；敲钟的条件应该是 `s.threat > 0`，不是 `s.night > 0`。字段名字都很有提示性，但新手仍容易看错。

### 3.2 最小分支：只有一条路

先看最小形式：一个 `if`，没有 `else`，只处理「有威胁」这一种情况。

```ts caption:[照抄] 有威胁的夜：敲钟，再去北门
const s = world.vars.scenario
if (s.threat > 0) {
  golem.moveTo(bell)
  golem.place("bell", bell)
  golem.moveTo(gate)
}
```

运行后世界会看到：若今晚有威胁，灰崽走到钟楼、把钟放上钟位、再走到北门；若今晚没有威胁，花括号里的三行全部跳过，世界没有任何变化。这个最小形式暴露了一个问题：没有 `else` 时，安静夜什么也不做。

在分支里放什么，要受「这个分支的条件」约束。敲钟属于「有威胁」分支，因为安静的夜不该有钟声；走到北门也属于这个分支，因为守门是有威胁时的动作。救人则不属于这个分支，因为它的条件是「有人被困」，与有没有威胁是两件事。把动作放进正确的分支，比把分支写对更难，也更容易出错。

### 3.3 两分支：把「否则」补上

补上 `else`，安静夜就有了安排。下面这段程序同时覆盖「有威胁」与「没威胁」两种情况。

```ts caption:[照抄] if / else：有威胁敲钟，安静夜只巡查
const s = world.vars.scenario
if (s.threat > 0) {
  golem.moveTo(bell)
  golem.place("bell", bell)
  golem.moveTo(gate)
} else {
  golem.moveTo(bell)
  golem.say("安静夜：钟不响")
}
```

运行后世界会看到：有威胁时敲钟并去北门；安静时灰崽走到钟楼下说一句「钟不响」，钟没有被敲。两种夜晚，同一段程序，两条互斥的路，各自有动作。`else` 里为什么还要走到钟楼？因为巡查本身是守夜的一部分，安静不代表可以不管；但巡查时只说一句，不敲钟。

`if / else` 是完整的二选一：两条路必走一条，不会两条都走，也不会两条都不走。写分支时，先确认条件是否真的把世界分成「是」与「否」两半：有威胁与没有威胁是一对，有人被困与没有被困是一对。如果条件的「否」不是你想的另一半（比如你想区分「有威胁」与「安静」，却写成了「有威胁」与「北门开着」），分支结构本身就是错的。

### 3.4 三分支：三夜的剧本

三张剧本卡对应三种情况，用 `if / else if / else` 按优先级排列。注意顺序：有人被困最紧急，排第一；有威胁排第二；安静夜作为兜底排最后。

```ts caption:[照抄] 三夜分支：if / else if / else
const s = world.vars.scenario
if (s.trapped) {
  golem.moveTo(well)
  golem.moveTo(door)
  if (s.threat > 0) {
    golem.moveTo(bell)
    golem.place("bell", bell)
  }
} else if (s.threat > 0) {
  golem.moveTo(bell)
  golem.place("bell", bell)
  golem.moveTo(gate)
} else {
  golem.moveTo(bell)
  golem.say("安静夜：钟不响")
}
```

运行后世界会看到：第一夜（安静）走 `else` 分支，灰崽在钟楼下说「钟不响」；第二夜（北门有僵尸）走中间的 `else if` 分支，敲钟并去北门；第三夜（井边有人被困）走第一块，先去井边、再到村口大门，若还有威胁再补一次钟声。三张卡，三条路，同一段程序。

这段程序里有一个嵌套：第一块内部又判断了一次 `s.threat > 0`。为什么？因为「有人被困」与「有威胁」可以同时发生，救人优先，救完之后如果还有威胁，仍然要敲钟报信。嵌套让「救人」这件事保持在最高优先级，同时不放弃次要动作。读这种结构时，先把外层三块分开看，再看第一块内部的那一层，层次就清楚了。

把它写成执行路径表，可以更直观地检查覆盖情况。

1. 第一夜：`s.trapped` 为假；`s.threat > 0` 为假（威胁 0）；进入 `else`，只走钟楼并说「钟不响」。灯柱与人家门口的点灯动作不在分支里，稍后单独执行。
2. 第二夜：`s.trapped` 为假；`s.threat > 0` 为真（威胁 3）；进入 `else if`，敲钟并走到北门。
3. 第三夜：`s.trapped` 为真；进入第一块，先去井边、再去村口大门；此时 `s.threat > 0` 为真（威胁 2），内层分支再敲钟一次。
4. 三个夜晚都执行完分支后，继续执行分支之外的公共动作：点亮八根灯柱、四户人家门口、检查北门、巡查三处、回艾拉身边。

再单独看第四夜（加练层）的执行顺序。第四夜的剧本是有人被困、有威胁、北门开着三件事同时发生，程序按优先级处理。

1. 先进入 `if (s.trapped)`：灰崽去井边，再把人带到村口大门。救人排第一，因为它是唯一与人身安全直接相关的事。
2. 在救人分支内部检查 `s.threat > 0`：威胁存在，灰崽去钟楼敲钟。敲钟排第二，报信能让村里其他人有准备。
3. 分支结束后检查 `if (s.gateOpen)`：门开着，灰崽去北门放圆石堵上。堵门排第三，可以在救人报信之后做。
4. 最后执行公共动作：点灯、巡查、回艾拉身边；这些动作与三件事是否发生无关，每种夜晚都要做。
5. 如果顺序颠倒——先堵门再救人——第四夜会失败：分支顺序与语句位置共同决定优先级，不是随意排列的。

这张路径表说明了一个重要设计：**只有分歧动作放进分支，公共动作放在分支外**。点灯、巡查、回艾拉身边在每个夜晚都要做，它们不是三种情况各自的答案，而是守夜任务的共同部分。如果把点灯写进每个分支，代码会重复三遍，改一处就要改三处；放进分支外，写一遍就够。

### 3.5 逻辑与或：合并条件与堵门

北门是否要堵，取决于 `s.gateOpen`。堵门与敲钟、救人没有互斥关系，所以它不放进那条 `if / else if / else` 链，而是单独一个 `if`。单独判断的好处是它在任何夜晚都可以执行，不会因为命中某个分支而被跳过。

```ts caption:[改写] 单独判断与逻辑与：北门开着就堵上
if (s.gateOpen) {
  golem.moveTo(gate)
  golem.place("cobblestone", gate)
}
if (s.trapped && s.gateOpen) {
  golem.moveTo(door)
  golem.say("门开着，人已经带到门口")
}
```

运行后世界会看到：北门开着时，灰崽走到北门，在门格上放一块圆石，门被堵住；若同时有人被困且门开着，它再走到村口大门说一句话。两段判断互不影响，各自独立执行。

第二个 `if` 演示了 `&&` 的用法：`s.trapped && s.gateOpen` 要求两个条件都为真。第一个 `if` 演示了「单独判断」的用法：它与其它分支不互斥，多个单独的 `if` 会依次检查、依次执行。什么时候用链、什么时候用独立判断？规则是：互斥的情况用链，可以同时发生的情况用独立判断。救人、敲钟、静夜是三选一，用链；堵门、巡查、点灯可以与前三种情况并存，用独立判断。

`||` 的用法类似。比如「有威胁或者北门开着」就进入警戒状态：`if (s.threat > 0 || s.gateOpen) { … }`。这种合并适合「只要有一个条件成立就要做同一件事」的场景。混用 `&&` 与 `||` 时加括号，例如 `if ((s.trapped || s.threat > 0) && s.gateOpen) { … }`，避免读者去背优先级。

### 3.6 分支之外：公共动作

守夜程序的大部分行不是分支，而是分支结束后继续执行的公共动作。点亮八根灯柱和四户人家门口，每一夜都要做；巡查井边、北门、钟楼，每一夜都要做；最后回艾拉身边报平安，每一夜都要做。下面是一小段点灯动作，其余照这个形态逐处补完。

```ts caption:[改写] 点灯片段：每根灯柱两行，其余照写
golem.moveTo(lamp1)
golem.place("torch", lamp1)
golem.moveTo(lamp2)
golem.place("torch", lamp2)
golem.moveTo(lamp3)
golem.place("torch", lamp3)
golem.moveTo(lamp4)
golem.place("torch", lamp4)
```

运行后世界会看到：1 到 4 号灯柱顶部出现火把；5 到 8 号灯柱与四户人家门口按同样的「先走、再放」写法补齐。点灯是状态动作，与具体是哪个夜晚无关，所以它不属于任何一个分支。

把公共动作与分歧动作分开，是本章程序结构的核心。分歧动作决定「这一夜与别夜有什么不同」，公共动作决定「所有夜晚共同的底线」。读一段守夜程序，先找分支链（分歧），再找分支之后的顺序语句（公共），结构就清楚了。改动程序时也按这个结构改：换剧本只动分支，换灯柱数量只动公共动作。

### 3.7 完整参考解走读

把分支、堵门、点灯、巡查拼起来，就是一段完整的守夜程序。下面这段以分支与巡查为主，点灯部分按上一段的形态补齐。

```ts caption:[读参考解] 守夜主程序：分支 + 堵门 + 巡查 + 收岗
const s = world.vars.scenario
if (s.trapped) {
  golem.moveTo(well)
  golem.moveTo(door)
  if (s.threat > 0) {
    golem.moveTo(bell)
    golem.place("bell", bell)
  }
} else if (s.threat > 0) {
  golem.moveTo(bell)
  golem.place("bell", bell)
  golem.moveTo(gate)
} else {
  golem.moveTo(bell)
  golem.say("安静夜：钟不响")
}
if (s.gateOpen) {
  golem.moveTo(gate)
  golem.place("cobblestone", gate)
}
golem.moveTo(well)
golem.say("井边：平安")
golem.moveTo(gate)
golem.say("北门：平安")
golem.moveTo(bell)
golem.say("钟楼：平安")
golem.moveTo(eira)
golem.say("三夜平安，天亮收岗")
```

运行后世界会看到：三种夜晚各走各的分支；北门开着就被圆石堵上；井边、北门、钟楼依次巡查并各报一声平安；最后灰崽回到艾拉身边收岗。完整的通关程序还要在分支之前或之后点亮灯柱与人家门口，那部分不涉及判断，按前面的点灯形态写即可。

走读参考解时，可以按「读数据、判断、分歧动作、公共动作」四层拆开。第一层是 `const s = world.vars.scenario`；第二层是分支链的条件与顺序；第三层是每个分支里的具体动作；第四层是分支之后的公共动作。四层各自的职责不同，出问题时也能按层定位：剧本读错，查第一层；三种夜处理错，查第二层与第三层；每一夜都少东西，查第四层。

:::tip 写分支前先画三种情况
写 `if` 链之前，在纸上列一张「情况—动作」对照表：每种情况一行，写清楚条件、要做的动作、做完之后世界该是什么样。然后检查三件事：情况之间是否互斥、所有情况是否被覆盖、有没有动作是每种情况都要做的。三件事都确认了，再写代码。这张表就是分支的草稿，代码只是把表翻译成语法。
:::

## 4 常见错误

### 错误一：条件里把 `===` 写成了 `=`

现象：程序能运行，但行为不对，或者条件永远成立。原因：`=` 是赋值，`if (s.threat = 0)` 会先把 0 赋值给字段（在只读对象上会失败），或者把条件变成一个数字；判断相等必须用 `===`。改法：条件里只使用比较运算与逻辑运算；写完 `if` 后先读一遍括号里的表达式，确认没有赋值号。这个错误在语法上不总报错，所以要靠读代码发现。

### 错误二：条件写反或边界写错

现象：安静的夜晚敲了钟，或者有僵尸的夜晚没有敲。原因：条件的方向写反，比如写 `s.threat === 0` 却想要「有威胁」；或者边界写错，把 `> 0` 写成 `> 1`，漏掉 1 个威胁的情况。改法：把「条件成立时应该发生什么」写在纸上，再对照代码；凡是涉及 0、1 的边界，逐个取值试一遍。剧本卡上有具体数字，可以拿三张卡当测试用例。

### 错误三：漏掉 `else`，某种情况没有安排

现象：某一夜程序什么都没做，灯没点，艾拉没收到话。原因：只写了 `if`，没有写 `else`；当条件不成立时，整块被跳过，程序继续往下走，如果公共动作也没写，世界就毫无变化。改法：写完 `if` 就问「否则呢」；把「以上都不成立时做什么」补进 `else`。对于三夜任务，安静夜正是那个「否则」，必须有明确安排。

### 错误四：把公共动作放进了某个分支

现象：程序在某几种夜晚正常，换一种夜晚就漏了点灯或漏了巡查。原因：本该每个夜晚都执行的动作被写进了某个分支，只在该分支命中时执行。改法：把动作分成「每种情况都一样」与「随情况变化」两类；前者放在分支链之外，后者放进分支。检查方法：把三种夜晚分别代入，看公共动作是不是每种情况都执行了一次。

### 错误五：分支顺序颠倒，优先级错乱

现象：有人被困的夜里程序先跑去敲钟或堵门，没有救人。原因：`if / else if` 链按书写顺序检查，排在前面的分支优先；如果把「有威胁」放在「有人被困」前面，第三夜会先命中威胁分支，救人分支永远轮不到。改法：按紧急程度排列分支，最紧急的放最前，兜底的 `else` 放最后；画一张优先级表再写代码。

### 错误六：条件合并时漏掉情况

现象：两个条件用 `&&` 合并后，某些组合没有被处理。原因：把本来需要分别处理的情况合并成一个条件，导致组合之间互相覆盖或漏掉；或者 `||` 用错，把「两个都要」写成了「一个就够」。改法：先列出所有组合（两个布尔值有四种组合），逐个写明期望行为，再决定用 `&&`、`||` 还是嵌套；混用时加括号，让意图清晰。

## 5 与关卡的关系

L03 的机制叫「三夜试炼」：同一段程序连续在三个夜晚运行，每一夜都按当夜的剧本判定。这个机制的意义在于，它无法被「针对某一夜写死」通过。如果程序按第一夜写死「不敲钟」，第二夜就会失败；按第二夜写死「敲钟」，第一夜就会吵醒全村。只有真正读取剧本、按情况分支的程序才能连过三夜。

三条目标对应三层检查。第一条「看剧本：有威胁才敲钟」，检查的是程序有没有读对数据：有威胁的夜晚必须有钟声，没威胁的夜晚不能有钟声。这条规则把「读剧本」与「敲钟」绑定在一起，如果程序不读 `s.threat` 就敲钟，第一夜就会失败。第二条「按剧本救人、点灯、堵好北门」，检查三个具体动作：有人被困时必须到达井边与村口大门；八根灯柱与四户人家门口必须全部点亮；北门开着时门格必须变成圆石。第三条「天亮后你亲手敲钟」，是玩家节拍：灰崽敲的钟不算守夜钟声，天亮钟声必须由玩家对着钟楼的钟按右键完成。

把三条目标翻译成程序结构，就是本章示例的组合：读 `s`、用分支链处理三种夜、用独立判断处理堵门、用顺序语句处理点灯与巡查、最后回艾拉身边。参考解里还有一句「三夜平安，天亮收岗」，它只是信息，不参与判定；写不写 `say` 取决于任务是否要求报平安，本关的参考解写了，读者可以照抄。

新手在这一关容易卡在两处。第一处是读剧本与做动作脱节：读进了 `s`，条件却写成 `s.night === 2` 之类与任务无关的判断，导致某些夜行为错误。第二处是点灯漏写：三夜的分支写得很漂亮，却忘了八根灯柱和四户人家门口是每一夜都要点的公共动作，或者只点了灯柱忘了人家门口。工作台的目标面板会逐条显示，哪一条没勾就去对应位置找原因；三夜试炼每通过一夜会显示进度，通过之后才发现的问题，多半在下一夜的剧本组合里。

加练「第四夜」把三件事放在同一夜：有人被困、有威胁、北门开着。这不是新知识，而是对优先级的检验：先救人（井边到村口大门），再敲钟，最后堵门。参考解的结构是「救人分支里嵌套敲钟判断」，再单独处理堵门与巡查；顺序对了，第四夜就能过。把加练当成一次组合练习，而不是额外负担。

## 6 小结与练习

本章的要点收成六条。

- 布尔值只有 `true` 与 `false`，由剧本字段直接给出，或由比较运算算出。
- 比较运算把两个值变成布尔值；判断相等用 `===`、不等用 `!==`，不要与赋值 `=` 混淆。
- `if (条件) { 语句块 }` 在条件为真时执行整块，为假时跳过整块；条件必须是能算出布尔的表达式。
- `if / else if / else` 从上往下检查，只执行第一个命中的分支，其余跳过；`else` 负责兜底。
- 逻辑与 `&&`、逻辑或 `||` 用来合并条件，两者都有短路行为；混用时加括号。
- 分支的顺序就是优先级；互斥的情况用链，可以同时发生的动作用独立判断，公共动作放在分支外。

练习不计分，也不需要提交。建议先在纸上判断，再运行验证。

1. 给定 `s.trapped = false`、`s.threat = 0`、`s.gateOpen = true`，本章的三分支程序会走哪个分支？钟敲了吗？北门堵了吗？写出每一步。
2. 把三分支程序里「有人被困」的内部判断 `if (s.threat > 0)` 删掉，第三夜会发生什么？任务还能通过吗？为什么？
3. 用 `&&` 把「有人被困且北门开着」写成一个条件；再用 `||` 写一个「有威胁或有人被困」的条件。两个条件分别适合放在哪种动作前面？
4. 把三分支程序的 `else` 分支删掉，第一夜的世界会变成什么样？任务面板上哪一条目标不会打勾？
5. 假定任务改成「先堵门，再救人，最后敲钟」，三分支结构应该怎么调整？只改顺序够不够，为什么？
6. 写一段程序：如果北门开着就堵门；不管北门开不开，都去井边巡查一次。写出它的分支结构与执行路径。

## 7 延伸

分支是控制流的基本结构之一，也是「程序能根据情况做选择」这件事的最初形态。早期程序只有无条件跳转，读代码时很难知道某一行会在什么情况下被执行；结构化编程把跳转限制成顺序、分支、循环三种结构，程序从此可以被逐段阅读、逐段验证。今天几乎所有语言都保留 `if / else`，只是语法细节不同：Python 用缩进代替花括号，Rust 用 `match` 表达多路分支，函数式语言用模式匹配替代条件链。

在计算理论里，条件分支与循环一起构成了「程序可以表达任意计算」的关键能力。没有分支的程序只能一路执行到底，无法根据输入调整行为；有了分支，程序才开始「看情况」。本章的三夜试炼就是最朴素的例子：同一段程序，输入不同，行为不同，结果也不同。理解这一点，你就能理解为什么测试要覆盖不同输入——只测一种情况的程序，等于没有测分支。

分支也有代价。每多一种情况，就要多写一条路径，测试要覆盖的组合数量随之增长；当情况之间开始互相影响时，条件链会变得又长又难读。这个代价在游戏里很快就会出现：第 6 章的货箱与工作点会把「物品类别」变成数据里的一个字段，用 `switch` 与穷尽性检查代替一长串 `if`，让「漏掉一种情况」从容易犯错变成编译期就能发现的问题。本章先把两三条分支写清楚，后面的章节再谈如何组织更多的情况。

## 术语

- 布尔值（boolean）— 只有 `true` 与 `false` 两个取值的类型，用来回答「是不是」；示例：`s.trapped`。
- 比较运算（comparison）— 读两个值、产出一个布尔值的运算；示例：`s.threat > 0`、`s.night === 1`。
- 条件（condition）— `if` 后面括号里的布尔表达式，决定这一块语句执不执行。
- 分支（branch）— 程序按条件选择执行路径的结构；示例：`if / else if / else`。
- 代码块（code block）— 用一对花括号围起来的一段语句，要么整体执行，要么整体跳过。
- 逻辑与（logical AND）— 用 `&&` 连接两个条件，两边都真时结果才为真；示例：`s.trapped && s.gateOpen`。
- 逻辑或（logical OR）— 用 `||` 连接两个条件，任意一边为真时结果就为真。
- 短路求值（short-circuit）— 逻辑运算在结果已经确定时不再计算另一半表达式。
- 控制流（control flow）— 程序语句的执行顺序，包括顺序、分支与循环三种基本结构。
- 剧本对象（scenario）— 本关通过 `world.vars.scenario` 提供的只读数据，包含 `night`、`threat`、`trapped`、`gateOpen` 四个字段。
