# 双织者：消息、协议与合龙

> 两个执行者的协调：先发后等、共享材料与 Promise.all

## 0 本章要解决的问题

前九章的程序都只有一个执行者：灰崽。所有动作排成一条时间线，等待与并发都在这一条线上安排。第 10 关的桥面缺口太长，一个织偶铺不完；工坊派来了两只：左织与右织，各自从桥的一头往中间铺。于是程序第一次有了两条动作线，它们同时存在、同时前进，需要互相配合。

两条线一出现，问题就换了性质。一个执行者时，你只需要想「先做什么、后做什么」；两个执行者时，你要想「谁先动」「各自拿多少材料」「什么时候算都做完了」「谁不能替谁做最后一步」。这些问题不是靠多写几个 await 能解决的——如果两只织偶都站在原地等对方先开口，程序会卡住，直到超时失败。这种互相等待叫死锁。

本章要学的，就是用消息把两条时间线接起来：给每只织偶一个句柄，用 send 与 receive 交换约定，用协议规定谁先说、说什么、收到之后怎么核对；用 world.supply 读共享材料的快照，按份额把材料分给两只织偶；用 Promise.all 让两条线同时开工，并用 agent.waitIdle() 等它们真正闲下来；最后把桥中央的一格留给玩家，用 world.keystone() 把最后一步交还给人。

这一章没有新的语法构造需要大量记忆，几乎全部难点都在「安排」：发送与接收的先后、份额与几何的对应、启动与汇合的时机、最后一步留给谁。这些都是第 7 章的「做法当值」、第 8 章的「计划与执行分离」、第 9 章的「等待编排」在两条线上的组合。学完本章，回头看前九章，会发现每一章都在为这种协调攒工具。

## 1 直觉：两个人搬砖

看两个工人搬一堵砖墙。如果两个人各搬各的，会出现三种乱子：一个人搬得太多，另一个没砖可搬；一个人堵在窄道口，另一个过不去；或者两个人都以为对方会先动手，站在原地互相等。要避免这些，他们不需要变得更聪明，只需要先商定几句话：「我拿这边的砖」「我这头开始砌」「中间那块留着，等工头来放」。说话的顺序也有讲究：两个人都先等对方开口，就永远没人开口；必须有一个人先说，或者两边都主动先说，然后各自听。

消息（message）就是程序里的「说话」。执行者之间不能直接读写对方的内存，只能通过消息传递：把一段文字放进对方的箱子里，对方从自己的箱子里取出来。这个箱子叫邮箱（mailbox）。消息不是动作，它不改变世界，只传递信息；但信息能让两只织偶的行动互相配合。

消息和动作是两回事，这一点要分清。`left.place(...)` 会改变世界，`right.send(...)` 只把一段文字放进右织的邮箱；邮箱里的消息不会自己变成动作，必须由某段代码 `receive` 出来、读它、再决定做什么。所以协议写的是「信息如何流动」，动作仍然由每只织偶自己的代码执行。信息先行、动作跟进，这是协调程序的基本节奏。

还有一个直觉要建立：邮箱是「每只织偶一个」，不是「每个程序一个」。发给左织的消息进左织的邮箱，发给右织的进右织的邮箱；左织取不到右织邮箱里的东西。所以脚本里写 `left.receive()`，读的是左织自己的邮箱——谁收、谁发，句柄要说清楚。

协议（protocol）是双方共同遵守的说话规则：什么时机说、说什么、收到之后怎么回应。协议对了，两个执行者各写各的代码也能配合；协议错了，各自跑得再顺，合起来也会乱。本章的协议很短：开工时互相报出自己算好的份额，收到后核对一致；铺完之后再互相报一次完工。就这么几句话，把两条时间线钉在了一起。

## 2 定义与机制

### 执行者与句柄

执行者（agent）指一个独立的动作来源。本章有左织与右织两个执行者，用 `agent("左织")`、`agent("右织")` 取得它们的句柄（handle）。句柄是一个值，可以存进变量、可以传给函数；拿到句柄，就有了指挥这个执行者的途径：`left.moveTo`、`left.place`、`left.say`、`left.collect`、`left.send`、`left.receive`。

写句柄时要注意「这只手属于谁」。`left.moveTo(x, z)` 让左织移动，`right.moveTo(x, z)` 让右织移动；两个方法名字一样，对象不同。程序的并发能力正来自这里：两个执行者的动作可以同时排队、各自推进，不必一条等一条。`Promise.all([左织开工(), 右织开工()])` 让两条动作线同时跑起来。

两个执行者的动作是并行排队的，但「并行」不意味着「没有先后」。每个执行者内部仍然按 await 的顺序执行；两只织偶之间才可能同时动作。写代码时要区分这两种时间：一只织偶内部是顺序的，两只织偶之间是交错的。判断某段代码属于哪一层，看句柄：同一个句柄的调用属于同一只织偶，不同句柄的调用分属两条线。

执行者也带来新的责任：一只织偶的动作只能由它自己完成。左织不能替右织走位，右织也不能替左织放置；代码里写错句柄，动作就会发到另一个执行者身上，表现是「某一边一直没动」。读代码时先看句柄，再看方法，是排查多执行者问题的第一步。

### 消息与邮箱

`left.send(正文)` 把一条消息投进左织的邮箱；`right.receive()` 从右织的邮箱里取一条消息。这里有一个容易绕晕的地方，需要记牢本章的约定：发消息时用「收件人」的句柄 `send`，收消息时用「自己」的句柄 `receive`。于是两只织偶互相说话时，代码写成「给对方的句柄 send，给自己的句柄 receive」——左织那一路用 `right.send(...)` 发给右织、用 `left.receive()` 收自己的；右织那一路正好相反。

消息是一个对象，含 `from` 与 `text` 两个字段。`text` 是正文；`send` 会把传入的值转成字符串，所以 `send(String(份额))` 之后，对方拿到的 `text` 也是字符串。`from` 记录来源信息，本章主要用 `text` 核对份额。判断份额时一定要比较字符串，或者两边都换算成数字再比：`回话.text !== String(右份额)` 是安全的，`回话.text === 右份额` 在类型上就说不通。

`receive` 是异步操作：没有消息时它会等，默认等 10 秒。超时会失败并给出提示「等不到对方的回话：先发消息、再等回话」。注意本章没有非阻塞的 `tryReceive`：不要写它，也不要用轮询去「看看有没有消息」。等就是等，收不到就失败，失败信息会告诉你协议哪里不对。

接收还有一点值得提前知道：`receive` 拿到的消息顺序与你 `send` 的顺序一致，每个消息只会被取走一次。多次 send 会排队，多次 receive 会依次取；取空了就等，等到超时失败。本章的协议每条线只收一两条消息，所以队列问题不突出，但设计协议时要把「谁发的哪条消息对应哪个 receive」对上，否则会取到上一次握手遗留的消息。

### 协议与先发后等

协议是一组关于消息的约定。本章的协议包含四句话：

1. 开工前，每只织偶先把自己的份额告诉对方；
2. 说完之后，各自收对方报来的份额；
3. 收到后核对：两份加起来是不是等于材料总数，份额是不是和自己算的一样；
4. 铺完之后，再互相报一次完工。

为什么发送必须排在接收前面？因为两条动作线是同时跑的。如果左织那一路先 `left.receive()`，它会停在那里等右织的消息；如果右织那一路也先 `right.receive()`，它同样在等左织。两条线互相等对方先开口，谁也不会先开口，程序卡住，直到 10 秒超时失败。这就是死锁（deadlock）：不是程序算错了，而是等待关系形成了环。

先发后等打破了这个环：发送不依赖对方任何动作，写完立刻执行；两边都先把消息投出去，然后再各自等对方的消息。消息已经在邮箱里，接收就不会落空。协议的设计目标之一，就是保证「任何时刻，每个接收都能等到一条已经存在的消息」。这类「先动手再等回音」的结构叫握手（handshake）：你报一声，我回一声，双方确认状态一致再继续。

协议的另一个名字是「约定」，它不需要双方用同一份代码，只需要双方遵守同一套规则。本章两条开工函数看起来几乎对称：左岸用 `right.send` 与 `left.receive`，右岸用 `left.send` 与 `right.receive`。对称不是巧合——两条线各自扮演「发送者 + 接收者」两个角色，只是句柄相反。写协议时先画一张两列的表：一列是「我发什么、发给谁」，一列是「我收什么、从哪收」；两列都填满，协议才算完整。

:::warn 常见误解：先发后等只是「礼貌」
有人觉得先发后等只是让程序好看，先收后发也能跑。两条线都先收的后果是死锁；只有一边先收、另一边先发时才勉强能跑，但哪个先收会随任务变化，把成功寄托在「恰好」上。协议的价值就是把顺序固定下来，让任何一边先启动都正确。先发后等应当写成规则，而不是靠运气。
:::

### 共享资源与份额

两只织偶要用的木板装在同一个材料箱里，这是共享资源（shared resource）。共享资源的第一个问题是「有多少」：`world.supply(材料箱位置).count("oak_planks")` 读到一个只读快照（snapshot），告诉你箱子里现在有几块木板。快照不是实时余额，它读的是调用那一刻的数量；之后的取用不会自动更新它。所以正确做法是：开工前读一次、算出份额、把数字通过消息对齐，再让两只织偶各取各的。

份额的算法要和缺口对齐。缺口有几格、中央一格留给玩家，剩下的才是织偶要补的块数。参考解用 `左份额 = Math.ceil(材料总数 / 2)`、`右份额 = 材料总数 - 左份额`：向上取整保证左岸多拿的那一块与铺桥的起点对得上，右岸拿剩下的。两边通过消息核对份额，是为了防止「一边以为自己拿 3 块，另一边也以为对方拿 3 块」这种错位。共享资源配上明确份额，才能做到一块不超、一块不丢。

共享资源最容易出的问题不是「拿不到」，而是「多拿」或「重复拿」。多拿会让后面的织偶拿不到；重复拿会在同一个位置放两次，判定把它算成一块或两块取决于记录方式。防这种问题的办法是把「数量」在开工前就说清楚：读快照、算份额、双方核对。口头核对（通过消息）比各自心算可靠，因为两边的数字都会落到日志里，错了一眼能看出来。

### Promise.all 与 waitIdle

两条动作线各写成一个 async 函数，各自内部按协议走完取料与铺桥。顶层用 `Promise.all([左织开工(), 右织开工()])` 同时启动并等待两者都完成。和第 9 章一样，Promise.all 只负责汇合：它不改变两个任务的启动顺序，也不保证谁先完成；它只是站在那里等两个 Promise 都有结果。

`等待两者都完成` 之后还有一层：织偶的动作是排队的，async 函数返回只代表「这段代码走到了终点」，不代表「这只织偶的动作队列清空了」。`agent.waitIdle()` 等所有执行者真正闲下来——没有排队中的移动、放置、说话。参考解在 Promise.all 之后调用它，再让左织说最后一句、再呼出合龙，确保收尾动作发生在所有铺桥动作之后。`waitIdle` 不带参数，写 `agent.waitIdle()`，不要写成 `agent.waitIdle("左织")`。

Promise.all 与 waitIdle 的先后也有讲究：先等两个 async 函数返回，说明两条线里的协议与铺桥代码都执行完了；再等动作队列清空，说明最后一块木板真的落下了。如果反过来，可能在一只织偶还有动作在排队时就说了「铺好了」，日志与世界的先后就对不上。

### 合龙石与玩家节拍

桥面只剩中央一格时，程序停下来。那一格要放的是合龙石，只有活人的手能放。`world.keystone()` 的作用是「呼叫玩家来完成最后一步」：它把流程停在合龙这一步，等玩家放下合龙石后继续。它不是「替玩家放石头」——代码不能放、也不该放；它是把交接做进程序里，让代码把桥铺到「只剩一格」为止。

这一设计延续了前几关的玩家节拍传统：L01 的第四盏灯、L06 的织线、L08 的总拉杆、L09 的暮钟，都由玩家亲手完成。不是为了给玩家找事，而是为了让最后一步的归属清楚：织偶能替你跑、替你等、替你铺，替不了你把手放上去。

## 3 语法与示例

先看两个执行者各自开工的最小例子。两条动作线各写一个 async 函数，句柄不同，动作用各自的句柄。

```ts caption:两条独立的动作线
const 桥 = world.vars
const left = agent("左织")
const right = agent("右织")

async function 左岸动工(): Promise<void> {
  await left.moveTo(1, 0)
  await left.say("左岸到了")
}

async function 右岸动工(): Promise<void> {
  await right.moveTo(26, 0)
  await right.say("右岸到了")
}

await Promise.all([左岸动工(), 右岸动工()])
await agent.waitIdle()
```

运行后世界会看到：左织与右织几乎同时从各自桥头出发，各自说一句话；两条线互不等待。`agent.waitIdle()` 在最后等所有动作队列清空，确保下一句代码在所有移动与说话都完成之后才执行。

这段代码里两个函数没有任何共享变量，也没有互相等待；它们唯一的联系是顶层的 Promise.all。这就是两条独立动作线的最小形态：各跑各的，汇合处等。

接下来是本章的核心：先发后等的消息协议。

```ts caption:先发后等：两边都先发，再各自收
const left = agent("左织")
const right = agent("右织")

async function 左织开工(): Promise<void> {
  await right.send("左岸拿 2 块")
  const 回话 = await left.receive()
  await left.say("左岸收到：" + 回话.text)
}

async function 右织开工(): Promise<void> {
  await left.send("右岸拿 2 块")
  const 回话 = await right.receive()
  await right.say("右岸收到：" + 回话.text)
}

await Promise.all([左织开工(), 右织开工()])
```

运行后：两条线各报出份额，再各自收到对方的消息并复述出来。四条消息（两次发送、两次接收）的顺序由你的代码决定；因为两个函数都是先 send 再 receive，没有任何一方在等待中空转。

注意发送的内容是字符串，接收端直接打印 `回话.text` 就能看到。若想让对方的数字参与计算，记得先 `Number(...)` 转回数字；这一章比较份额用字符串，就不用转。

如果把接收放到发送前面，程序就会卡住。下面这段是死锁的反例。

```ts caption:[错误示例] 两边都先等，就互相等死
const left = agent("左织")
const right = agent("右织")

async function 左岸等(): Promise<void> {
  const 消息 = await left.receive() // 等右岸先发；可右岸也在等
  await left.say("左岸收到：" + 消息.text)
}

async function 右岸等(): Promise<void> {
  const 消息 = await right.receive() // 等左岸先发；可左岸也在等
  await right.say("右岸收到：" + 消息.text)
}

await Promise.all([左岸等(), 右岸等()])
await agent.waitIdle()
```

运行后：程序不会报语法错误，两条线都静静地等对方；大约 10 秒后，接收超时失败，提示「等不到对方的回话：先发消息、再等回话」。这就是死锁的样子：没有 bug 的语法，只有错误的等待顺序。

死锁的代码没有一行看起来「危险」，这正是它难查的原因。判断一段协议会不会死锁，不要看代码长短，要看等待图上有没有环：A 等 B 的消息，B 等 A 的消息，就是一个环。

共享资源的份额要先读快照再分。

```ts caption:读材料快照，按份额分配并各自取料
const 桥 = world.vars
const left = agent("左织")
const right = agent("右织")
const 木板 = "oak_planks"

const 材料总数 = world.supply(桥.materialsBox as number[]).count(木板)
const 左份额 = Math.ceil(材料总数 / 2)
const 右份额 = 材料总数 - 左份额

async function 左岸取料(块数: number): Promise<void> {
  for (let i = 0; i < 块数; i++) {
    const 取到 = await left.collect(木板, 桥.materialsBox as number[])
    if (取到 !== 1) {
      throw new Error("材料箱提前空了")
    }
  }
}

await 左岸取料(左份额)
await left.say("左岸取料 " + 左份额 + " 块")
```

运行后：左织从共享材料箱里取走自己那一份，每取一块检查返回值是不是 1；取不到就当场报错，而不是继续铺。右岸取料写成对称的一份，块数用右份额。两边加起来正好等于缺口要补的块数，一块不多、一块不少。

`world.supply` 读到的是快照，不是实时余额。代码里读一次、把数字算清楚，之后不再依赖它；如果边取边读，读到的数可能已经被另一只织偶取走了。

铺桥只做一件事：按份额从桥头往中间铺，铺到中央前停下。

```ts caption:[片段] 左岸铺桥：从缺口起点往中间铺
async function 左岸铺桥(块数: number): Promise<void> {
  for (let i = 0; i < 块数; i++) {
    const x = 缺口起点 + i
    await left.moveTo(x, -1)
    await left.place(木板, x, 桥面高度, 0)
  }
  await left.say("左岸铺好了")
}
```

运行后：左岸那一侧的世界里，缺口从各自一侧被木板填上，中央一格仍然空着。右岸铺桥把起点换成「缺口起点 + 左份额 + 1」，从另一头往中间铺；两边合起来正好填到中央基座两侧。

铺桥片段里没有协议、没有取料，只有「按给定的块数铺到哪一格」。把它单独写成函数，是为了让协议那一层只关心协调，节点那一层只关心几何；两层修改互不牵连。

把协议、取料、铺桥拼起来，就是参考解里两只织偶的完整开工函数。

```ts caption:[读参考解] 左织开工：先发后等 + 核份额 + 取料 + 铺桥
const left = agent("左织")
const right = agent("右织")

async function 左织开工(): Promise<void> {
  await right.send(String(左份额))
  const 回话 = await left.receive()
  if (回话.text !== String(右份额)) {
    throw new Error("右岸的份额对不上")
  }
  await 左岸取料(左份额)
  await 左岸铺桥(左份额)
  await right.send(String(左份额))
  await left.receive()
}
```

运行后：左织先报份额、核对右岸报来的数字；对得上才取料、铺桥；铺完再报一次完工消息。如果右岸报来的份额对不上，它会在核对那一行直接失败，而不是带着错误的份额去铺桥——错误在最早能发现的地方停下。

核对份额失败时抛错，是这条协议的安全阀：份额对不上就停下，而不是硬着头皮铺。错误信息写清楚是谁对不上，排查时一眼知道去查哪边的计算。

最后是汇合与合龙。两条线同时开工，等它们完成，再由玩家放上最后一块。

```ts caption:汇合、等空闲、把最后一步交给玩家
await Promise.all([左织开工(), 右织开工()])
await agent.waitIdle()
await left.say("桥面铺好了，最后一块交给织者")
await world.keystone()
```

运行后世界会看到：两只织偶同时铺桥，桥面中央只剩一格；左织说一句话；流程停在合龙这一步，等玩家手持合龙石右键中央基座。玩家放下之后，桥面完整，演出与村民过桥随之开始。`world.keystone()` 不是替玩家放石头，它只是把控制权交给玩家。

这四行的顺序就是本章的收尾顺序：先汇合两条线，再清空动作队列，再说收尾话，最后交还玩家。任何一步提前或延后，日志与世界事件的相对顺序都会变。

## 4 常见错误

### 错误一：两边都先 receive，形成死锁
现象：程序不报语法错误，但卡住十几秒后失败，提示等不到回话。原因：两条线都在等对方先发消息，等待关系成环。改法：固定「先发后等」的顺序；或者指定一方先发言、另一方先听。规则写下来，两边都照它执行。

### 错误二：把消息里的数字当数字比较
现象：份额明明一样，核对却失败；或者提示「对不上」但你检查数字没错。原因：`send` 会把内容转成字符串，`text` 是字符串；用 `回话.text === 右份额` 时，字符串与数字永远不相等。改法：统一用 `String(...)` 两边都转成字符串再比，或者用 `Number(回话.text)` 转成数字再比，二选一，不要混。

### 错误三：把句柄写反了
现象：某一边一直没动，或者消息发到了错的邮箱，双方都收不到。原因：发送用了自己的句柄、接收用了对方的句柄；或者左岸那一路把 `left`、`right` 写反。改法：记住「send 用收件人、receive 用自己」；读代码时逐个核对句柄与方法，看到「某只织偶没动」先查这里。

### 错误四：份额分配与桥面几何对不上
现象：桥面中央空出两格，或者一边多铺一格、另一边少铺一格。原因：份额没有按「缺口块数减去玩家那一格」来算，或者左右两侧的起点算错。改法：先算材料总数（缺口块数）、再算每侧份额与起点；两边份额之和必须等于材料总数，左侧起点是缺口起点，右侧起点是缺口起点 + 左份额 + 1。

### 错误五：把合龙交给代码，或者以为 keystone 是替玩家放
现象：代码里自己 put 合龙石，验收说「合龙石必须由玩家放」；或者以为 `await world.keystone()` 会替你把桥合上。原因：混淆了「呼叫玩家」与「替玩家做」。改法：代码只负责把桥铺到只剩中央一格；最后一格由玩家放；`world.keystone()` 只负责把流程停在合龙这一步等玩家。

### 错误六：只用顺序 await，不用 Promise.all
现象：两只织偶一前一后动，任务说「两只织偶都要动」却有一只几乎没铺；桥面能铺完但过程不符合协调要求。原因：`await 左织开工()` 之后才调 `await 右织开工()`，第二条线在第一条线完成前根本没启动。改法：先调用两个 async 函数拿到两个 Promise，再用 `Promise.all` 汇合。

两条线写在一个文件里，容易让人以为它们天生一起跑。事实是：一起跑是 `Promise.all` 的选择，不是 async 函数的自动行为。把两个调用分别 `await`，得到的就是先后；把它们先存成两个 Promise 再 `Promise.all`，得到的才是并行。这个区别在第 9 关讲过，在第 10 关被两个执行者放大，因为顺序执行时「另一只织偶几乎没动」会在世界里直接看出来。

## 5 与关卡任务的关系

第 10 关的数据在 `world.vars` 里：桥面长度 `deck`、缺口块数 `gap`、缺口起点 `gapStart`、桥面高度 `deckY`、桥宽 `bridgeWidth`、共享材料箱 `materialsBox`、两只织偶的名字与两岸桥头位置。缺口从 x=10 开始、宽 5 格，中央一格留给玩家；两只织偶各补 2 块，共享材料箱里正好 4 块木板。

参考解的分工是：读材料快照、算左右份额；两条 async 线各自先发后等核对份额；各自取料、铺桥；顶层 `Promise.all` 汇合、`agent.waitIdle()` 等队列清空、左织说收尾话、`world.keystone()` 把最后一步交给玩家。验收看三件事：桥面完整（含玩家放的合龙石）、两只织偶都动过并各铺一半、材料一块不超不丢。三件事分别对应本章的协议、并发与共享资源。

铺桥的几何也值得记：缺口 5 格，中央一格留给玩家，织偶各补 2 格；左岸从缺口起点往中间铺，右岸从「缺口起点 + 左份额 + 1」往中间铺，两边正好在中央基座两侧停下，中间空出 keystone 那一格。几何算错一格，桥面就会出现两格空洞或一格重叠，验收会在桥面完整性上失败。

任务里还有两个细节：铺桥时两只织偶的站位在桥面两侧（左岸 z=-1、右岸 z=1），放置落在桥面中央列；合龙石由玩家放在中央基座。验收不关心日志说得漂不漂亮，只关心世界里铺了什么、谁铺的、合龙石是谁放的。这也是十关下来一直重复的规矩：看世界，不看意图。

## 6 小结与练习

本章的要点可以收成五条。

1. 执行者是独立的动作线；给每只织偶一个句柄，动作用对应句柄的方法。
2. 消息通过邮箱传递，`send` 用收件人的句柄、`receive` 用自己的句柄；消息含 `from` 与 `text`，`text` 是字符串。
3. 协议规定说话的次序与含义；先发后等是避免死锁的基本结构，两边都先等会形成环。
4. 共享资源先读快照再分份额，份额之和必须等于要补的块数；两边各取各的、各铺各的。
5. Promise.all 汇合两条线，`agent.waitIdle()` 等动作队列清空，`world.keystone()` 把合龙交给玩家。

把五条连起来，本章解决的是「协调」这个维度：两个执行者各有自己的时间线，程序不再只描述一条线怎么走，而要描述两条线怎么对齐。消息是它们的共同语言，协议是语法，份额是它们共享的世界，Promise.all 是汇合点，玩家是它们共同的终点。

这一章是十关的最后一关，也是前面所有概念的大会合：记录（第 6 章）用来描述桥与消息、函数值（第 7 章）用来写两条线的做法、接口与计划（第 8 章）用来组织动作、异步与 Promise（第 9 章）用来重叠等待、多执行者（第 10 章）用来协调两条线。这些名词不必死记，重要的是能在新的双人任务里把同样的结构再想一遍。

练习题不计分，建议动笔。

1. 把本章协议改成「右岸先发、左岸先收」，写出两条开工函数；再检查是否仍满足「任何时刻接都能等到已存在的消息」。
2. 假设缺口从 4 格变成 6 格、中央一格仍留给玩家，重算左右份额与铺桥起点；说明份额算错一格时桥面会出什么现象。
3. 用一两句话向别人解释：为什么 `world.keystone()` 不是「替玩家放合龙石」？如果代码自己放了合龙石，验收会用哪条标准判它不对？

## 术语

- 执行者（agent）— 一个独立的动作来源；本章有左织与右织，各自通过句柄接受指挥。
- 句柄（handle）— 指向某个执行者的值，可以存进变量、传给函数，用来调用它的动作。
- 消息（message）— 执行者之间传递的信息，形如 `{ from, text }`，正文被转成字符串。
- 邮箱（mailbox）— 存放发给某个执行者的消息的队列；`send` 投入，`receive` 取出。
- 协议（protocol）— 双方共同遵守的消息次序与含义约定，决定谁在什么时机说什么。
- 握手（handshake）— 双方互发消息、确认状态一致后再继续的协议结构。
- 死锁（deadlock）— 双方都在等对方先动手，等待关系成环，程序卡住直到超时失败。
- 共享资源（shared resource）— 多个执行者共同使用的资源，本章指装满木板的材料箱。
- 快照（snapshot）— 在某一时刻读到的只读数量；之后资源变化不会自动更新它。
- 合龙石（keystone）— 桥面中央最后一格要放的石头；只能由玩家亲手放，代码负责把这一格留出来。
