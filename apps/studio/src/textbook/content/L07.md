# 把做法交出去：函数值、闭包与流水线

> 从「写死每一步」到「把判断与处理当作值传来传去」

## 0 本章要解决的问题

第 6 章把一件货的事实绑成记录，把分类写成 switch。程序已经能分拣八件货，但分拣的结构仍然是「写死」的：哪一段代码负责判断矿石、哪一段负责判断木料、哪一段负责算格子，全都摆在同一段流程里。每增加一类货，就要复制一段几乎相同的代码，改一处判断。

这一章要换一种组织方式：把「怎么判断」本身抽出来，变成一个可以传递的值。有了它，判断矿石、判断木料、判断食物可以是三个独立的「规矩」；筛选货堆和分配格子可以交给现成的函数去重复执行；而「先筛、再分格、最后逐个放」这条流水线只写一遍。代码从「列出每一步」变成「说明每一步是什么，再让通用零件把它们串起来」。

任务对这套组织方式有真实的需求：主线货堆要分三只箱子，复核箱还要再分一遍。如果两批货各写一段分拣逻辑，代码里就有两套几乎相同的判断与分配；只要规则改一次，两处都得改。把规矩与流水线抽出来后，主线与复核箱的差别只剩下数据来源和箱子位置，结构完全共用。这也是本章的代码会比上一章更短、更「不像在写步骤」的原因。

还有一个常被忽略的细节会在本章展开：一个「做法」被创建出来之后，它会不会记住创建时身边的变量？答案是会，这种记忆叫闭包。第 7 关参考解正是靠闭包让「给矿石分格子的做法」记住自己已经分到了第几格。

这一章不新增任何游戏动作。悦灵的规矩、货堆的筛选、箱子的分配，全部由你已经会的移动、放置、说话加上新的语言结构完成。要学的不是「更多指令」，而是「怎么把指令组织成可复用的做法」。这种组织方式一旦会了，第 8 关的机器接口、第 9 关的异步流程都会反复用到。

## 1 直觉：规矩也是一种值

设想营地里来了三只信风谷的悦灵，它们不认识货，只执行你给的规矩。你想要的是：给每只悦灵一条规矩，比如「kind 是 ore 的货归你」，然后让它们各自去货堆里挑。要做到这件事，程序里「一条规矩」必须能作为一个东西被交出去。

在已经学过的语言里，数字、字符串、记录、数组都是值：它们能存进变量，能当参数传给函数，能当返回值带出来。函数也一样。第 5 章你已经用过 `golem.moveTo` 这种「外面提供的函数」；这一章要做的是把函数当成普通的值来看待：给它起名、放进变量、当参数传、当结果返回。

「把规矩交出去」听上去抽象，换成指令的说法就具体了。给悦灵下命令的传统写法是：每遇到一件货就写一段 if，判断它是不是矿石，是就搬走。八件货写八段，换一批货重写一遍。换成本章写法，你只写一次「是不是矿石」的规矩，然后把这条规矩交给一个遍历货堆的通用零件；零件负责挨个取货、调用规矩、把结果为真的货留下来。通用零件是别人写好的，你只需要交对规矩。

把函数当值有一个直接的后果：函数可以「吃」另一个函数。接收函数作为参数的函数，叫高阶函数（higher-order function）。名字听起来复杂，含义很朴素：它把「一段做法」当材料用。反过来，返回函数的函数也是高阶函数，它把「做法」当产品卖。你要写的 `makeRule` 属于后者，你要用的 `filter` 和 `map` 属于前者。

这两类高阶函数对应两种抽取规律的方式。把判断交给别人的时候，你只写「什么算矿石」；把判断收进口袋的时候，你写的是「怎么从类别生成判断」。前者让通用的遍历替你跑腿，后者让重复的判断只写一次。第 7 关参考解两种都用了：`makeRule` 是生产规矩的，`filter`、`map` 是消费规矩的。

## 2 定义与机制

本章的五个概念彼此咬合：函数值让判断能被传递，箭头函数让写法短，高阶函数让传递有接收方，filter/map 让接收方是现成零件，闭包让传递出去的做法还记得自己的环境。下面逐个拆开，再在同一段代码里合起来。

### 函数值

函数值（function value）指函数本身，而不是它执行的结果。这个区别初学者常常混淆。`判断矿石` 是一个函数值；`判断矿石(货)` 是调用它得到的结果，一个布尔值。把函数放进变量，写的是 `const 规矩 = 判断矿石`，没有括号；带上括号就变成调用了。

函数声明（function declaration）会创建一个函数值，并把它绑定到名字上。函数表达式（function expression）把函数写在表达式的位置，例如赋值号的右边。两种写法创建的东西是同一类值，区别在于是否立刻绑定名字、以及能否在声明之前调用。本章更常用箭头函数，因为它短，而且适合把「一条规矩」写成一行。

函数值还有一个自然的去处：放进记录。第 6 章用记录描述货物，字段都是数据；字段同样可以装函数。第 8 关的机器记录里，`name` 和 `status` 是数据，`startSteps` 和 `stopSteps` 是函数——一条记录既描述「它是什么」，也描述「它能做什么」。这不是炫技，而是把「能力」也当成数据来组织。本章先把函数值单独看懂，到第 8 关再把它放回记录里用。

### 箭头函数

箭头函数（arrow function）是函数表达式的一种简写。`(item) => item.kind === "ore"` 读作「给定 item，返回 item.kind 是不是 ore」。箭头左边是参数，箭头右边是函数体；函数体只有一句表达式时，这一句的结果就是返回值，不用写 `return`。参数只有一个时可以省掉括号，两个以上或没有参数时要写括号。

箭头函数有一个必须记住的语法坑：函数体想直接返回一个对象字面量，要给对象加一对圆括号。因为花括号在箭头右边会被优先解释成函数体，而不是对象。写 `(kind) => { kind: kind }` 时，引擎看到的是一段函数体，返回值是 undefined；写成 `(kind) => ({ kind: kind })` 才返回对象。

箭头函数在回调里特别常见，因为它短到可以塞进调用的一行里。`cargo.filter((item) => item.kind === "ore")` 把「怎么判断」直接写在「筛」的旁边，读者不必跳到别处找这个函数。代价是匿名：没有名字的回调在堆栈里不好认，调试时也难用日志点名。经验是：一次性、一两句话能读懂的规矩写成箭头函数；会被反复调用、值得解释的做法，先起名再传。

### 高阶函数

高阶函数的两个方向都值得熟悉。接收函数作为参数，是为了让通用流程按你给的规矩办事：`filter` 接收一条判断规矩，`map` 接收一条转换规矩。返回函数作为返回值，是为了批量生产规矩：`makeRule("ore")` 生产「判断是不是矿石」的规矩，`makeRule("wood")` 生产「判断是不是木料」的规矩；两条规矩逻辑一模一样，只是记住的类别不同。

传进去的函数通常叫回调（callback）：你先把它交给别人，别人在合适的时机（这里是遍历到每个元素时）回头调用它。传进去的「返回布尔值的判断函数」有一个正式名字：谓词（predicate）。谓词回答是或不是，所以 `filter` 的返回值永远是一个更短的数组。

为什么值得让函数来接收函数，而不是自己写循环？因为「遍历」这件事本身是重复的，而「怎么判断」才是每个任务不同的部分。把重复的部分交给现成的高阶函数，你只需要写不同的部分。这和组织函数的动机一致：第 5 章把重复步骤收进函数，这里把重复的「遍历 + 调用」交给高阶函数。区别在于，函数封装的是「做什么」，高阶函数封装的是「怎么遍历、怎么调用」。

### filter 与 map

`filter`（筛选）遍历数组，对每个元素调用你给的谓词，只把返回真的元素留下，组成新数组。`map`（映射）遍历数组，对每个元素调用你给的转换函数，把返回的新值收集成新数组，长度与原数组相同。两者都不修改原数组，都返回新数组。

用一句话区分：filter 决定「留谁」，数量会变；map 决定「每个变成什么」，数量不变。筛矿石用 filter，把每条货记录换成格子坐标用 map。写反了不会报错，但结果不对：对记录用 map 会得到每个元素的转换结果，丢掉「筛」的意图；对坐标用 filter 会留下部分坐标，丢掉「一一对应」的结构。

把一次完整的筛选过程拆开看，每一步都是新数组。设货堆是六件货：粗铁与煤是矿石，橡木与云杉木是木料，面包与胡萝卜是食物。
- `filter(isOre)` 对六件货各调用一次谓词，留下两件，得到矿石数组。
- 在矿石数组上 `map((item) => item.id)` 对两件货各调用一次转换，得到两个编号。
- 反过来先 map 再 filter 不是不能运行，但含义变了：你先得到六个编号，再按「编号是不是某两个值」筛。这等于把数据里的类别字段丢掉，换一批货就失效。

还有一件事关系到后面的闭包：`map` 是逐个元素调用你的函数，调用顺序固定，但每次调用拿到的元素不同。如果你的转换函数内部有状态（比如「这是第几次被调用」），那么顺序就重要了。

### 闭包

闭包（closure）指函数连同它创建时所在的变量环境一起形成的整体。用直白的话说：函数会记住创建时身边的变量，之后即使外层函数已经执行完毕，这些变量仍然活着。被记住的变量叫自由变量（free variable）：它们不是函数的参数，也不在函数体内声明，而是从外层捕获（capture）来的。

闭包记住的是绑定（binding），不是一次快照。如果外层变量后来被修改，闭包读到的是修改后的值。这一点容易误解：很多人以为闭包「复制了一份当时的数值」，它持有的是那个变量本身。第 7 关参考解里 `planFor` 返回的分配函数，每次调用都修改并读取 `n`，所以连续分配格子时 `n` 会递增；如果闭包是快照，每次都会分到同一格。

闭包让「带状态的做法」成为可能。计数器、分配器、只属于自己的小账本，都可以用「外层函数声明变量、内层函数读写它」的方式做出来。每个外层调用都会创建一套新的变量环境，所以两次调用得到的是两个互不干扰的闭包。

闭包的生命周期值得留意。外层函数返回之后，它的局部变量本来该被回收，但只要内层函数还引用着它们，这些变量就会一直活着。这既是能力也是代价：能力是你可以用闭包保存状态，不必把状态暴露成全局变量；代价是这些被捕获的变量会一直占着内存，直到所有引用它的函数都不再被使用。对本章的程序来说不必担心，但理解这一点，以后读别人的代码时就知道「为什么这个变量过了那么久还在」。

### 管道

把筛选、转换、再处理串成一条线，这个想法叫管道（pipeline）。名字来自更广的编程实践：数据从左往右流过若干处理步骤，每一步的输出是下一步的输入。本章不实现自己的管道函数，只用语言现成的数组方法拼出同一条线：

`world.vars.cargo.filter(isOre).map(planOre)` 读作「从货堆里筛出矿石，再把每块矿石变成一条待放记录」。链式调用的顺序就是数据流动的顺序，先筛后换，筛掉的货不会进入换的步骤。这个顺序不是风格问题，而是正确性问题，后面讲常见错误时会看到反例。

管道有一个容易忽略的性质：每一步都是独立的。filter 不关心 map 做什么，map 不关心谁筛过它；把两步换掉一步，另一部分照常工作。这种独立性让程序好改：要把「矿石」换成「木料」，只改谓词，分配器和循环不动。反过来，如果一开始就把筛选、分配、放置全写进一个循环，改一处就得读全段。管道的价值不在省行数，而在把可以独立变化的部分分开。有些语言和函数库里，这种串联有专门的工具叫 `pipe`；本章不实现它，只用 filter 与 map 的链式调用表达同一个思想——先把数据筛成合用的，再逐项处理成想要的。

:::warn 常见误解：高阶函数只是语法糖
有人以为 filter/map 只是 for 循环的缩写，用不用都行。它们确实可以还原成循环，但价值不在写法短：filter/map 把「遍历」和「判断」分开，你只需要提供判断；一旦判断需要复用（三条规矩、两批货），分开的结构才显现出来。反过来说，如果只是跑一遍、不需要复用，写循环也完全正确。选哪种，看「做法」会不会被别人当值使用。
:::

## 3 语法与示例

先看函数值最朴素的样子。下面两个函数做同一件事，一个是函数声明，一个是先存进变量的箭头函数。

```ts caption:函数也是值：可以起名，也可以装进变量
// 函数声明：给一段步骤起名，绑定到「判断矿石」这个名字上
function 判断矿石(货) {
  return 货.kind === "ore"
}

// 箭头函数：把「一段做法」直接放进变量；注意没有调用括号
const 判断木料 = (货) => 货.kind === "wood"

// 把函数值再赋给另一个变量，两个名字指向同一个函数
const 另一条规矩 = 判断矿石

golem.say(String(另一条规矩({ kind: "ore" })))
golem.say(String(判断木料({ kind: "wood" })))
```

运行后日志会看到：灰崽先报 `true`，再报 `true`。两条调用分别验证了「矿石」和「木料」的规矩；世界方块没有变化。

这两段调用有一个共同点：`另一条规矩`、`判断木料` 先被当作值取出，再被调用。把函数当值看，`判断矿石({ kind: "ore" })` 就不再神秘——它只是先取变量，再对取出的函数加括号。括号在这里是「现在执行」的标记。

接下来把规矩真正交给高阶函数。`filter` 接收一条谓词，返回筛过的数组。

```ts caption:把一条判断规矩交给 filter
const cargo = world.vars.cargo as { id: string; kind: string }[]

// 一条规矩：吃一件货，吐「是不是矿石」
const isOre = (item) => item.kind === "ore"

const 矿石 = cargo.filter(isOre)
golem.say("矿石 " + 矿石.length + " 件")
golem.say("第一块是 " + 矿石[0].id)
```

运行后：日志先报「矿石 2 件」，再报第一块矿石的编号。`filter` 没有移动灰崽，它只在内存里造了一个新数组；原数组 `cargo` 仍然是六件货。

注意 `filter(isOre)` 里 isOre 没有括号。如果写成 `filter(isOre())`，程序会先执行 isOre，把它返回的布尔值交给 filter；filter 期待一个函数，拿到布尔值就会在遍历时出错。传「做法」还是传「结果」，是这一章最常出错的分界。

`map` 的形状与 filter 对称，只是返回值的含义变了：每个元素被换成了另一个值。

```ts caption:filter 留谁，map 换什么
const cargo = world.vars.cargo as { id: string; kind: string }[]
const isOre = (item) => item.kind === "ore"

// filter：元素是货，结果还是货，只是更短
const 矿石 = cargo.filter(isOre)
// map：元素是货，结果是每件货的编号，数量不变
const 全部编号 = cargo.map((item) => item.id)
// 串起来：先筛出矿石，再取它们的编号
const 矿石编号 = cargo.filter(isOre).map((item) => item.id)

golem.say("货共 " + cargo.length + " 件，矿石 " + 矿石.length + " 件")
golem.say("全部编号：" + 全部编号.join("、"))
golem.say("矿石编号：" + 矿石编号.join("、"))
```

运行后日志会看到三行：货的总数与矿石数、六件货的编号、两件矿石的编号。三行数字之间的关系正好说明两种方法的分工：filter 让数组变短，map 让数组变样。

闭包需要一个「外层函数声明变量、内层函数使用它」的结构。先看一个最小的计数器。

```ts caption:闭包：内层函数记住外层的变量
// 外层函数每调用一次，就创建一套新的变量环境
function 做计数器(起点: number) {
  let 当前 = 起点
  return () => {
    当前 = 当前 + 1
    return 当前
  }
}

// 两次调用得到两个互不干扰的闭包
const 数工具 = 做计数器(0)
const 数杂货 = 做计数器(0)
golem.say("工具 " + 数工具() + " 件")
golem.say("杂货 " + 数杂货() + " 件")
```

运行后：日志是「工具 1 件」和「杂货 1 件」。两个计数器各数各的，说明每个闭包拥有自己的 `当前`；`数工具` 连续调用两次会得到 1 和 2，但这段代码只调用了一次。

计数器只会加一，分配格子需要「每次取下一格」。参考解的 `planFor` 就是把计数器换成了「下标 + 格子列表」的闭包。

```ts caption:planFor：闭包记住格子列表与下一个下标
const boxes = world.vars.boxes as { ore: number[][]; wood: number[][]; food: number[][] }

// 外层接收「一排格子」，内层返回「分配下一格」的做法
const planFor = (slots: number[][]) => {
  let n = 0
  return (item: { id: string }) => {
    const slot = slots[n]
    n = n + 1
    return [item.id, slot[0], slot[1], slot[2]]
  }
}

const planOre = planFor(boxes.ore)
const 第一条 = planOre({ id: "raw_iron" })
const 第二条 = planOre({ id: "coal" })
golem.say("第一条待放：" + 第一条[0] + " 去 " + 第一条[1] + "," + 第一条[3])
golem.say("第二条待放：" + 第二条[0] + " 去 " + 第二条[1] + "," + 第二条[3])
```

运行后：第一条去矿石箱第一格，第二条去第二格。两次调用之间，闭包里的 `n` 从 0 变成 1 再变成 2，所以「下一格」真的在往下走。

两句日志里的坐标不同，是闭包里的 `n` 在两次调用之间变化的结果。可以这样验证：把 `n = n + 1` 挪到 `return` 之后，第二次调用就会读到 1 而不是 2，日志会显示两件货都去第一格。闭包的状态是活的，写在哪里、什么时候改，直接决定结果。

箭头函数返回对象要加括号，这是一个必须用代码看一眼的坑。

```ts caption:[错误示例] 箭头函数直接返回对象要加圆括号
// 花括号被当成函数体，kind 这个标签什么也不返回
const 做规矩 = (kind) => { kind: kind }
const 坏规矩 = 做规矩("ore")

// 加上圆括号，花括号才是对象字面量
const 好规矩 = (kind) => ({ kind: kind })
const 规矩对象 = 好规矩("ore")

golem.say("坏规矩返回：" + 坏规矩)
golem.say("好规矩返回：" + JSON.stringify(规矩对象))
```

运行后：日志先出现「坏规矩返回：undefined」，再出现一个带 kind 字段的对象。坏规矩不只是写法丑，它返回 undefined，后面若把 undefined 当函数调用，报错会指向调用处而不是定义处。

最后把零件拼成参考解的流水线。三段代码可以对照着看：造规矩、造分配器、拼清单。

```ts caption:[读参考解] 造规矩 + 分配格子 + 拼成待放清单
const cargo = world.vars.cargo as { id: string; kind: string }[]
const boxes = world.vars.boxes as { ore: number[][]; wood: number[][]; food: number[][] }

// 一次造出三条「是不是某一类」的规矩
const makeRule = (kind: string) => (item: { kind: string }) => item.kind === kind
const isOre = makeRule("ore")
const isWood = makeRule("wood")
const isFood = makeRule("food")

const planFor = (slots: number[][]) => {
  let n = 0
  return (item: { id: string }) => {
    const slot = slots[n]
    n = n + 1
    return [item.id, slot[0], slot[1], slot[2]]
  }
}

// 每条支线都走「filter 筛 → map 分格」，最后拼成一张清单
const 待放 = [
  ...cargo.filter(isOre).map(planFor(boxes.ore)),
  ...cargo.filter(isWood).map(planFor(boxes.wood)),
  ...cargo.filter(isFood).map(planFor(boxes.food)),
]

for (const cell of 待放) {
  golem.moveTo(cell[1], cell[3] + 2)
  golem.place(cell[0], cell[1], cell[2], cell[3])
}
```

运行后世界会看到：六件货按类别落进三只箱子的前列格子，矿石两件、木料两件、食物两件；灰崽在每格旁边停一下再放。跑完以后 `待放` 这张清单还在内存里，世界里的箱子上多了六件货。

## 4 常见错误

### 错误一：把函数值和调用结果搞混
现象：报错说「xxx is not a function」，或者程序什么也没发生。原因：传参时多写了括号。`filter(isOre)` 是对的，`filter(isOre())` 是先调用 isOre 再把它的结果（布尔值）传给 filter。改法：传「做法」时不带括号，传「结果」时才带；记住 `filter` 需要的是谓词，不是谓词的返回值。

### 错误二：先 map 后 filter，格子错位
现象：分类看起来没错，但货被放到了偏后的格子，或者某排箱子空出了前面的格。原因：`planFor` 每被调用一次就分配一格；如果先对所有货 map 分格、再 filter 掉非本类，那些被 filter 掉的货已经占掉了下标，真正的货就分到了后面。改法：顺序固定为 filter 在前、map 在后，让分配器只看见真正要处理的货。这条错误也是管道顺序为什么重要的最好例子。

### 错误三：以为闭包是快照
现象：想用闭包记录已经分了几格，结果每次分到同一格，或者计数一直是一。原因：把闭包理解成「复制了一份数值」。闭包持有的是变量绑定，读写都发生在同一个变量上。改法：把「状态变量声明在外层、修改在内层」写清楚，确认它在外层函数执行完之后仍然被内层函数引用；用日志打出每次分配的下标，验证它确实在递增。

### 错误四：箭头函数返回对象忘了圆括号
现象：函数返回 undefined，后续访问字段时报「读不到属性」。原因：箭头右边直接写花括号，被解析成函数体而不是对象。改法：`(x) => ({ ... })`；或者写成带 `return` 的完整函数体，让意图更明显。

### 错误五：在回调里改原数组
现象：流水线跑完后，货堆数组被改得面目全非，或者同一件货被处理两次。原因：在 filter 或 map 的回调里对原数组做了 push、赋值之类的事，把「读取」变成了「改写」。改法：回调只做判断与转换，处理结果放进新数组；需要积累时用 filter/map 的返回值，而不是在原数组上动手。

### 错误六：谓词返回的不是布尔值
现象：filter 筛出来的件数不对，或者把不该留的货也留下了。原因：谓词写成了赋值、字符串比较漏了半边，或者返回了「真值」而非「真」。`item.kind = "ore"` 是赋值，会让 kind 变成 ore 并返回字符串；`item.kind === "ore"` 才是比较。改法：谓词只写一个布尔表达式，不产生副作用；拿不准时用 `golem.say(String(isOre(货)))` 把谓词的结果打出来看。

## 5 与关卡任务的关系

第 7 关的任务是：给三只悦灵各一条分辨货物的规矩，把货堆分进矿石、木料、食物三只箱子；再用同一条流水线把复核箱里的错货送回原处；最后逐箱报数、回营地。世界给出 `world.vars.cargo`、`world.vars.recheck`、`world.vars.boxes`、`world.vars.recheckBoxes`；判定只看箱子里放了什么。

参考解分三阶段。第一阶段造规矩并清点：`makeRule` 生产三条谓词，分别筛出矿石、木料、食物，用 `filter(...).length` 数出每类件数并报给艾拉。这一步不改变世界，但让「规则对不对」在放货之前就暴露。第二阶段拼流水线：三条支线各自 filter 出本类货，map 用对应的分配器把每件货变成待放记录，再用展开语法拼成一张清单，循环逐条执行。第三阶段对复核箱重复同一条流水线：换的只是数据源与分配器，结构完全不变。

三阶段的分工也能解释「为什么函数只排动作单、不直接指挥织偶」。本幕的织偶调用会在顶层被自动补上等待，函数体里的调用不在这个机制覆盖范围内。所以参考解让函数只做纯计算：造规矩、算格子、拼清单；真正的移动与放置放在顶层循环里。这不是本关的怪癖，而是一个通用原则：纯计算的部分应当和产生副作用的部分分开，前者好测、好改、好复用。

这里最值得体会的是「同一条流水线」的意思。复核箱的货不同、箱子不同、方向不同，但程序没有为此多写一套逻辑：`filter(isOre).map(planRecheckOre)` 与主线只差变量名。这就是把做法抽成值的收益——结构能被复用，而不是被复制。任务里最后开笼门是玩家节拍，笼门只有活人的手能开；代码负责把三只箱子分对，悦灵按规矩出发。

还有一层关系值得点出：任务说悦灵「认规矩不认命令」。程序里对应的就是谓词——它没有名字、没有身份，只凭「是不是这一类」决定去留。你把规矩写对，悦灵就把对的货搬走；规矩写错，它一本正经地搬错。世界不会因为你的意图正确而放过错误，这和前面每一关的判定逻辑一致。

## 6 小结与练习

本章的要点可以收成五条。

1. 函数是值：能起名、能装进变量、能当参数和返回值；传值时不带括号，调用时才带。
2. 箭头函数是函数的简写；返回对象要加圆括号，参数只有一个时可省圆括号。
3. 高阶函数吃函数或吐函数；`filter` 吃谓词留下元素，`map` 吃转换函数换出元素，两者都不改原数组。
4. 闭包让函数记住创建时身边的变量，记住的是绑定不是快照；每次外层调用产生一套新的环境。
5. 管道就是「先筛后换」的链式顺序；顺序写反会让分配器把格子分给不该处理的元素。

把这五条连起来看，本章只做了一件事：把「判断」和「处理」从具体循环里抽出来，变成可以命名、传递、组合的值。抽出来之后，八件货的循环变成一条流水线，复核箱的循环变成同一条流水线。抽象不是让代码变短，是让同一套结构能应付不同的数据。

练习题不计分，建议动笔。

1. 写一条谓词 `isFood`，再用 `cargo.filter(isFood).map((item) => item.id)` 取出所有食物编号；想想如果 map 与 filter 调换顺序会错在哪里。
2. 用 `做计数器` 的思路写一个 `做报数器(名字)`，返回一个函数，调用时说出「名字 第几件」；连续调用三次，观察日志里的序号。
3. 把 `makeRule` 改成「判断一类货的重量是否超过上限」的规矩生成函数，说明它和 `makeRule("ore")` 在闭包捕获上的相同点与不同点。

延伸一句：闭包与高阶函数在真实语言里是日常工具。界面上的按钮点击回调、服务器里每个请求的处理函数、数组排序的比较函数，都是「把做法当值传」；前端框架里保存状态的 `useState` 返回一对「读当前值」和「更新值」的函数，背后也是闭包。第 8 关你会把这些能力放进记录，第 9 关会看到异步函数同样是值：`Promise.all` 接收的数组里装的就是一个个还没做完的「做法」。本章是后面几章的地基，值得多读两遍。

## 术语

- 函数值（function value）— 函数本身作为可以传递的值；给变量赋值时不调用，带括号才是调用。
- 函数声明（function declaration）— 用 `function` 关键字给一段步骤起名并创建函数值的写法。
- 函数表达式（function expression）— 把函数写在表达式位置（如赋值号右边）的写法。
- 箭头函数（arrow function）— 用 `=>` 写的函数简写；单表达式体自动返回，返回对象要加圆括号。
- 高阶函数（higher-order function）— 接收函数作为参数，或返回函数作为结果的函数。
- 回调（callback）— 先交给别人、由别人在合适时机调用的函数。
- 谓词（predicate）— 返回布尔值的判断函数；`filter` 的参数就是谓词。
- 闭包（closure）— 函数连同它创建时所在的变量环境；内层函数能继续读写外层的变量。
- 自由变量（free variable）— 不在函数参数和函数体内声明、从外层捕获的变量。
- 绑定（binding）— 名字与值之间的关联；闭包持有绑定，读到的是变量的当前值而不是旧快照。
- 流水线（pipeline）— 把多个处理步骤按顺序串起来，前一步的输出是后一步的输入。
