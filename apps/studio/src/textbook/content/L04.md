# 麦田的咒语：用循环替你把重复做完

> 从「一格格手写」到「按规则重复」，掌握 for、while 与嵌套循环

## 0 本章要解决的问题

雨一直下，上一季的麦子还长在地里；再拖下去，冬天就没粮。村里有三块麦田，每一块的行数、列数都不一样，水渠的位置也不一样。任务很明确：先把每一块田里上一季的残株收掉，再把能种的格子全部种上新麦，水渠那一行不能下种，种子用完就停，种完回谷仓。

如果用前几章学会的写法硬写，会得到一份极长的程序：每一格两行，先走再种，一块田少算也有二十格，三块田加起来一百多行。这份程序有四个问题。第一，写不动：一百多行几乎一样的动作，抄到后面注意力必然下降。第二，改不了：田的尺寸每季都在变，行数列数一换，整份程序都要重写。第三，查不出错：一百行里错一行，肉眼很难发现，运行后只能看到某处空了一格。第四，重复的代码让意图被淹没：读程序的人看到一百行 `moveTo` 加 `plant`，要很久才能明白它想做的事是「把这块田种满」。

「一格一格写」和「把田种满」之间差了整整一个抽象。人看到田会想：只要沿着每一行、每一列走一遍，遇到水渠就跳过，遇到种子用完就停。这个想法里有三件事：一个会数数的计数器、一个继续或停止的条件、一段每次都要重复的动作。把这三件事写成程序，就是循环（loop）。

本章要引入的就是循环。循环让一段动作按规则重复执行很多次，重复的次数不必在写代码时固定，可以到运行时由数据决定。田有 6 行就重复 6 次，有 7 行就重复 7 次；种子只有三成也照样能跑，种完就停。这个能力看起来只是「省几行代码」，实际上它改变了程序与数据的关系：程序不再为某一块具体的田写死，而是对「任意一块有行、列、水渠、种子的田」都成立。

先看一个让人痛的对照。下面是「写死 5 行 5 列」的一小段程序，它只能应付尺寸恰好是 5×5、恰好没有水渠的田。

```ts caption:[错误示例] 写死 5 行 5 列：田一换就错
const a = world.vars.fieldA
for (let r = 0; r < 5; r = r + 1) {
  for (let c = 0; c < 5; c = c + 1) {
    golem.moveTo(a.x + c, a.z + r)
    golem.plant("wheat", [a.x + c, 65, a.z + r])
  }
}
```

运行后世界会看到：如果这块田恰好是 5 行 5 列且没有水渠，它能把田种满；如果实际是 4 行 6 列，它会把种子种到田外，或者漏掉后面的格子；如果有一行是水渠，它会把种子丢进水里。错误的根源不是循环写错了，而是边界写死了。本章要解决的，正是让循环跟着数据走。

## 1 直觉：重复的事交给规则

循环的直觉可以用一句话概括：把「每次都要做的事」写成一段，把「什么时候继续」写成一个条件，然后让程序反复回到这段的开头。人做重复的事情时不需要每次重新想一遍，只需要知道「还差多少、下一步做什么」。循环就是把这个过程形式化。

具体到种田，人会说：从第一行开始，一行一行往下；每一行从第一列到最后一列，一格一格种；遇到水渠那一行就跳过；每一格先收残株再种新麦；种子用完了就停，别再种了。这段话里有四层结构：外层走行、内层走列、中间判断跳过、最后判断种子。前两层是重复，后两层是条件。循环与分支在这里配合，而不是互相替代。

要理解循环，先要理解「重复到什么时候」。程序不会自己判断「该停了」，它只会在每一轮开始前检查一个条件：条件为真就再来一轮，为假就退出。所以循环的条件必须是会变化的：如果条件永远为真，程序就永远出不来；如果条件一开始就是假，循环一轮也不会执行。写循环时，最重要的两个问题是「条件是什么」和「什么操作会让条件最终变成假」。

这就是循环三要素的来历。第一是初值：循环变量（loop variable）从几开始。第二是条件：满足什么条件时继续。第三是更新：每轮结束时把循环变量改成什么。三要素缺一不可：没有初值，变量没有起点；没有条件，不知道何时停；没有更新，条件永远不变，循环停不下来。for 循环把这三要素写在同一行的括号里，while 循环把它们拆到三个位置，本质相同。

循环与顺序执行不矛盾。循环的每一轮内部仍然是顺序执行：先走、再收、再种；一轮结束后，程序回到循环开头，再做下一轮。重复不是「同时做很多次」，而是「把同一段按顺序做很多次」。这个区别很重要：循环里的世界状态是逐轮累积的，前一轮种下的麦子会影响后一轮能做什么，所以循环体内部的顺序、循环的遍历顺序都会影响结果。

遍历顺序还决定了一件容易被忽略的事：外层与内层谁先走。按「外层行、内层列」遍历，就是一行一行、从左到右地把田走一遍；按「外层列、内层行」遍历，就是一列一列地走。两种顺序都能覆盖整片田，但走的路线不同，执行时间与日志顺序不同，某些任务要求的顺序也不同。本章的田按行种，外层一定是行。

数据驱动的直觉是本章的第二个重点。写死 5 与读 `a.rows` 的区别，不只是「哪个更好看」，而是「程序对什么负责」：写死意味着程序只对一种田负责，那一种田一换就错；读数据意味着程序对「任何有行列的田」负责，换田换季都能跑。隐藏测试会换田的尺寸、换水渠位置、减少种子数量，写死的程序必然失败。这不是为了刁难，而是把「程序应该适应数据」这件事变成必须做到的事。

:::aside 循环与「机器会重复」
计算机最擅长的事之一是不厌其烦地重复，而人做重复工作时会累、会走神、会漏掉一步。循环的意义不是「少打字」，而是把重复的正确性交给程序保证：同一段动作执行一千次，每一次都按同样的规则。这也是自动化的核心：人负责定义规则，机器负责不折不扣地重复规则。后面几章会把「规则」进一步抽象成函数、模块与协议，但所有抽象的底子都是本章这个「按条件反复执行」的结构。
:::

## 2 定义与机制

### 2.1 循环：条件成立就再来一轮

循环（loop）是一种控制流结构：它把一段语句包起来，反复执行这段语句，直到某个条件不再成立。被包起来的这段语句叫循环体（loop body）。每一轮执行都会先检查条件：条件为真，执行一遍循环体；执行完回到条件处再检查；条件为假，退出循环，继续执行循环后面的语句。

这个结构的关键是「回到条件处」。程序不会在循环体里自动停住，也不会自己判断「差不多了」；它只会绕回条件处，重新检查一次。所以循环的行为完全由条件与循环体的内容决定：条件写对、循环体能让条件最终变假，循环就会正常结束；否则会一直转下去，直到运行超时被强行停止。

循环与分支的关系值得说清。分支是「看条件，选一条路走一次」；循环是「看条件，决定要不要再走一遍」。两者都用条件，但分支的条件只影响这一次走向，循环的条件每轮都要重新检查。循环体内部可以有分支（比如遇到水渠就跳过），分支内部也可以只有普通语句。本章的程序两者都会用到。

### 2.2 for 循环：把三要素写在一行

`for` 循环的写法是 `for (初始化; 条件; 更新) { 循环体 }`。括号里用两个分号隔开三段：第一段在循环开始前执行一次，用来给循环变量赋初值；第二段在每一轮开始前求值，为真就执行循环体；第三段在每一轮循环体结束后执行，用来更新循环变量。三段各司其职，缺一不可。

执行顺序需要精确记住：先执行初始化一次；然后检查条件；条件为真就执行循环体；循环体结束后执行更新；再检查条件；如此反复，直到条件为假。这个顺序解释了为什么循环体能读到循环变量的当前值，也解释了为什么更新写在循环体之后。初学者常把「更新」误认为在循环体之前执行，导致对循环变量在每一轮里的值判断错误。

循环变量是 for 结构里最有用的东西。它既控制循环次数，也可以在循环体里参与计算：`a.x + c` 用列号算横坐标，`a.z + r` 用行号算前后坐标。没有循环变量，循环体就只能做完全一样的事；有了它，循环体每一轮做的是「结构相同、参数不同」的事。这正是循环能覆盖整片田的原因。

循环变量声明在 for 的括号里，它的作用域（scope）局限在循环内部：循环结束后，外面读不到这个变量。这个设计避免了很多命名冲突，也提醒读者：`r`、`c` 只在循环的语境里有意义。本章会同时写行与列两个循环变量，行变量叫 `r`，列变量叫 `c`，读代码时不要混用。

### 2.3 while 循环：条件成立就继续

`while` 循环的写法是 `while (条件) { 循环体 }`。它没有固定的初值与更新位置：初值要写在循环之前，更新要写在循环体里面。执行过程中，每一轮开始前检查一次条件，为真就执行循环体，执行完再检查。与 for 相比，while 更自由，也更危险：更新藏在循环体里，忘记写或者写错位置，循环就停不下来。

什么时候用 for、什么时候用 while？经验规则是：重复次数由计数器控制、可以提前算出大致的次数，用 for；重复到某个条件不再成立，次数不确定，用 while。本章的东田先用 while 控制「还有种子吗」，内层用 for 走列，因为列数由数据决定、但循环体内需要列号；外层用 while，因为循环还要看种子是否用完，不只是看行数。

while 的终止性（termination）必须由写代码的人保证。判断方法很朴素：找出循环体里所有可能让条件变假的操作，确认它们一定会被执行、一定会让条件朝假的方向走。比如 `while (r < a.rows && seeds > 0)`，循环体里一定有 `r = r + 1` 和 `seeds = seeds - 1` 吗？只要有一个漏掉，条件就可能永远不假。只要能说出「哪一行让条件变假」，终止性就有保障；说不出来，就要怀疑死循环。

### 2.4 嵌套循环：一行一行走遍二维

田是二维的：有行、有列。只用一个循环只能沿一个方向走，所以需要嵌套循环（nested loop）：外层管行，内层管列。外层每走一行，内层把这一行的所有列走一遍；外层走到下一行，内层再从头把下一列走一遍。两个循环合起来，覆盖田里的每一个格子。

嵌套循环的执行顺序可以想象成翻页：外层是页码，内层是行号。每翻一页（外层更新一次），内层都要从头读一遍。全部读完的总次数是「行数 × 列数」。这个乘法关系很重要：如果行数是 4、列数是 5，内层循环一共执行 20 次；如果田变大到 6 行，总次数变成 6 × 5 = 30 次。程序不需要为 20 或 30 写任何东西，外层与内层的边界从数据里读，次数自然就对。

嵌套循环里容易出现变量混用：外层的 `r` 和内层的 `c` 都是循环变量，写的时候容易把 `c` 写到外层、把 `r` 写到内层，或者坐标里把 `x + r` 与 `z + c` 写反。这类错误往往不报错，只是把田种到错误的位置。避免的方法有两个：命名上固定「r 是行、c 是列」，坐标上固定「x 加列、z 加行」；写完后拿第一格与最后一格核对：`(a.x + 0, a.z + 0)` 是左上角，`(a.x + a.cols - 1, a.z + a.rows - 1)` 是右下角。

### 2.5 边界与差一错误

循环的边界（boundary）是最容易出错的地方。田有 5 行，行的编号是 0 到 4，条件是 `r < 5`：当 r 为 0、1、2、3、4 时执行，共 5 次；当 r 为 5 时条件为假，退出。如果写成 `r <= 5`，r 会取到 5，相当于多走了一行，访问到田外的格子。这类「差一」的错误叫差一错误（off-by-one error），是循环最常见的 bug。

差一错误的根源是「个数」与「最大下标」不是同一个数。`a.rows` 是行数，下标从 0 开始，所以最大下标是 `a.rows - 1`。写条件时问自己一句：这个边界值是「数量」还是「下标」？数量用 `<`，下标用 `<=`，两者不能混。新手写 `<=` 常常是因为把「5 行」直接当成「循环到 5」，实际上是循环到 4。

测试边界的好办法是拿最小的田试。假想田只有 1 行 1 列：条件 `r < 1` 执行一次（正确）；`r <= 1` 执行两次（错误）。再假想田有 2 行：`r < 2` 执行两次（正确）。拿最小数据试边界，比盯着代码想更可靠。如果田可能为空（0 行或 0 列），`<` 会让循环一次也不执行，这是正确的；`<=` 会执行一次，访问到不存在的格子。

### 2.6 数据驱动：让循环跟着田走

数据驱动（data-driven）的意思是：循环的次数、边界、要跳过的位置，都从数据里读，而不是在代码里写死。本章的田数据放在 `world.vars.fieldA` 里，包含行数 `rows`、列数 `cols`、原点坐标 `x` 与 `z`、水渠行 `waterRow`、种子数 `seeds`，以及可种格数 `plantable`。程序读这些字段，而不是自己记数字。

数据驱动带来的好处在换田时最明显。中田与西田的行列不同、水渠行不同，程序的循环结构完全不变，只需要换数据来源。写死边界的程序每换一块田都要改循环头，改三处就可能错一处；读数据的程序改一行数据来源，其余照旧。隐藏测试会把田的尺寸与水渠位置换掉，只有数据驱动的程序能全部通过。

数据驱动还有一个隐含要求：程序不能假设「水渠只有一行」或「种子一定够」。主线的田只有一行水渠，加练的田有两行；主线的种子够种满，加练的种子只有六成。把 `r !== a.waterRow` 写成 `r !== a.waterRow && r !== a.waterRow2` 之后，没有水渠的地块里 `a.waterRow2` 是 `undefined`，比较结果恒为真，行为依然正确——这是数据驱动写法的另一个好处：多一种情况，只要数据里有位可读，逻辑就能扩展。

### 2.7 先收后种：循环体里的顺序

循环体内部的顺序与循环结构一样重要。任务要求「先收残株、再种新麦」，这句话翻译成循环体就是：走到格子、`harvest` 收掉上一季的麦子、`plant` 种下新麦。两行的顺序不能反：如果先种，成熟麦那一格会被占据，新麦种不下去；先收再种，格子先变成空气，再落新苗。

把「收」与「种」放进同一个循环体，意味着每走一格就完成一轮「收 + 种」。也可以分两个循环：第一个循环只收，第二个循环只种。两种写法都能完成任务，但循环体的顺序与循环的轮次不同：分两轮遍历时，收是完整一遍、种是完整一遍；同一轮遍历时，每一格先收后种。参考解选择同一轮遍历，因为每格的活本来就成对，一次走完更省路途。

:::warn 常见误解：循环就是「一直做」
有人把循环理解成「一直做下去」，以为循环会自己判断什么时候停。循环不会。它只会在每一轮开始前检查条件，条件为真就继续；如果条件永远为真，循环就永远不结束，程序会一直跑，直到运行超时被停止。写循环时不要依赖「它应该会停」，而要主动回答两个问题：条件是什么？哪一行让条件变假？回答不出来，就不要运行。
:::

## 3 语法与示例

### 3.1 最小 for：三要素与一次跟踪

先看一个不碰世界、只打印的 for 循环，用它把三要素与执行顺序看明白。

```ts caption:[照抄] 最小 for：初始化、条件、更新
for (let r = 0; r < 3; r = r + 1) {
  golem.say("第 " + (r + 1) + " 行")
}
```

运行后世界会看到：灰崽依次说出「第 1 行」「第 2 行」「第 3 行」，一共三句。循环结束后程序继续往下走。

把执行过程逐步写出来。第一，初始化 `let r = 0` 执行一次，r 变成 0。第二，检查 `r < 3`，0 小于 3 为真。第三，执行循环体，说「第 1 行」。第四，执行更新 `r = r + 1`，r 变成 1。第五，检查 `r < 3`，为真，执行循环体，说「第 2 行」。第六，更新后 r 变成 2，检查为真，说「第 3 行」。第七，更新后 r 变成 3，检查 `3 < 3` 为假，退出循环。

这张跟踪清单说明了三要素各自的位置与作用。初始化只在开头执行一次；条件在每一轮开始前检查；更新在每一轮循环体之后执行。循环体里之所以能说「第 (r + 1) 行」，是因为语句写的是给人看的行号，而循环变量从 0 开始。这种「程序从 0 数、人从 1 数」的换算在循环里很常见，写多了自然会习惯，初学时先在纸上把 r 的值列清楚。

### 3.2 数据驱动：按行、列走遍整片田

把 for 的边界换成田数据，就能对任意大小的田遍历。下面这段程序对东田逐格执行「先收后种」，并跳过水渠行。

```ts caption:[照抄] 数据驱动：按行列遍历东田，跳过水渠
const a = world.vars.fieldA
for (let r = 0; r < a.rows; r = r + 1) {
  for (let c = 0; c < a.cols; c = c + 1) {
    if (r !== a.waterRow) {
      golem.moveTo(a.x + c, a.z + r)
      golem.harvest("wheat", [a.x + c, 65, a.z + r])
      golem.plant("wheat", [a.x + c, 65, a.z + r])
    }
  }
}
```

运行后世界会看到：东田里除水渠行以外的每一格先被收走残株、再种下新麦；水渠行的水保持原样，没有种子落进去。程序内部，外层 r 从 0 走到 `a.rows - 1`，内层 c 从 0 走到 `a.cols - 1`，每一次内层循环处理一格。

逐层读这段程序。`const a = world.vars.fieldA` 把田数据拿进程序，后面用 `a.rows`、`a.cols` 等字段。外层 `for` 的初始化是 `let r = 0`，条件是 `r < a.rows`，更新是 `r = r + 1`。内层 `for` 同理，变量是 c，边界是 `a.cols`。内层的 `if (r !== a.waterRow)` 在每一轮检查当前行是不是水渠行：不是水渠，执行收与种；是水渠，整块跳过，内层继续走到下一列。

`[a.x + c, 65, a.z + r]` 是 `harvest` 与 `plant` 要求的坐标写法：一个方括号里放三个数，依次是 x、y、z。本章的田都在 y=65 这一层，所以高度写 65；横坐标是田原点的 x 加列号，前后坐标是田原点的 z 加行号。把行列换算成坐标的规则记牢：列影响 x，行影响 z。

执行顺序也值得跟踪一遍。假设东田 3 行 4 列、水渠在第 1 行。外层的执行是：r=0，内层 c=0、1、2、3 依次处理第一行四格；r=1，内层 c=0 时检查发现这是水渠行，整块跳过，c=1、2、3 也都跳过；r=2，内层处理第三行四格。总处理格数是 3 × 4 减去水渠行的 4 格，共 8 格。检查点：每一格的处理顺序是「走、收、种」，一步不少，一步不漏。

### 3.3 条件驱动：种子用完就停

主线的种子够种满，但加练的田种子只有六成。这时外层循环不能只看行是否走完，还要看种子是否用完。把外层从 for 改成 while，条件变成「还有行可走并且还有种子」，循环体里每收一格就减一枚种子。

```ts caption:[照抄] while：种子用完就停
const a = world.vars.fieldA
let seeds = a.seeds
let r = 0
while (r < a.rows && seeds > 0) {
  for (let c = 0; c < a.cols; c = c + 1) {
    if (r !== a.waterRow && seeds > 0) {
      golem.moveTo(a.x + c, a.z + r)
      golem.harvest("wheat", [a.x + c, 65, a.z + r])
      golem.plant("wheat", [a.x + c, 65, a.z + r])
      seeds = seeds - 1
    }
  }
  r = r + 1
}
```

运行后世界会看到：东田按行、列顺序逐格收种，直到种子用完为止；种子不够时，后面的格子保持原样。程序内部，`seeds` 从 `a.seeds` 开始，每处理一格减一；`r` 每处理完一行加一；两个条件都在每一轮开始前检查。

这段程序有两处条件需要解释。外层 `while (r < a.rows && seeds > 0)` 用 `&&` 连接两个条件：行还没走完、并且种子还有剩余，两个都成立才继续。内层 `if (r !== a.waterRow && seeds > 0)` 除了跳过水渠，也检查种子：如果一行还没走完种子就用完了，内层剩下的列不再处理，直接结束这一行。为什么内层也要检查种子？因为外层条件只在每一行开始时检查一次，一行之内种子可能用完；内层不检查，就会在种子为 0 之后继续尝试种，虽然 harvest 空格是 no-op，plant 却会失败。

`seeds = seeds - 1` 是让循环最终停止的关键一行。没有它，`seeds > 0` 永远为真，外层循环永远不结束；写错成 `seeds = seeds + 1`，种子越用越多，同样停不下来。每一轮减少一次，减少的条件与检查的条件一致，循环就一定会在种子耗尽时退出。把「哪一行让条件变假」说清楚，是 while 循环的安全检查。

跟踪一下种子的值：假设 `a.seeds` 是 5。处理第一格后 seeds=4，第二格后 3，第三格后 2，第四格后 1，第五格后 0。第六格开始时内层条件 `seeds > 0` 为假，跳过；这一行结束后外层检查 `seeds > 0` 为假，退出。总共种了 5 格，正好用掉 5 枚种子。这个例子说明「数据驱动 + 条件驱动」的写法：种子数来自数据，停止条件来自种子本身，程序没有任何写死的数字。

### 3.4 三块田：同一段结构换数据

东田、中田、西田的尺寸与水渠位置不同，但处理逻辑相同。最直接的写法是把同一段结构抄三遍，只换数据来源与变量名。

```ts caption:[照抄] 东田完整流程：种完报数并回谷仓
const a = world.vars.fieldA
let seeds = a.seeds
let r = 0
while (r < a.rows && seeds > 0) {
  for (let c = 0; c < a.cols; c = c + 1) {
    if (r !== a.waterRow && seeds > 0) {
      golem.moveTo(a.x + c, a.z + r)
      golem.harvest("wheat", [a.x + c, 65, a.z + r])
      golem.plant("wheat", [a.x + c, 65, a.z + r])
      seeds = seeds - 1
    }
  }
  r = r + 1
}
golem.say("东田：种下了 " + (a.seeds - seeds) + " 格")
golem.moveTo(barn)
```

运行后世界会看到：东田被收好种满，灰崽报出「东田：种下了 N 格」，然后走回谷仓。报数里的 N 是 `a.seeds - seeds`，也就是「一开始有多少种子，减去还剩多少」，正好等于种下去的格数。这个减法不依赖任何写死的数字，换一块田自动正确。

中田与西田照同一段写，把 `fieldA` 换成 `fieldB`、`fieldC`，把变量名换掉避免重复声明。三段程序结构一样，这不是「复制粘贴的坏习惯」，而是第 5 章「函数」要解决的问题：把这段结构收成一个有名字的步骤，三块田各调用一次。现在还没有函数，先用三段相似代码把流程跑通；等到第 5 章再回来，你会发现这三段可以压缩成一段定义加三次调用。

为什么变量名要换？同一段结构抄三遍时，`const a`、`let seeds`、`let r` 这些名字在同一个程序里不能重复声明。第二段用 `const b`、`let seedsB`、`let rB`，第三段用 `const c`、`let seedsC`、`let rC`。名字带田的标记，既避免重复，也让报数时能分清是哪块田。这种「为了区分而加的标记」是临时的；函数出现后，这些名字会变成参数，不再需要手写后缀。

### 3.5 边界实验与执行路径

下面两段是反例实验。第一段把条件写成 `<=`，第二段忘了更新。

```ts caption:[错误示例] 条件写成 <=：多走一行
const a = world.vars.fieldA
for (let r = 0; r <= a.rows; r = r + 1) {
  for (let c = 0; c < a.cols; c = c + 1) {
    golem.moveTo(a.x + c, a.z + r)
    golem.say("走到第 " + (r + 1) + " 行")
  }
}
```

运行后世界会看到：程序会多走一行，那一行的坐标已经出了田的范围；如果那一格附近有可站的位置，灰崽会站上去并说出「走到第 a.rows + 1 行」，暴露越界。把 `<=` 改回 `<`，最后一行的坐标就落在田内。

```ts caption:[错误示例] 忘记更新：循环停不下来
let r = 0
while (r < 5) {
  golem.say("第 " + r + " 行")
}
```

运行后世界会看到：这句话被反复说出，r 一直是 0，条件 `r < 5` 永远为真，循环永远不结束，直到运行超时被停止。原因是循环体里没有任何一行改变 r。修法是在循环体末尾补 `r = r + 1`，让 r 每一轮向 5 靠近。这个反例要记住的不是「别忘写」，而是「每一轮都要让条件朝假的方向走一步」。

再看一个完整的执行路径。假设东田 3 行 4 列、水渠行是第 1 行、种子足够。执行路径是：外层 r=0 → 内层 c=0、1、2、3，每格走、收、种 → 外层更新 r=1 → 内层 c=0 时判断水渠，跳过；c=1、2、3 同样跳过 → 外层更新 r=2 → 内层 c=0、1、2、3，每格走、收、种 → 外层更新 r=3，条件 `3 < 3` 为假，退出。

这个路径可以用面积来核对：处理格数 = 行数 × 列数 − 水渠格数。如果实际处理的格数与这个公式不一致，就说明边界或跳过逻辑有问题。核对时不要凭印象，写出实际处理过的格子数，与公式对照。这个核对方法对任意尺寸的田都成立，也是隐藏测试会检查的内容。

:::tip 循环自查清单
写完一个循环，按顺序检查五件事：初值给了吗？条件用的是「数量」还是「下标」？哪一行让条件最终变假？循环体里的坐标换算对不对（列管 x、行管 z）？有没有该跳过的格子（水渠）没跳过？五件事都能答出来，循环才算写明白。检查时用最小的田（1 行 1 列）试一遍边界，往往能立刻发现差一错误。
:::

## 4 常见错误

### 错误一：条件用 `<=`，多走一行

现象：程序运行后多处理了一行，种子被种到田外，或者灰崽走到一个不该去的坐标。原因：`a.rows` 是行数，下标最大是 `a.rows - 1`；条件写成 `r <= a.rows` 会让 r 取到 `a.rows`，越界一行。改法：数量用 `<`，下标用 `<=`；拿 1 行的田测试，`r < 1` 执行一次是对的，`r <= 1` 执行两次是错的。

### 错误二：把行数、列数写死

现象：换一块田、换一季尺寸，程序就种不满或种到田外。原因：循环条件里写的是 `5`、`6` 之类的数字，而田的实际尺寸来自数据。改法：条件里读 `a.rows`、`a.cols`，水渠读 `a.waterRow`，种子读 `a.seeds`。写死后写代码省事，但隐藏测试换数据时就会失败。

### 错误三：忘记更新，或者更新写错变量

现象：程序一直运行不结束，最后超时被停止；或者某一轮突然结束得太早。原因：`while` 循环的更新写在循环体里，忘记写、写错位置、写错变量，条件都会永远为真或提前变假。改法：循环体末尾集中写更新，并检查更新的变量就是条件里检查的那个；每轮结束时问一句「条件离变假更近了吗」。

### 错误四：把种子种进水渠

现象：水渠那一行出现新麦，检验失败；或者程序报告「这里不能种」。原因：循环体没有跳过水渠行，或者跳过条件写错（例如把 `r !== a.waterRow` 写成 `r === a.waterRow`，正好反了）。改法：把跳过判断放在循环体最前面，先判断这一行是不是水渠，再走进、收、种；用两行水渠的田测试，确认两行都被跳过。

### 错误五：先种后收，顺序颠倒

现象：成熟麦那一格种不下新麦，或者收成数量不对。原因：循环体里 `plant` 写在 `harvest` 前面，成熟麦还占着格子。改法：同一格先 `harvest` 收残株，再 `plant` 种新麦；顺序与任务描述一致。检查方法：读循环体，确认 harvest 出现在 plant 之前。

### 错误六：循环变量混用，行列写反

现象：程序能运行、能种完，但种的位置整片偏移，或者把行数当列数用。原因：外层变量与内层变量混用，或者坐标里把「x 加行、z 加列」写反。改法：固定命名习惯（r 行、c 列），固定坐标规则（列加 x、行加 z）；写完后核对左上角 `(a.x, a.z)` 与右下角 `(a.x + a.cols - 1, a.z + a.rows - 1)` 两个位置。

## 5 与关卡的关系

L04 的主任务是三块田「先收残株、再种满、跳过水渠、种完回谷仓」。三条目标分别检查三件事：先收后种的顺序、能种的地方都种上、最后回到谷仓。三条都不是「写死某一块田」能过的，因为三块田的尺寸与水渠位置不同，检验还会读取田数据核对每一格。

第一条目标「先收掉上一季留下的残株」检查顺序。注意残株不是在每一格都有，只有成熟麦所在的格子才有；`harvest` 在空格上是 no-op，不会报错。所以程序不需要先知道哪些格子有残株，只要对每一格都执行一次 harvest，成熟的收走、空的跳过。这个「统一处理、按数据自适应」的思路与循环本身一致。

第二条目标「把能种的地方都种满」检查覆盖与边界。程序必须遍历每一行每一列，跳过水渠行，种子不够时停下来；最终田里的新麦数量要等于「可种格数与种子数中较小的那个」。如果循环多跑一行，种子会被种到田外；如果少跑一行，田里会空出一条；如果漏了跳过水渠，种子会丢进水里。三种错误都会在这一条上失败。

第三条目标「种完回谷仓」检查收尾。三块田都种完之后，灰崽要走到谷仓附近。这一步容易被忽略：前面循环写得很完整，最后忘了 `moveTo(barn)`，目标面板上就会有一条不勾。写程序时把「任务要求」逐条列在纸上，每写完一条就勾掉，比运行后看结果再补要快。

本关的数据里还有两个细节值得注意。第一，田的成熟格记录在 `world.vars.matureCellsA` 这类数据里，参考解不需要读它，因为「每格都收一次」已经覆盖了所有成熟格；它适合在复查时使用，比如只检查成熟格是否都变成了新苗。第二，种子数与可种格数的关系：主线田的种子刚好够种满可种格，加练田的种子只有六成。程序用 `seeds > 0` 作为停止条件，两种田都能跑，只是加练田会提前停。

玩家节拍是「把南瓜头放到干草捆上，让稻草人立起来」。这一步与代码里的循环无关，是任务结构的收尾动作，与 L01 的第 4 盏灯、L02 的蛋糕同类。工作台的目标面板会显示三条主线目标，卡住时先看面板，再回到循环里找对应的问题：残株没收、田没种满、或者忘了回谷仓。

## 6 小结与练习

本章的要点收成六条。

- 循环把一段动作按条件反复执行；循环体每轮执行一次，条件在每轮开始前检查。
- for 的三要素是初始化、条件、更新，三者在括号里用分号隔开；更新在每轮循环体之后执行。
- while 的初值写在循环前，更新写在循环体里；写 while 时必须能指出「哪一行让条件最终变假」。
- 嵌套循环外层走行、内层走列，覆盖二维数据；坐标换算规则是列加 x、行加 z。
- 边界要用数量与下标区分：行数列数是数量，用 `<`；下标最大值是数量减一。差一错误靠小数据测试发现。
- 数据驱动的循环从数据里读尺寸、水渠与种子数，换田换季只换数据来源；循环体里先收后种，水渠行跳过。

练习不计分，也不需要提交。建议先用手算或纸笔跟踪，再到关卡里验证。

1. 用跟踪表写出 `for (let i = 0; i < 4; i = i + 1) { golem.say("第 " + (i + 1) + " 行") }` 每一轮 i 的值、条件结果与输出，一共说几句话？
2. 把本章东田程序的外层条件从 `r < a.rows` 改成 `r <= a.rows`，田有 3 行时会发生什么？哪一行的坐标会出界？
3. 本章 while 循环里，如果删掉 `seeds = seeds - 1`，运行会怎样？如果把它改成 `seeds = seeds - 2`，种子为 5 时能种几格？
4. 一块田 4 行 6 列，水渠在第 0 行，种子足够。手工算出程序一共处理多少格、内层循环执行多少次、外层执行多少次。
5. 把东田程序改成处理中田：需要改哪些行？哪些地方必须保留（比如 `a.rows` 的读法）？为什么不能只改 `fieldA` 为 `fieldB` 而保留变量名 `a`？
6. 写一段程序：对西田逐格执行「先收后种」，但只在第 2 行到第 4 行之间工作（用条件控制），种子用完就停。写出循环条件与判断条件。

## 7 延伸

循环与分支一起，让程序具备了表达任意计算的能力。没有循环，程序只能处理固定数量的数据；有了循环，程序可以对任意长的数据做同样的事。计算理论里，图灵机的基本操作就是「读一个格子、判断、写、移动」，重复这些操作直到停机；循环正是这种重复在语言层面的表达。理解循环，你就能理解为什么程序可以不随数据量增长而变长。

真实语言里，循环有更多形态。C 与 JavaScript 保留 for、while、do-while；Python 的 for 遍历序列，写法更接近「对每个元素做一次」；现代语言还提供 `forEach`、`map`、`filter` 这类高阶方法，把「遍历」与「做什么」分开。本课程在第 7 章会见到其中一部分：把「做什么」写成函数传给 `filter`、`map`，循环的骨架由语言提供，你只写意图。本章手写的 for 与 while 是那些写法的基础：不理解循环怎么走，就看不懂高阶方法在背后做了什么。

循环也有代价。差一错误、终止性问题、循环体里的状态累积，都需要写代码的人仔细检查；循环越多、嵌套越深，程序越难推理。工程上有很多降低循环风险的办法：用数据驱动边界、把循环体抽成小函数、给循环写清楚不变量（invariant，指每一轮结束时都成立的性质，比如「前 r 行已经处理完毕」）。本章的东田程序就有一个隐含的不变量：每一轮开始时，前 r 行已经全部处理完。想清楚不变量，循环的正确性就有了检查点。

## 术语

- 循环（loop）— 让一段语句按条件反复执行的控制流结构；每轮开始前检查条件，为真则执行循环体。
- 循环体（loop body）— 循环中反复执行的那段语句，用一对花括号包起来。
- 循环变量（loop variable）— 控制循环次数、并在循环体里参与计算的变量；示例：`for (let r = 0; …)` 里的 `r`。
- 迭代（iteration）— 循环体执行一轮；一轮叫一次迭代。
- 嵌套循环（nested loop）— 一个循环写在另一个循环里面，外层每走一步，内层完整走一遍。
- 边界（boundary）— 循环开始与结束的取值；行数、列数是数量，最大下标是数量减一。
- 差一错误（off-by-one error）— 循环多执行一次或少执行一次的错误，常由 `<` 与 `<=` 混用引起。
- 终止条件（termination condition）— 让循环退出的条件；写 while 时必须能指出哪一行让条件最终变假。
- 死循环（infinite loop）— 条件永远为真、不会自行结束的循环；运行超时会被停止。
- 循环不变量（loop invariant）— 每一轮结束时都成立的性质，用来检查循环是否正确；示例：前 r 行已经处理完毕。
- 数据驱动（data-driven）— 循环的边界与次数从数据里读取，而不是在代码里写死。
