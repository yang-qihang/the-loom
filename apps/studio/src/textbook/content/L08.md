# 同一种心跳：接口、组合与计划执行分离

> 用一张能力清单描述机器，把动作单排好再交给织偶执行

## 0 本章要解决的问题

第 7 章把做法变成了可以传递的值。可工坊里的机器还带来一个新问题：每台机器长得不一样、名字不一样、开关位置不一样，但它们要做的事高度一致——能启动、能停机、能报出自己的状态。如果按名字一台台写，程序会变成一串 `if (名字 === "熔炉组")`；来一台没见过的机器，就得再加一条分支。第九章、第十章还会遇到同样结构的代码：任务不同，协调方式相同。

本章要把「做什么」和「是谁」分开。一台机器是谁、叫什么名字、合闸位在哪一格，这些是数据；一台机器能启动、能停机，这是能力。用一张能力清单（接口）描述后者，让所有机器按同一张清单说话，于是启动逻辑写一遍就能叫醒所有机器，包括以后才出现的新机器。

另一件在本章第一次明确的事，是计划与执行分离。本幕的织偶动作会被自动补上等待，而自动等待只改写顶层语句。所以参考解把「该做什么」先排成一张动作单，再由一层很薄的顶层循环照着单子执行。计划是纯数据，可以被拼接、检查、重排；执行是副作用，集中在一处。这种分工不只为了绕开机制限制，它本身就是一种值得学会的组织方式。

把这一章前后串起来看，会发现它讲的三件事是同一件事的三个层面。接口解决「按什么说话」——所有机器对同一种方式回应；组合解决「怎么复用」——不靠复制、不靠血缘，靠把能力拼起来；计划与执行分离解决「谁负责决定、谁负责动手」——决定归数据，动手归一处。三件事合起来，程序从「为每台机器写一段」变成「为一种能力写一段」。

## 1 直觉：插头和插座

接口（interface）这个词容易让人想到「继承」「父子类」。先用一个日常的东西把直觉立住：插头和插座。墙上的插座不关心插上来的是一台灯、一个充电器还是一台风扇，它只约定三件事——几个孔、孔的间距、能通多大的电。任何满足这个形状的插头都能插进去用。插座定义的是「能对接的形状」，不是「谁的亲戚」。

把插头换回机器：所有机器只要能启动、能停、能报状态，就对上了工坊的「插座」。启动函数拿到一台机器，按清单调用 `startSteps`，不需要知道它是熔炉组还是红石门。反过来说，如果启动函数里出现「熔炉组」三个字，它就不再是通用零件，而是一段只为某台机器写的代码。

这个类比还能再往前推一步。插座不关心插头背后是什么电器，但它确实约定了电的规格；接口不关心机器内部怎么实现，但它确实约定了方法的签名。约定清楚，双方才能互相信任：启动方相信「调用 startSteps 一定能拿到动作单」，机器方相信「启动方会按顺序执行这些动作」。这种双向信任就是契约。契约不是法律条文，它是代码之间可以依赖的稳定表面。

接口的稳定表面还带来一个调试上的好处：出问题时，你只需要检查两件事——机器有没有按清单实现，执行方有没有按清单调用。两件事之外的部分（谁造了机器、机器内部怎么算动作单）可以暂时不看。这把问题的范围从「整个程序」缩到「一张清单的两端」。

这也解释了接口和「名字」的关系。名字是数据，会变；能力是形状，相对稳定。按名字写逻辑，换一台机器就要改代码；按能力写逻辑，换一台机器只需要换数据。第 6 章用判别字段决定「分哪一类」，这里用能力清单决定「能怎么用它」，两者都在把「变化的东西」移到数据里。

## 2 定义与机制

### 接口与能力清单

接口（interface）声明一组成员：属性、方法、参数与返回值的形状。本章的 `Machine` 声明三项：`name` 与 `status` 是属性，`startSteps()` 与 `stopSteps()` 是方法。接口本身不产生任何运行时代码，它是一张清单，规定「能被称为 Machine 的值必须长这样」。

接口的写法有几个细节。属性之间用分号或换行分隔，类型写在冒号后面；方法写成 `名字(参数): 返回类型`，不写花括号里的实现。`status: "正常" | "过热"` 又一次用到字面量联合：接口不只是说「有个 status」，而是说「status 只能是这两个值之一」。清单越精确，实现方越不容易写错，调用方也越敢依赖。

接口不检查「谁声明了实现」。这一点和第 6 章的类型别名一致：它们都是编译期的事，运行时被擦除。所以不要指望接口在运行时拦住一个形状不对的数据——真正的护栏由运行时检查与测试提供。接口的职责是让写代码的人在编译期就看见不匹配。

接口与类型别名有一个分工值得记住：类型别名更常用来描述「数据长什么样」，接口更常用来描述「一个值能做什么」。两者在 TypeScript 里可以互换，写法上的选择只是让意图更清楚。本章用 `type Step` 描述动作单这种纯数据，用 `interface Machine` 描述能力，读代码的人一眼能分出「数据」与「能力」。

方法声明只写签名（method signature），不写实现：`startSteps(): Step[]` 表示「调用它不需要参数，返回一个 Step 数组」。实现（implement）由具体对象提供。一个值满足接口，不一定要写 `implements` 关键字：TypeScript 使用结构化类型（structural typing），只要形状对得上，就可以当这个接口用。这是它和很多面向对象语言最不同的地方——判断兼容性看的是形状，不是声明过的血缘。

### 结构化类型与多态

结构化类型带来一个直接好处：不同来源的对象可以放进同一个数组。参考解里，`world.vars.machines` 里的每条数据先用 `machineOf` 转成 `Machine`，再用 `map` 得到 `Machine[]`。数组里的每一项都保证有那四项成员，循环体因此可以统一调用。把「同一段代码作用于不同类型的值」这件事叫多态（polymorphism）。本章的多态不靠继承，靠的是「都满足同一张清单」。

多态让代码对「以后」友好。任务说验收会换一批机器，甚至送来一台没见过的机器；只要它能启动、能停机、能报状态，机器清单就装得下它，`runAll` 就能叫醒它。启动函数不需要知道它叫什么，因为没有一处代码依赖具体名字。

多态在代码里的表现往往是一个循环。循环变量声明成接口类型，循环体只调用清单成员；数组里具体是什么由数据决定。这种写法把「有多少台机器」「机器叫什么」全部交给数据，代码只描述「每台机器都要被启动」。以后新增机器，数组多一项，循环体一个字不用改。

要检验自己有没有真的写出多态，可以做一个小实验：把机器清单里的名字全部换成编造的（比如 A、B、C），运行程序。如果照常工作，说明代码只依赖能力；如果报错或行为不对，说明某处还藏着名字或坐标。

### 组合优于继承

面向对象里有另一种复用方式叫继承（inheritance）：让子类拥有父类的全部能力，再追加或改写。继承在「确实是一种」的关系里成立，机器之间却没有这种关系——联动机不是某种更具体的熔炉组。硬造一条继承链，会把「是什么」和「能做什么」绑死，改一处影响一串。

本章采用的组合（composition）是横向拼装：把两台机器的动作单拼成一台新机器的动作单。`combine(a, b)` 返回的仍然是一个满足 `Machine` 的对象，它的 `startSteps` 是 `[...a.startSteps(), ...b.startSteps()]`，`stopSteps` 是 `[...b.stopSteps(), ...a.stopSteps()]`。新机器没有复制任何一行原机器的实现，它只是把两个「能力」按顺序缝在一起。组合的可贵之处是：新机器和原机器是同一种形状，可以继续被组合、被放进数组、被同一套代码处理。

组合与继承的差别可以落在一句话上：继承说「这也是一种」，组合说「这也有那些能力」。联动机不是一种熔炉组，它同时有两台机器的动作，所以它不该继承熔炉组。硬用继承，你会得到一个「继承熔炉组、再偷偷加红石门行为」的怪东西，名字和行为对不上，后面谁读都困惑。

组合还有一个继承没有的优点：方向由你决定。动作单的拼接顺序写在 `combine` 里，想让联动机先启动哪台就拼哪台；继承的成员顺序由类结构决定，改起来要动整个继承链。本章的联动机启动是 a 再 b，停机是 b 再 a，这个「启停对称、顺序相反」的约定就写在组合函数里，读一眼就明白。

### 计划与执行分离

计划（plan）在本书里指一份纯数据（plain data）：要做哪些动作、每步对哪一格、报什么名字。本章的动作单类型 `Step` 就是计划的一条，`Step[]` 就是整张计划。排计划（planning）只做计算，不碰世界；执行（execution）照着计划移动、放置、说话。

为什么值得分开？第一，计划可检查。排完之后可以先数条数、先看顺序，甚至先打印出来，再决定执不执行。第二，计划可复用。`runAll` 和 `stopAll` 各自生成一段计划，拼起来就是整场流程；要调顺序只动拼接处。第三，副作用集中。所有会改变世界的调用都挤在同一个循环里，出问题只需看这一段。第四，本幕的机制要求如此：函数体里藏着的织偶调用不会被自动补等待，所以函数只排动作单、顶层负责真的做。

计划与执行分离在真实工程里有更多名字：命令模式、事件队列、任务调度、构建流水线。名字不同，骨架相同——先产生一份可检查的描述，再由一个执行器消费它。好处在规模变大时更明显：计划可以被打印、被比较、被存档、被重放，而「直接动手」的代码只能重跑。

对初学者来说，这条原则有一个很实用的判断标准：一个函数里如果既有「算」又有「做」，就考虑拆开。算的部分不需要世界，做的那部分尽量短。本章的 `runAll`、`stopAll` 是算，执行循环是「做」；这样的代码读的时候可以一段一段读，错的时候可以一段一段查。

### 启停顺序

启动与停机的顺序不是随意的。启动按照清单顺序逐个来，遇到状态为「过热」的机器，当场补一条停机动作，避免它带着故障继续运行。收工停机则按反序：最后启动的先停，最先启动的最后停。反序的理由和收摊一样：后启动的机器可能依赖先启动的机器提供的环境，先停依赖方，再停被依赖方，才不会被半路断供。这个「后进先出」的顺序在真实系统里也常见，学到后面会看到它的另一面：栈、撤销、资源释放，都是同一个道理。

过热机器的处理是启停顺序里的特例。设计意图是：发现一台机器过热，先把它停了再继续启动下一台，而不是等全部启动完再回头处理。这个选择把「安全」放在了「效率」前面——一台过热的机器多转一会儿，代价可能比多一次停机动作大得多。计划生成函数里那句 `if (m.status === "过热")` 就是这条策略的落点。

策略写在计划里而不是执行里，也有好处：执行层不知道「过热」是什么，它只认识 on 与 off。以后想加一种「冷却中」状态，改的只是计划生成函数与数据，执行层不用动。

## 3 语法与示例

先写清单本身。接口声明、动作单类型、以及一个「形状满足就算数」的对象。

```ts caption:接口只是一张能力清单
interface Machine {
  name: string
  status: "正常" | "过热"
  startSteps(): Step[]
  stopSteps(): Step[]
}

type Step = {
  kind: "on" | "off"
  pos: [number, number, number]
  name: string
  status: string
}

// 没有写 implements，形状对得上就能当 Machine 用（结构化类型）
const 一台: Machine = {
  name: "熔炉组",
  status: "正常",
  startSteps: () => [],
  stopSteps: () => [],
}
golem.say(一台.name + "：" + 一台.status)
```

运行后：日志出现「熔炉组：正常」。对象里的两个箭头函数返回空数组，表示这台机器暂时没有动作；世界没有变化。

这段代码里有两个值得注意的地方。`Step` 被引用时还没有声明，这在类型世界里没问题：类型声明不按文本顺序执行，编译器先收集所有声明再检查。`一台` 这个对象没有写 `implements Machine`，只是因为形状对得上就被接受——结构化类型的名字就是这么来的：它看的是结构。

注意到 `Step` 用了 `kind: "on" | "off"`：这又是第 6 章的可辨识联合，`kind` 是判别字段。机器把「开」和「停」都表示成同一种数据形状，执行层就能用同一个循环处理两种动作。

接下来把数据变成机器。`machineOf` 是「造机器」的函数：吃一条机器数据，吐一个满足清单的对象。

```ts caption:machineOf：把数据造造成接口形状
function machineOf(spec: MachineSpec): Machine {
  return {
    name: spec.name,
    status: spec.status,
    startSteps() {
      return [{ kind: "on", pos: spec.switchPos, name: spec.name, status: spec.status }]
    },
    stopSteps() {
      return [{ kind: "off", pos: spec.switchPos, name: spec.name, status: spec.status }]
    },
  }
}
```

运行后（如果接上真实数据）：每调用一次就得到一台机器，它的启动单和停机单各有一条动作。`startSteps` 与 `stopSteps` 里没有移动、没有放置，只有构造数据——这正是计划与执行分离在最小函数上的样子。

`machineOf` 没有一行与世界交互。它把「机器数据」翻译成「机器能力」，返回的对象里装的是两个函数。函数值在这里第二次出场：第 7 章用函数值传递判断，本章用函数值描述能力。一个对象只要带上这两个函数，就自动拥有「能被启动」的资格。

有了清单和构造函数，就可以写不依赖名字的通用代码。

```ts caption:[片段] 多态：按清单调用，不按名字调用
const specs = world.vars.machines as MachineSpec[]
const fleet: Machine[] = specs.map(machineOf)

for (const m of fleet) {
  golem.say(m.name + "：" + m.status)
}

// 这个函数只认识清单上的三项，永远不需要知道具体是哪台机器
function 报状态(m: Machine): void {
  golem.say(m.name + " 状态 " + m.status)
}
报状态(fleet[0])
```

运行后：日志逐台报出机器名与状态，然后再报一次第一台的状态。循环和函数里都没有出现任何机器名字；清单里加几台，日志就多几行。

这段代码里 `fleet` 的类型被显式标成 `Machine[]`，这一点值得留意。`specs.map(machineOf)` 的结果本来就可以被推断，显式标注把「这里的每一项都满足清单」写成了承诺；一旦 `machineOf` 的返回形状被改坏，标注处会先报错。类型标注的作用不是啰嗦，而是在关键接口处留一个检查点。

组合比继承更短，也更直接。把两台机器的动作单缝成一台新机器：

```ts caption:combine：把两个能力缝成一个
function combine(a: Machine, b: Machine): Machine {
  return {
    name: a.name + "与" + b.name + "联动机",
    status: a.status === "过热" || b.status === "过热" ? "过热" : "正常",
    startSteps() {
      return [...a.startSteps(), ...b.startSteps()]
    },
    stopSteps() {
      return [...b.stopSteps(), ...a.stopSteps()]
    },
  }
}

const 联动 = combine(fleet[0], fleet[2])
golem.say(联动.name + " 启动单 " + 联动.startSteps().length + " 条")
```

运行后：日志报出联动机的名字与启动单条数（两台机器各一条，所以是 2）。联动的停机单是两台机器停机单的反序拼接；这里没有复制任何原机器的代码，也没有新建父子关系。

联动机的 `status` 用两个条件相或来判断过热：任一台过热，联动机就算过热。这是组合时唯一需要「合并语义」的地方——名字拼接、动作拼接都只是机械操作，状态合并却要人来定规则。写组合函数时，先问自己哪些字段需要合并语义，哪些字段可以简单拼接。

计划生成函数只做数组拼接，不碰世界。

```ts caption:runAll 与 stopAll：生成计划，不执行
function runAll(ms: Machine[]): Step[] {
  const steps: Step[] = []
  for (const m of ms) {
    steps.push(...m.startSteps())
    if (m.status === "过热") {
      steps.push(...m.stopSteps())
    }
  }
  return steps
}

function stopAll(ms: Machine[]): Step[] {
  const steps: Step[] = []
  const reversed = ms.slice().reverse()
  for (const m of reversed) {
    steps.push(...m.stopSteps())
  }
  return steps
}

const plan = [...runAll(fleet), ...stopAll(fleet)]
golem.say("计划共 " + plan.length + " 条动作")
```

运行后：日志报出计划条数。没有一台机器被真的启动，因为这段代码里没有任何移动与放置；计划只是内存里的数组。

两个函数的差别只在遍历方向与调用的方法。`runAll` 里多出的那个 `if` 处理过热：启动一台、发现过热、立刻补一条停机。`stopAll` 用 `slice().reverse()` 复制一份再反转，避免改到调用方传进来的数组——计划函数不应该偷偷修改输入。

最后是执行层。它只认识 `Step` 的字段，不关心计划是谁排的。

```ts caption:执行层：照单办事，副作用集中在这里
const lever = world.vars.lever as [number, number, number]

for (const step of plan) {
  const standX = step.pos[2] <= -10 ? step.pos[0] : (step.pos[0] > 0 ? step.pos[0] - 4 : step.pos[0] + 4)
  const standZ = step.pos[2] <= -10 ? step.pos[2] + 4 : step.pos[2]
  golem.moveTo(standX, standZ)
  if (step.kind === "on") {
    golem.place("redstone_block", step.pos[0], step.pos[1], step.pos[2])
    golem.say("启动 " + step.name + "：" + step.status)
  } else {
    golem.place("air", step.pos[0], step.pos[1], step.pos[2])
    golem.say("停机 " + step.name)
  }
}
golem.moveTo(lever[0], lever[2] + 2)
golem.say("全部待机，请织者把拉杆推到底")
```

运行后世界会看到：灰崽按计划逐格移动，启动的机器合闸位变成红石块、停机的合闸位变回空气；每处理一条动作说一句话；最后走到总拉杆旁等人来推。世界判定只看合闸位与事件顺序，所以执行层是唯一需要被世界看见的一段。

执行层里有三处细节与计划无关：站位偏移、`on` 与 `off` 的分支、最后走向总拉杆。前两处是对世界的必要知识，第三处是叙事上的收尾。真正由计划驱动的是「对哪一格、放什么、报什么」；执行层没有一条规则依赖机器名字。

按名字写死会是什么样？下面这段是错误示范。

```ts caption:[错误示例] 按名字写死，漏一台就少一台
const machines = world.vars.machines as { name: string }[]

for (const m of machines) {
  if (m.name === "熔炉组") {
    golem.place("redstone_block", -6, 65, -6)
  } else if (m.name === "红石门") {
    golem.place("redstone_block", 6, 65, -6)
  }
  // 警钟没有分支；换一批机器更无从下手
}
golem.say("启动完成")
```

运行后：熔炉组与红石门启动，警钟没有动作，日志却仍然说「启动完成」。这段代码的毛病不在写法，而在结构：它把「谁」写进了逻辑，于是新增机器必然漏。

这段代码与上面的通用版本只差一个决定：把「机器是谁」当成了分支条件。改起来并不难——把 if 链换成对 `Machine` 的调用，把坐标从数据里读出来。难的是意识到该这样做：看到「换一批就失败」时，先怀疑结构，再怀疑数据。

## 4 常见错误

### 错误一：以为 interface 就是继承
现象：不敢用接口，或者写了 `interface` 却非要再写一个类去「继承」它。原因：把接口理解成父子关系的声明。接口只是形状清单，任何形状对得上的对象都能用；本章的机器由对象字面量构造，根本没有类。改法：先写清单，再让数据通过构造函数变成清单形状；需要复用就组合，不需要类。

:::warn 常见误解：接口就是抽象类
有人把接口当成「只能被类继承的空类」，先想类再想接口。接口不需要类：对象字面量、函数返回的对象都能满足它，本章的机器就是纯对象。接口描述能力，类描述实现；需要一组共享实现时才考虑继承，需要一段共享流程时用函数。把两者分开，代码反而更小。
:::

### 错误二：启动函数里出现具体机器名
现象：换一台机器，启动函数就不工作；或者任务提示某台机器没反应。原因：函数按名字分支，把「谁」写进了「怎么做」。改法：函数参数类型写成 `Machine`，函数体只调用清单上的成员；所有差异留在数据里。判断标准很简单：函数体内搜不到机器名，才算通用。

### 错误三：把组合写成复制粘贴
现象：联动机能启动，但停机顺序不对，或者改一台机器的行为后联动机没跟着变。原因：`combine` 里把两台机器的动作单内容抄了一份，而不是调用它们的 `startSteps` 和 `stopSteps`。组合是「调用并拼接」，不是「抄写并保存」；前者跟随原机器的变化，后者是快照。改法：组合函数只做 `[...a.startSteps(), ...b.startSteps()]` 这样的调用与拼接。

### 错误四：启停顺序随手写
现象：收工时先停了熔炉组，警钟或联动机还在运行；或者过热机器没有被当场停。原因：停机顺序与启动顺序相同，依赖关系被倒着切断。改法：启动按清单顺序，过热当场补停；收工按反序停机。顺序本身是计划的一部分，别把它留给运气。

### 错误五：计划与执行混在一段里
现象：排计划的时候机器已经动了，想改顺序只能重跑；调试时说不清是计划错了还是执行错了。原因：在 `runAll`、`stopAll` 里直接调用移动与放置。改法：计划函数只返回 `Step[]`，执行层只消费 `Step[]`；两段各自可测、各自可读。

## 5 与关卡任务的关系

第 8 关的数据是 `world.vars.machines`（每台机器有 id、名字、合闸位、状态）与 `world.vars.lever`。启动一台机器，是在它的合闸位放红石块；停机，是在合闸位放回空气。四台机器指三台基础机器加一台联动机（熔炉组与警钟）。任务要求逐台启动、逐台汇报状态、过热当场停、收工按反序停机；最后总拉杆由玩家亲手推到底。

参考解的顺序是：先 `machineOf` 把数据变成机器，`combine` 造联动机，得到 `fleet`；`runAll` 生成启动计划（含过热补停），`stopAll` 生成反序停机计划；两段拼成 `plan`；顶层循环执行；最后走到总拉杆旁说一句「请织者把拉杆推到底」。玩家节拍、世界判定、代码执行各管一段，互不越界。

执行层的站位计算值得单独说一句。参考解没有站在合闸位本身，而是站在合闸位旁边：`standX` 与 `standZ` 根据合闸位做偏移。原因是机关格本身不能站人，也不该被踩；一个「照着计划执行」的通用执行器仍然要懂一点世界的物理规则。这也说明执行层并不是纯粹无脑：它保留了对位置与安全的最小知识，其余全部来自计划。

任务里还有一个细节值得对照：`status` 的类型是 `"正常" | "过热"` 的字面量联合，`Step` 的 `kind` 是 `"on" | "off"` 的可辨识联合。第 6 章的类型工具在这里直接派上用场：接口写形状，联合缩小取值，switch/if 按判别字段分路。到第 9 关，这些动作单会变成异步函数里的步骤；到第 10 关，同一张清单会交给两只织偶分头执行。

计划与执行分离在本关还有一个现实的收益：判定看的是世界事件（合闸位放没放红石块、顺序对不对），而计划是纯数组。出问题时，可以先打印计划、数一数条数、核对顺序，再决定是计划错了还是执行错了。如果一开始就把放置写在排计划的函数里，世界已经变了，你连「原本打算做什么」都看不到。

## 6 小结与练习

本章的要点可以收成五条。

1. 接口是一张能力清单：写形状、不写实现；结构化类型只看形状是否匹配。
2. 多态让同一段代码作用于所有满足清单的值；机器放进数组，循环里不出现具体名字。
3. 组合优于继承：把能力调用后拼接，而不是复制代码或建立父子关系。
4. 计划是纯数据，执行是副作用；分开写能让计划被检查、复用、重排。
5. 启停顺序有含义：启动按清单、过热当场停、收工反序停。

把这五条合起来看，本章在回答一个问题：怎样让代码不随着机器数量增长而膨胀？答案是把「机器的差异」压进数据，把「机器的共同点」写成接口，把「流程」写成可拼接的计划。机器从三台变四台、从四台变一批，代码的骨架不变。第 9 章会遇到另一种「量」的增长——等待的次数；第 10 章会遇到另一种「并行」——两个执行者。思路是同一个：把不变量写一次，把变量交给数据。

本章结束时，你手里有了一套比前几章更「工程化」的工具：先定义形状，再让数据实现形状，最后用组合把形状拼起来。它们不依赖任何游戏动作，只依赖语言本身。后面的异步与多执行者，一样可以用这套思路描述：一个异步函数有它的「能做什么」，两只织偶有它们的「消息接口」，清单写清楚，协调就有了基础。

练习题不计分，建议动笔。

1. 给 `Machine` 增加一个 `report(): string` 方法，让 `machineOf` 与 `combine` 都实现它；想一想联动机的汇报应该怎么写，才不丢两台机器的信息。
2. 把 `combine` 的 `stopSteps` 改成与 `startSteps` 相同的正序，推出收工时的动作顺序，判断它是否合理。
3. 用一句话说明「计划与执行分离」与第 7 章「把做法当值」之间的联系：计划是什么的值？执行又是什么？

## 术语

- 接口（interface）— 一组成员形状的声明，只写能力与签名，不写实现。
- 方法签名（method signature）— 方法的名字、参数与返回类型，不含方法体。
- 结构化类型（structural typing）— 只看形状是否匹配、不看是否显式声明实现的类型兼容规则。
- 多态（polymorphism）— 同一段代码可以作用于多种具体类型，本章靠「都满足同一张清单」实现。
- 组合（composition）— 把已有能力的调用结果拼装成新能力，而不是复制实现或建立继承关系。
- 继承（inheritance）— 子类获得父类能力并扩展；适合「确实是一种」的关系，本章的机器不使用。
- 计划（plan）— 描述「要做什么」的纯数据，例如由 `Step` 组成的数组。
- 执行（execution）— 按计划产生实际动作与副作用的阶段，例如循环调用移动与放置。
- 纯数据（plain data）— 只由基本值与记录、数组组成、不含行为副作用的值。
- 契约（contract）— 接口所代表的双向约定：调用方按签名调用，实现方按签名实现。
