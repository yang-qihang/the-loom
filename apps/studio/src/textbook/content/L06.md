# 账本上的记录：用类型给货物分类

> 从散装的值到记录、可辨识联合与 switch 穷尽性

## 0 本章要解决的问题

第 5 章结束时，你已经能把一段重复的步骤收进函数，用一个名字调用它。可世界交给你的数据换了一种麻烦：商队的混装货箱里有八件货，斧、镐、剑、粗铁、煤、蜜脾、面包、胡萝卜。每一件货都带着三个事实——编号、类别、是不是食物。编号决定它叫什么，类别决定它该进哪只桶，而「是不是食物」只在它是材料类货物的时候才有意义。

按第 2 章的办法，给每件货的每个事实各开一个变量，八件货就是二十四个变量。二十四个变量能跑，但没法写循环。循环以「一件货」为单位重复，而变量世界里没有「一件货」这个东西，只有二十四个彼此无关的名字。就算把名字起成 斧编号、斧类别、斧是食物，也只是把二十四行排得更整齐，机器仍然不知道它们属于同一件货。

本章要做的第一件事，是让「属于同一件货的几个事实」在语言里成为一个整体，再给这个整体起一个名字。第二件事，是用整体里的某一项把货分成互斥的几类，并且保证漏掉一类时程序当场出错，而不是悄悄把货放进错误的桶。做成这两件事，分拣八件货就只是一个循环加一个分类函数；做不成，就得手写八段几乎一样的代码，换一批货立刻失效。

有人会问：把三个事实当三个参数一起传给函数，不也行吗？单次调用行得通，但传参解决不了「存」的问题。清单里存着八件货，每件货都要被保存下来等待处理；参数只能表达「这次调用用哪三个值」，表达不了「清单里第 3 行是一条完整记录」。记录是数据结构，参数是调用方式，两者不在一个层面。分拣程序真正需要的，是一种能把「一条货」整体放进数组、传递、比较的东西，记录就是它。

## 1 直觉：一条账本行

商人的账本是一行一行的。一行写一件货，而不是把整页纸切成「所有编号」「所有类别」「所有食物」三栏。人这样记账，是因为一行是一条完整的事实：第三行写着「铁斧 / 工具 / 否」，你不必去别处找它的另外两栏。

程序里的记录（record）就是这一行：把一组有名字的字段（field）绑成一个值。字段有名字，所以你知道每个位置是什么；字段绑在一起，所以它们不会走散。对象字面量（object literal）是写出记录的方式：一对花括号里写若干「字段名: 值」，字段之间用逗号隔开。读字段用点号，`货物.kind` 读作「货物的 kind 字段」。

数组和记录的区别值得先说清。数组用序号区分元素，`第五件` 和 `第五件的类别` 是两个独立的值；记录用名字区分字段，一条记录同时装着编号、类别、食物三个事实。货物的清单是一个数组，数组的每个元素是一条记录，这样「第几件货」和「这件货的三个事实」就分了两层：外层按序号，内层按名字。

用一次小实验看清差别。假设要数一数工具类货物有几件。用散装变量，你得为八件货各写一遍「类别是不是 tool」的判断；用记录，只需在循环里读 `货.kind`，循环写一次。散装写法的问题不是行数多，而是「重复的结构没有名字」：每次重复都可能写错一个变量名，编译器也不会替你把同一件货的三个变量绑在一起。

记录还有一个容易忽视的好处：它可以成为函数的参数与返回值。`类别Of(货: 货物)` 只接收一条记录，返回一个类别名；函数内部不关心清单有多大、数据从哪来。如果把三个事实拆成三个参数，函数签名会变成 `类别Of(编号, 类别, 是食物)`，每次调用都要凑齐三个值，调用点一多就容易错位。记录把「一组一起进出的值」打包成一个参数，签名短了，错位的机会也少了。

下面是同一条信息的两种写法，左边是散装变量，右边是一条记录。

```ts caption:同一件货的两种存在方式
// 散装：三个值各自独立，谁都能改，谁都能混
const 编号 = "iron_axe"
const 类别 = "tool"
const 是食物 = false

// 记录：三个字段绑成一条，它们永远属于同一件货
const 货物 = { id: "iron_axe", kind: "tool", food: false }
golem.say(货物.id + " 属于 " + 货物.kind)
```

运行后世界会看到：灰崽说「iron_axe 属于 tool」。方块没有变化，`say` 只把一行字写进世界日志；散装写法里那三个变量则什么也没发生。

## 2 类型：给形状起名

记录解决了「绑在一起」，但还有一件反复出现的事：形状。八件货的记录都是同样的三个字段，写八遍形状就是八次重复，而且改动一处要改八处。类型别名（type alias）解决这个问题：用 `type` 给一个形状起名字，之后只用这个名字。

```ts caption:用 type 给货物形状起名
// 一件货有哪几个字段、各是什么类型，写一次就够
type 货物 = { id: string; kind: "tool" | "supply"; food?: boolean }

// world.vars 里的数据是只读的；as 只是告诉编译器「按这个形状读」
const 货物表 = world.vars.cargo as 货物[]
const 第一件 = 货物表[0]

golem.say("第一件：" + 第一件.id)
if (第一件.food === true) {
  golem.say(第一件.id + " 是吃的")
}
```

运行后：灰崽先报第一件货的编号；如果它是食物，再补一句「是吃的」。`货物表[0]` 拿到的是记录，`第一件.id` 和 `第一件.food` 是两条独立的字段读取。

先看必填字段。`id: string` 表示每条货物记录都必须有 id，值是字符串；`kind: "tool" | "supply"` 表示 kind 必须有，且只能取这两个字符串之一。这种只允许几个具体值的类型叫字面量类型（literal type）。如果写成 `kind: string`，编译器就只能保证「有 kind」，没法保证它只有两种取值，后面按 kind 分路时也就得不到帮助。字面量类型把约束写进了类型，让错误在更早的地方暴露。

再看可选属性（optional property）。`food?: boolean` 的问号表示这个字段可以有，也可以没有。读一个可能不存在的字段，结果是 `boolean | undefined`，所以判断要写 `第一件.food === true`，不要写 `if (第一件.food)`。在这份数据里两者恰好等价，但 `=== true` 明确表达「只有明确为真才算食物」，读者不必去猜 undefined 被当成什么。可选属性适合表达「大部分货没有、少数货才有」的信息；如果所有货都该有，就不要加问号。

类型别名还有一层作用，是让错误信息可读。两个形状相同的记录，一个叫「货物」，一个叫「工作」，编译器报错时会用你起的名字说「这里需要 工作，给的是 货物」。如果处处内联写花括号，报错就是一大串看不清的结构。起名不是为了省字，是为了让「这个值代表什么」写在代码里。

类型不是注释，但比注释严格：注释写错了没人管，类型写错了编译器会指出不匹配的地方。本章开头说「类型是说明书」，更准确的说法是：类型是写给编译器检查的说明书。它描述值可能取哪些形状，编译器负责在你违反描述时提醒。它不负责检查世界，世界由运行时决定，所以后面还要讲断言与兜底。

类型在运行时不存在。`type 货物 = ...` 这一行在代码真正执行之前就被抹掉了，世界里的记录仍然只是花括号和值。这一点叫类型擦除（type erasure），后面讲 `as` 时还会用到。现在只需记住：类型是写给编译器和你自己看的说明书，它约束不了世界，只约束你对世界的描述。

## 3 联合与判别字段

货的类别是互斥的：工具、材料、食物，一件货不可能同时属于两类。语言里表达「互斥的几种情况」用联合类型（union type）：`"工具" | "材料" | "食物"`，读作「三者之一」。联合可以出现在任何类型位置：可以是字符串字面量的联合，也可以是对象类型的联合。

对象类型的联合有一个反复出现的模式。让几种对象类型共享一个字段，这个字段在每个类型里取不同的字面量值，于是看这个字段的值就知道当前是哪一种类型。这个字段叫判别字段（discriminant），这样的联合叫可辨识联合（discriminated union）。第 6 关的数据里，`kind` 就是判别字段：`kind` 为 `"tool"` 时是工具，为 `"supply"` 时是材料类货物，材料类里再看 `food` 是否明确为真，分出食物。

要理解可辨识联合为什么有用，先看一个反例。假设不用 kind，改用「有没有某个字段」来猜类别：有 food 字段就是食物，否则看 id 里有没有 iron。这种判断依赖数据碰巧长什么样，数据一换就失效，而且编译器帮不了你。判别字段把「我是哪一类」写进了数据本身，判断不再靠猜。

在 `switch (货.kind)` 的某个 case 里，编译器会把 `货.kind` 的类型收窄（narrowing）成对应的字面量。进入 `case "tool"` 之后，`货.kind` 的类型就是 `"tool"`；进入 `case "supply"` 之后，就是 `"supply"`，并且仍然可以继续看 `货.food`。收窄让编译器在分支内部也知道「现在处理的是哪一类」，于是字段访问和返回值都能被检查。

switch 与 if/else if 可以互相改写，但两者适合的场合不同。条件是「同一字段等于某个值」的链式判断，switch 更整齐；条件是范围、组合或多个字段，if 更自由。本章需要 switch，不是因为它更强，而是因为它的清单形状让穷尽性一目了然：所有 case 列在一起，default 落在最后，漏没漏能一眼看出来。

分类一旦写成函数，就有了统一的入口。下面这个函数只做一件事：吃一条记录，吐一个中文类别名。

```ts caption:switch 按 kind 分类，default 兜底
type 类别 = "工具" | "材料" | "食物"
type 货物 = { id: string; kind: "tool" | "supply"; food?: boolean }

function 漏掉的类别(货的类别: never): never {
  throw new Error("账本里出现了没登记过的类别：" + String(货的类别))
}

function 类别Of(货: 货物): 类别 {
  switch (货.kind) {
    case "tool":
      return "工具"
    case "supply":
      if (货.food === true) {
        return "食物"
      }
      return "材料"
    default:
      return 漏掉的类别(货.kind)
  }
}

golem.say("铁斧是" + 类别Of({ id: "iron_axe", kind: "tool" }))
```

运行后世界会看到：日志里出现「铁斧是工具」。这段代码没有移动灰崽，也没有放方块，它只做了一次纯计算；这类「吃数据、吐结果」的函数是分拣程序的核心零件。

`switch` 语句（switch statement）按一个值跳到对应的分支。`case "tool":` 是「如果这个值等于 tool 就从这里往下走」，分支之间互斥；每个分支结束要 `return` 或 `break`，否则执行会滑进下一个 case。这和 `if / else if` 能表达同一件事，区别在形状：switch 把「按同一个值的不同取值分路」写成一张清单，清单的形状让后面的穷尽性检查有地方落脚。

## 4 穷尽性：漏掉一类必须当场失败

先做一个实验。把上面的函数删掉 `default`，另外造一种数据里还没出现过的类别。

```ts caption:[错误示例] 没有 default 的 switch 会漏掉新情况
type 类别 = "工具" | "材料" | "食物"
type 货物 = { id: string; kind: "tool" | "supply" | "gift"; food?: boolean }

function 类别Of(货: 货物): 类别 {
  switch (货.kind) {
    case "tool":
      return "工具"
    case "supply":
      return 货.food === true ? "食物" : "材料"
  }
  // 没有 default：gift 走到函数末尾，什么也没返回
}

const 结果 = 类别Of({ id: "ribbon", kind: "gift" })
golem.say("分类结果：" + 结果)
```

运行后：日志里是「分类结果：undefined」。函数声明了返回 `类别`，但走到底部时没有值可返回，运行时得到 undefined。undefined 被拼进日志还算走运；如果它被拿去当数组下标，程序会在更远的地方报错，而错误现场离真正的原因已经很远。

穷尽性（exhaustiveness）说的就是这件事：所有可能的情况都必须被处理。语言给了三种互相配合的做法。第一种，不用 default，靠返回类型让编译器检查「是否每条路径都 return」；它能在编译期提醒漏了分支，但挡不住数据在运行时出现类型没写到的新取值。第二种，default 里直接抛错；漏掉的情况会在运行时当场失败，错误现场就在函数里。第三种，default 里把剩下的值交给一个参数类型为 `never` 的函数：`never` 类型（never type）表示「不可能有值」，所以能传进 `never` 参数，说明联合已经被处理干净了；如果以后给 kind 增加一种取值，这个调用的类型就对不上，编译期就会报错。

上面的 `漏掉的类别` 用的是第三种。它比第二种更早：第二种只在运行时出事时才发现，第三种在写代码时就会提醒你「有新类别没处理」。参考解用的是同一种写法，只是函数名和报错文案不同。

把三种做法摆在一起比较，时机与代价各不相同。

- 不写 default：靠返回类型检查每条路径是否 return。优点是编译器会提醒漏分支；缺点是运行时数据出现类型之外的值时不会当场失败。
- default 直接抛错：运行时当场失败，错误现场清晰。缺点是只有真的运行到那一步才发现。
- default 交给 never 兜底：编译期就检查分支是否穷尽，运行时漏了也会抛错。它同时占了两头的好处，代价是要多写一个小小的兜底函数。

为什么 `never` 能证明穷尽？因为在 switch 的所有 case 都被列出之后，剩下能进入 default 的值类型是空集。空集没有值，所以「传给 never 参数」这次调用在类型上根本不该发生；它一旦被写出来且能被编译器接受，就说明没有剩余情况。反过来说，如果联合里新增一种取值，default 里传过去的类型就不再是 never，编译器立刻报错，提醒你补一个 case。穷尽性检查的本质，是把「漏没漏」从人的记忆变成类型系统的判断。

参考解用的是第三种。这个函数短到只有两行，但它是整个分类逻辑的安全阀：分类函数越长、类别越多，安全阀越值钱。

:::warn 常见误解：default 写了就安全
有人看到 switch 有 default，就认为分类不会漏。default 的作用只是接住剩下的值；如果 default 里写 `return "材料"`，那么漏掉的类别会被悄悄归进材料桶，程序不报错、桶也是满的，只是账错了。default 要么当场报错，要么交给 never 兜底，不要用它替未处理的情况编一个答案。
:::

## 5 类型擦除与 as：说明书不检查现实

`as` 是类型断言（type assertion）的写法：`world.vars.cargo as 货物[]` 的意思是「我保证这里读出来的东西是货物数组」。编译器接受这个保证，不再追查。运行时什么也没发生；如果保证是错的——比如把 boxes 断言成货物数组——读字段时会得到 undefined，而报错会出现在使用 undefined 的那一行，不在断言那一行。

为什么需要 as？因为 `world.vars` 的类型是「任意只读数据」，编译器不知道货物数组长什么样。真实形状由关卡数据决定，类型系统只能靠你的断言接上。这也解释了为什么第 2 章讲「读世界、不背数据」：数据是运行时的事实，类型是你对事实的描述，两者要能对上，程序才有意义。

断言不是免检通道，只是把检查的责任从编译器挪到你身上。两个习惯能减少风险。第一，断言写完立刻用一次，早点让错误暴露：拿到 `货物表` 就立刻读 `货物表[0].id`，别拖到一百行之后。第二，对数据形状的假设集中在少数几行，最好紧挨着 `world.vars` 读取——这样换了一关的数据，只需检查那几行。

还有一个便宜的自检办法：把断言后的第一条记录用日志打出来。`golem.say(JSON.stringify(货物表[0]))` 会把整条记录摊成一串字符，字段名和值对不对一眼可见。日志不能替代类型检查，但它能证明「我以为的形状」和「世界给的形状」确实一致。调试断言时先看日志，比在报错行附近猜要快。

## 6 读参考解：账本、分类与分拣

第 6 关的参考解可以拆成四个阶段：建模、分类、放货、配工具。前两个阶段就是本章讲的记录和 switch；后两个阶段用前两章的函数和循环把决定变成动作。

第一阶段是清点。参考解先用 `类别Of` 把八件货数一遍，工具几件、杂货几件，再用 `say` 报出来。这一步不改变世界，只是让「账」先对上。为什么值得单独做？因为如果分类规则写错，计数会先暴露问题，比放错桶之后再回头查便宜得多。

第二阶段是分拣。循环里每件货做三件事：算出类别、从账本取下一格、走到货箱边再走向目标格、放下货物。注意这里有一处刻意的绕路：`moveTo(9, 3)` 出现在循环里，每次都要先回主路再走向目标格。绕路不是笔误，是因为营地的通道是固定的，两点之间不能直走；程序按书写顺序走格子，不会自己找路。

第三阶段是配工具。三个工作点在 `world.vars.jobs` 里，每个工作点要的工具是 `needs`，位置是 `station`。参考解用一个 `while` 循环扫描清单，把工具放到工作点上。这里再次用到记录：工作点也是一条条记录，字段名让循环体读起来像一句人话。

第四阶段是对账。灰崽走回塔卡身边说一句「账清了」。这句话不改变世界，但它是任务叙事的一部分；世界判定只看桶与工作点，玩家的最后一步是亲手插织线。代码说对了话不代表任务完成，桶对了才算。

放货的关键是一个「账本」记录。三只桶各有一排格子，每只桶还有「下一个空格子」的下标和「已放几件」的计数。把这三件事绑成一条记录，再用 `Record` 把它们按类别存成一张表，就可以只写一个函数处理所有桶。

```ts caption:记录层面的桶账：一只桶一条记录
type 类别 = "工具" | "材料" | "食物"
type 木桶 = { tools: number[][]; materials: number[][]; food: number[][] }
type 桶账 = { 名字: string; 格子: number[][]; 下一个: number; 已放: number }

const 木桶 = world.vars.boxes as 木桶
const 账本: Record<类别, 桶账> = {
  工具: { 名字: "工具桶", 格子: 木桶.tools, 下一个: 0, 已放: 0 },
  材料: { 名字: "材料桶", 格子: 木桶.materials, 下一个: 0, 已放: 0 },
  食物: { 名字: "食物桶", 格子: 木桶.food, 下一个: 0, 已放: 0 },
}

function 下一格(类别: 类别): [number, number, number] {
  const 桶 = 账本[类别]
  const 格 = 桶.格子[桶.下一个]
  桶.下一个 = 桶.下一个 + 1
  return [格[0], 格[1], 格[2]]
}

const 格 = 下一格("工具")
golem.say("工具桶的下一格是 " + 格[0] + "," + 格[1] + "," + 格[2])
```

运行后：日志报出工具桶第一格的三个坐标。每调用一次 `下一格`，对应桶的「下一个」加一；记录在这里是可变对象，字段可以被重新赋值。这一段没有移动灰崽，只是把「该放哪一格」算出来。

放货函数只做记录层面的决定，移动和摆放留在顶层循环里。原因是本幕的运行方式：织偶的移动、放置、说话会被自动补上等待，而自动补等待只改写顶层语句，不改写函数体里藏着的调用。所以参考解把函数写成「排动作单」——返回坐标与物品编号，顶层循环再真的让灰崽去走、去放。这是一个很实用的分界线：函数决定「做什么」，顶层决定「现在做」。

```ts caption:[读参考解] 顶层循环把决定变成动作
const 货物表 = world.vars.cargo as 货物[]
const 工作台 = world.vars.jobs as { id: string; needs: string; station: [number, number, number] }[]

for (const 货 of 货物表) {
  const 分 = 类别Of(货)
  const 格 = 下一格(分)
  golem.moveTo(9, 3)
  golem.moveTo(格[0], 格[2] + 2)
  golem.place(货.id, 格[0], 格[1], 格[2])
}
golem.say("八件货都进桶了。")

let 序号 = 0
while (序号 < 工作台.length) {
  const 工 = 工作台[序号]
  golem.moveTo(18, 3)
  golem.moveTo(工.station[0] - 2, 工.station[2])
  golem.place(工.needs, 工.station[0], 工.station[1], 工.station[2])
  序号 = 序号 + 1
}
golem.moveTo(trader)
golem.say("账清了，塔卡。")
```

运行后世界会看到：八件货依次落进三只桶的格子里，工具桶装斧、镐、剑，材料桶装粗铁、煤、蜜脾，食物桶装面包、胡萝卜；三个工作点各放上对应的工具；最后灰崽走到旅商塔卡身边说账清了。世界判定只看桶里和工作点上的方块，不看灰崽说的话。

这段代码里有一处值得回看：`类别Of(货)` 和 `下一格(分)` 分两次调用，一次为了分类、一次为了取格子。账本让「下一格」不必写三次循环，`while` 让「给每个工作点配工具」不必写三段重复代码。记录、联合、switch、循环、函数在这里各管一段，没有哪一段在替另一段做决定。

## 7 常见错误

### 错误一：字段散着传，对不上号
现象：程序能跑，但某件货被放进错误的桶，或者日志里的编号和类别不是同一件货。原因：没有用记录把事实绑在一起，而是用两个平行数组分别存编号和类别，循环时下标对错了位置。改法：一条货一条记录，循环变量就是整条记录；需要拿出字段时用点号，不要用「第几个数组的第几个元素」去对。

### 错误二：把「食物」当成第三种 kind
现象：分类逻辑越写越长，食物判断散落在各处，换一批数据就出错。原因：把两个不同层级的判断放进了同一个字段。kind 是货物的大类，食物是材料类货物里的一个特例；把食物硬塞进 kind，判别字段的取值就失去了互斥性，后面所有分支都要重写。改法：先按 kind 分路，再在 supply 分支里看 food，层级不要压平。

### 错误三：switch 漏了兜底，函数返回 undefined
现象：日志里出现 undefined，或者报错停在与分类无关的行。原因：switch 没有 default，新增的类别走到函数末尾没有返回值。改法：加上 default，里面调用参数类型为 never 的兜底函数当场抛错；不要用 default 给未处理的情况编一个默认答案。

### 错误四：以为 as 会检查数据
现象：断言写错形状，读字段得到 undefined，报错指向很远的行。原因：类型断言只是编译期的承诺，运行时被完全擦掉，数据不对不会在断言处报错。改法：断言紧挨着读取写，拿到后立刻用一次；类型写错时，先检查数据形状，而不是在报错行附近加更多断言。

### 错误五：账本没有边界检查
现象：某只桶只有八个格子，货超过八件时程序运行到中途报错，或者把货放到桶外的坐标上。原因：账本只递增下标，没有检查「下一个」是否还在格子数组里。改法：取格子之前检查 `桶.下一个 >= 桶.格子.length`，超过就抛出写明桶名的错误。分类保证货物进对了桶，边界检查保证桶装得下；这两件事都不是世界替你做的。

## 8 与关卡任务的关系

第 6 关的任务是：把混装货箱的八件货分进工具、材料、食物三只桶，再给三个工作点配好工具，最后回塔卡身边对账。世界给你 `world.vars.cargo`（货物清单）、`world.vars.boxes`（三只桶的格子）、`world.vars.jobs`（工作点的需求与位置）；判定只看桶里和工作点上放了什么，不看你的日志写得多漂亮。参考解的做法正好覆盖本章全部要点：记录建模、可辨识联合分类、switch 穷尽兜底、账本记录、循环分拣。

任务里的最后一步是玩家节拍：对完账，由你亲手把织线插进护符盒。代码不负责这一步，也替不了活人的手；代码负责的是把桶和工作点摆对，让世界判定通过。分清「代码负责的」和「玩家负责的」，和分清「函数决定的」与「顶层执行的」是同一种能力。任务面板上的每一条目标都对应世界里的一组方块；代码写得再优雅，桶里没放对就是没完成。反过来，只要桶对了，日志说得朴素也能过关。

## 9 小结与练习

本章的要点可以收成五条。

1. 记录把相关的几个事实绑成一个值，字段用名字读，不靠位置记。
2. 类型别名给记录形状起名；必填字段保证存在，可选属性表达「可能有」。
3. 字面量类型缩小取值范围，联合类型表达互斥；共享判别字段的联合叫可辨识联合。
4. switch 按判别字段分路，穷尽性要求所有情况都被处理：default 要么报错，要么交给 never 兜底。
5. 类型会被擦除，`as` 只是承诺；错误分类要在运行时当场失败，而不是悄悄归入某一类。

练习题不计分，建议动笔。

1. 给 `货物` 增加一个 `重量: number` 必填字段，再写一个函数 `重的货(货: 货物): boolean`，返回重量是否大于十；想一想这个函数应该放在分类前还是分类后。
2. 把 `类别Of` 的 default 改成 `return "材料"`，再让数据里出现一种没登记的类别，预测程序会发生什么；然后把 default 改回 never 兜底，比较两种做法发现问题的时机。
3. 用记录描述「一只桶的账」，把「名字、格子、下一个、已放」四个字段写出来，再写一个函数返回这只桶还能放几件。

延伸一句：类型别名、联合、判别字段、穷尽性这套东西并非教学游戏专有。真实 TypeScript 里到处是可辨识联合：网络请求的「加载中 / 成功 / 失败」三种状态、界面事件的几种形状、编译器的语法树节点。它们都有同一个模式：一个字段说明当前是哪一种，switch 分路，default 用 never 兜底。你在这里学到的不是一条本关规则，而是一种组织互斥数据的通用写法。

## 术语

- 记录（record）— 把若干具名字段绑成一个值，用点号按名字读字段。
- 字段（field）— 记录里的一个具名条目，例如 `货物.kind` 里的 kind。
- 对象字面量（object literal）— 用花括号和「名: 值」列表写出记录的方式；示例：`{ id: "coal", kind: "supply" }`
- 类型别名（type alias）— 用 `type` 给一个类型或形状起名字，运行前被擦除。
- 可选属性（optional property）— 字段名后加问号，表示该字段可能不存在；读出的类型要带上 undefined。
- 字面量类型（literal type）— 只允许几个具体取值的类型，例如 `"tool" | "supply"`。
- 联合类型（union type）— 用竖线连接若干类型，表示「是其中之一」。
- 可辨识联合（discriminated union）— 共享一个判别字段、该字段取不同字面量值的对象类型联合。
- 判别字段（discriminant）— 可辨识联合里用来区分当前是哪一种的字段，例如 kind。
- 类型擦除（type erasure）— 类型信息在代码执行前被删除，运行时只剩值本身。
- 穷尽性（exhaustiveness）— 所有可能的情况都被处理；漏掉一类要在编译期或运行期明确失败。
- never 类型（never type）— 表示不可能有值的类型；把剩余值传给 never 参数，能证明分支已经穷尽。
