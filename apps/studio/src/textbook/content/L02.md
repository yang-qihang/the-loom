# 会数数的织偶：用变量记住会变的值

> 从「灰崽没有记性」出发，理解变量、绑定与赋值

## 0 本章要解决的问题

麦穗节前，鸡舍攒了 6 枚蛋，要在天亮前全部收进谷仓门口的木桶。灰崽愿意干活：它会走、会收蛋、会倒蛋。问题在于它没有记性——收了几枚、倒了几枚、还剩几枚，它每一次行动结束就忘得干干净净。小筐一趟只装得下 4 枚，所以得分两趟：第一趟收 4 枚倒进木桶，第二趟收剩下的 2 枚再倒一次，最后回到艾拉身边，报出木桶里的数量。

如果不用变量，这段程序会写成什么样？第一趟固定收 4 枚，倒蛋时就写死 4；第二趟固定收 2 枚，就写死 2；报数时写死 6。程序在这一次能跑通，但数字全是写死的。换一间鸡舍、换一批蛋、或者明年蛋的数量变化，程序里的 4、2、6 就全错了。更麻烦的是中间过程：倒蛋的时候，程序怎么知道筐里现在有几枚？如果小筐一次只能装 4 枚，第二趟到底该收几枚？这些问题不是靠再写死一个数字能解决的，它们要求程序在运行过程中记住中间结果。

本章要解决的问题就是：程序怎样记住一个会变化的数，并在后面继续使用它。答案听起来很简单：给这个数起一个名字，把名字和值绑定（binding）起来，需要时用名字读取，改变时用名字写回。这个「名字」就是变量（variable）。

但「起个名字」这四个字背后有一整套需要精确理解的机制。名字在什么时候生效？值什么时候被读出来？`let` 和 `const` 有什么区别？为什么 `x = x + 1` 在数学里不成立、在程序里却成立？把这两处问题分开，本章的目标就清楚了：读完之后，你应当能对着一段记账代码，逐行说出「这个名字现在绑定什么值、下一步会变成什么值」，而不是凭感觉猜测。

先看一个具体的困境。下面这段程序的第一趟没有使用变量，倒蛋的数量是写死的。

```ts caption:[错误示例] 数字写死，换一批蛋就错
golem.moveTo(perch1)
golem.collect("egg", perch1)
golem.collect("egg", perch2)
golem.collect("egg", perch3)
golem.collect("egg", perch4)
golem.moveTo(barrel)
golem.deposit("egg", barrel, 4)
```

运行后世界会看到：第一趟的 4 枚蛋确实进了木桶。但这段程序有两个问题：它没有先走到每个蛋窝旁边，因为 `collect` 需要灰崽在可操作的距离内；倒蛋的 4 是写死的，如果这一趟只收到 3 枚，程序仍然会尝试倒 4 枚。第二个问题不是「数字抄错」，而是「程序没有地方记录真实数量」。变量要解决的正是这一类问题。

## 1 直觉：名字比数字多出了什么

先把变量理解成记账本上的一行。假设你站在鸡舍里，手边有一本小册子。每收一枚蛋，你在「已收」这一行把数字划掉，写上新数字；每倒一趟，你在「已倒」这一行加上这一趟的数量；最后报数时，你翻到「木桶」那一行读取结果。小册子的行有名字（已收、已倒、木桶），行里写着数字，数字会随着你做的事情变化。程序里的变量就是这本地册子。

名字与数字的区别，在「会变」这件事上体现得最清楚。数字 4 就是 4，写完就固定了；名字 `carried` 背后的数字可以是 0、1、2、3、4，程序运行到不同的位置，读到的值不同。你可以对名字做三种操作：写入一个值（赋值）、读出它当前的值（使用）、在计算之后把新值写回去（更新）。这三种操作合起来，就是「记账」的全部。

为什么不能一直用数字？有三个原因。第一，数字不能表达过程。任务要求「分两趟、每趟不超过 4 枚」，真实的一趟收了几枚，取决于你实际收了多少，写死的数字只是猜测。第二，数字无法通用。同一段程序要在第二间鸡舍里跑，窝的数量和位置换了，但「收一枚就加一」的规则没变；用变量写的规则可以原样复用，用数字写死的程序每换一次环境就要重写。第三，数字无法被检查。程序报出「6」这个数时，你无法判断它是真的数了 6 枚，还是背下了 6 这个字；用「从木桶里现数」的表达式报数，才能保证数字和世界一致。

还可以换一个角度理解：程序运行的时候，世界在变，程序自己也需要一个「小世界」来记住中间状态。这个世界里的东西不显示在屏幕上，只存在于运行过程里，变量就是程序员给这些小状态起的名字。名字起得好，读代码的人能顺着名字看到计算意图；名字起得差，读到 `a = b + c` 只能重新推导一遍。

变量不等于「盒子」。很多教材说变量像一个盒子，往里放值。这个比喻在初学时方便，但它会带来一个误解：以为「变量里存着值本身」，以为赋值是把值搬来搬去。更准确的说法是：变量是一个名字，名字绑定（binding）到一个值；赋值不是往盒子里塞东西，而是让这个名字改绑到另一个值。区别在哪里？区别在 `let banked = carried` 这一行：它不是把 carried 的存储空间借给 banked，而是读出 carried 当前的值，把这个值绑定到新名字 banked 上。之后修改其中一个名字，另一个名字不受影响。本章后面会专门验证这一点。

:::aside 为什么第一门语言课总从「记忆」开始
计算机的存储模型通常被概括为「存储程序」：机器里有可以编号的存储单元，程序和数据都放在里面，计算就是不断读取、修改这些单元的内容。变量是这套模型在语言层面的入口。先理解「名字绑定值、值可以变」，后面学习数组、记录、对象、闭包时，才不会把它们当成魔法——它们本质上都是「用某种方式组织存储单元」的语法。
:::

## 2 定义与机制

### 2.1 声明、初始化与赋值

变量的使用分三步。第一步是声明（declaration）：告诉程序「我要用这个名字」。第二步是初始化（initialization）：在声明的同时给它一个初始值。第三步是赋值（assignment）：把名字重新绑定到一个新值。三步可以分开写，也可以合并。

`let carried = 0` 这一行把声明和初始化写在了一起。拆开来看：`let` 是关键字，表示「声明一个可以改绑的名字」；`carried` 是变量名；`= 0` 是初始化，把名字绑定到数字 0。这一行的含义不是「carried 等于 0」，而是「从这一行起，名字 carried 指向 0 这个值」。

赋值 `carried = carried + 1` 看起来最像数学，含义却最不像数学。执行的顺序是：先读右边，此时 carried 绑定的是旧值；算出旧值加一的结果；再把结果绑定回 carried。所以 carried 从 0 变成 1。数学里 `x = x + 1` 是一个无解的等式，程序里它是一条最常见的「自增」操作。两者形式相同、语义完全不同，这是初学阶段最容易混淆的地方。

为什么要有「先右后左」？因为程序需要一个明确的求值顺序（evaluation order）。如果先看左边，左边此刻还没有新值可写；先读右边，才能拿到计算所需的材料。语言的规则是「先求值右边，再把结果赋给左边」，这条规则在所有主流语言里都一样。记住它，你就能自己推导出 `carried = carried + 1` 在每一步之后的值。

下面用一个三行的片段演示这个过程。假设 carried 初始值是 0。

```ts caption:[照抄] 赋值不是等式：逐步读出值
let carried = 0
carried = carried + 1
carried = carried + 1
```

运行后日志与内部状态会看到：第一行结束后 carried 是 0；第二行先读 0、算 1、写回，carried 变成 1；第三行先读 1、算 2、写回，carried 变成 2。如果把第三行改成 `carried = carried + 10`，carried 就是 11，而不是 12——每一步只做右边写的那一次计算。

### 2.2 常量：值不变的名字

有些数字在一次运行里不应当改变。比如「小筐一趟最多装 4 枚」「一共要收 6 枚」：这两个数是任务给定的约束，程序里到处用到，却不应该被某一行代码改掉。给这种值起名字用 `const`。

`const eggsPerTrip = 4` 声明了一个常量（constant）：名字与 4 绑定之后，程序不能再用赋值把它改绑到别的值。如果写 `eggsPerTrip = 5`，运行时会报错，提示不能给常量赋值。这个限制是保护：它让「4 就是 4」这件事由语言来保证，读代码的人看到 `eggsPerTrip` 就知道它的值从头到尾没有变过。

`const` 与 `let` 的选择有明确标准：这个值在程序运行过程中需要改绑吗？需要，用 `let`；不需要，用 `const`。经验上，大多数变量从头到尾不改变，很多语言因此鼓励默认用 `const`。在本章的程序里，`eggsPerTrip`、`need` 用 `const`，`carried`、`banked` 用 `let`。选择的关键字本身就在向读代码的人传递信息：看到 `const`，你可以把它当固定参数；看到 `let`，你要留意它在哪几行被改。

需要澄清一个常见误会：`const` 不是「值永远不会被计算出来」，而是「名字不会再改绑」。`const remaining = need - banked` 只在声明时计算一次，结果绑定到 remaining；之后 remaining 不能改，但它绑定的值可以是运行时才确定的结果。换句话说，`const` 约束的是名字，不是表达式的来源。

为什么需要可变的变量？因为有些计算必须边算边改：每收一枚蛋，数量加一；每倒一趟，累计更新。用 `const` 也能写出同样效果吗？可以，但要把每一步的结果起一个新名字（`carried1`、`carried2`……），名字会越堆越多，读代码的人还得逐一对照。`let` 允许一个名字承载「随时间变化的过程」，代价是读代码时必须跟踪它的当前值。这个代价换来的是简洁，选择的关键在于：这个量是否真的以「逐步更新」的方式参与计算，还是可以由已确定的输入一次算出。前者用 `let`，后者用 `const` 加表达式。

### 2.3 基本类型：数字、字符串，以及类型不匹配

变量绑定的值有类型（type）。本章接触两种：数字（number）与字符串（string）。数字可以参与加减，字符串是文字，用双引号或反引号包起来。`carried` 是数字，`"egg"` 是字符串，`"木桶里有 6 枚蛋"` 也是字符串。

类型不匹配时，语言不一定报错，而是按自己的规则「凑合」出一个结果。最典型的是 `"4" + 1`：引号让 4 变成了文字，文字加数字时，语言选择把数字也变成文字再拼接，结果是字符串 `"41"`，不是数字 5。这类错误很隐蔽：程序能运行，结果却没有意义。写代码时要有意识地区分：这个值是拿来算的，还是拿来显示的？拿来算的用数字，拿来显示和比较的用字符串。

本章还会用到一种方便的写法：模板字符串（template string）。用反引号包住一整句话，在 `${}` 里放变量或表达式，运行时会先算出表达式的值，再把它嵌进句子。`golem.say(\`木桶里有 ${inBarrel} 枚蛋\`)` 会把 inBarrel 当前的值填进句子。模板字符串的价值在于把「数字」和「围绕数字的文字」放在一个句子里，读起来像人话，也不必用一堆加号拼接。

### 2.4 从哪里读数字：背包、木桶与变量

变量只能记住程序自己算出来的值，不能替代世界本身。蛋的实际数量存在两个地方：灰崽的背包（本次运行收进来多少）和木桶（容器里已经有多少）。要读背包，用 `golem.count("egg")`；要读木桶，用 `world.container(barrel).count("egg")`。这两个数字来源不同，用途也不同。

这个区分很重要，因为「记住」与「现查」是两种策略。变量适合记住「我这一趟收了几枚」这类程序内部的计算结果；容器计数适合确认「木桶里到底有几枚」这类世界事实。报数时必须现查木桶，不能拿程序里记住的数字冒充：程序记的数字可能是旧的、错的，而世界里的容器计数是评分判定的事实来源。后面的关卡会反复出现这个规则：世界是唯一的真相，程序里的变量只是辅助记忆。

:::warn 常见误解：把 `=` 当成「等于」
数学里的 `=` 表示两边相等，程序里的 `=` 表示「把右边的结果绑定给左边」。`carried = carried + 1` 不是在说「carried 等于 carried 加一」（这句话在数学上不可能成立），而是在说「读出 carried，加一，写回去」。读代码时把 `=` 读成「变成」，把右边的计算读成「先算」，混淆就会少很多。判断两个值是否相等是另一类操作，第 3 章讲分支时会正式介绍。
:::

## 3 语法与示例

### 3.1 `let` 专讲：会改绑的名字

`let` 是本章最重要的关键字，值得单独拆开讲清楚。它的作用是声明一个可以改绑的变量：`let 名字 = 初始值`。名字由你起，必须是合法的标识符——只能用英文字母、数字、下划线、美元符号，不能以数字开头，也不能用语言保留的关键字（比如 `let`、`const`、`if` 本身）。名字区分大小写，`carried` 和 `Carried` 是两个不同的名字。

`let` 的第一层含义是「现在开始有这个名字」。声明之前，这个名字在程序里不存在；在声明之前使用它会报错。这不是语言的刁难，而是为了保证顺序执行的可预测性：名字从声明那一行起才有效，读到声明之前，没有人能说清它绑定什么。初学者常见的错误是把更新语句写在声明之前，程序直接报「未定义」。

「声明之前不可用」这条规则与作用域有关。`let` 声明的名字从声明那一行开始生效，直到它所在代码块的结尾。本章的程序只有一个顶层代码块，所以名字在整段程序里可见；如果把几条语句用花括号包起来，在花括号里用 `let` 声明的名字只在那一段里可见，出了花括号就消失。这个规则叫块级作用域，现代语言大多如此。更早的语言用 `var` 声明变量，`var` 会忽略代码块、把名字提升到整个函数，容易造成「名字在别处也能用」的混乱；本课程不使用 `var`，需要可改绑的变量时一律写 `let`。

`let` 的第二层含义是「这个名字可以改绑」。改绑用赋值语句 `名字 = 新值`。注意赋值语句的左边只能是一个可以改绑的名字，不能是表达式：`carried + 1 = 4` 在语法上就不合法，因为 `+` 的结果不是一个存储位置。语言区分「能放值的地方」和「只能读出的值」，这个区分会在后面用到（比如函数的参数是只读的，返回值可以直接使用）。

`let` 的第三层含义是「声明可以是局部的」。这一章的程序只有顶层，名字在整个程序里都有效；等到第 5 章写函数、或者用花括号把一段代码包起来时，在代码块内部声明的名字只在那一段里有效。这个性质叫作用域（scope），本章先建立一个直觉：名字有它的活动范围，超出范围就看不见。作用域的意义是避免名字互相干扰——函数里的临时变量不会污染外面的世界。

`let` 声明的变量如果没有初始化，会得到一个特殊值 `undefined`，表示「还没有绑定任何有效值」。`undefined` 参与数字运算会得到 `NaN`（Not a Number，表示「不是一个数」），之后的所有计算都会带着这个坏值往下跑，直到某处报错或者产出一个荒谬的结果。新手看到 `NaN` 往往以为是自己算错了，实际上是某一步读到了未初始化的变量。所以凡是会参与计算的 `let`，声明时最好立刻给初始值 0，这既是习惯，也是自查手段。

`let` 与 `const` 的差别只在「可不可以改绑」这一件事。`const` 声明时必须初始化，之后不能赋值；`let` 可以声明后再赋值，也可以反复赋值。两者都不能重复声明同名变量：同一作用域里写两次 `let carried` 是语法错误。为什么不允许重复声明？因为重复声明会让「这个名字到底指哪个值」变得含糊，语言选择直接禁止，而不去猜你的意图。

`let` 与数学变量还有一个深层区别，值得专门说清楚。数学里的变量通常表示一个固定的未知量：在一个方程里，x 从始至终指同一个数。程序里的变量是「随时间变化的存储位置」：同一行代码 `carried = carried + 1` 被执行四次，carried 就经历了四次不同的值。程序的行为不仅取决于「写了哪些式子」，还取决于「以什么顺序执行」。这也是为什么顺序执行要先学：变量的值，是执行顺序的产物。

下面用一张记账跟踪表（trace）把两趟搬运的状态写出来。假设第一趟收 4 枚、第二趟收 2 枚，总需求 6 枚。表中每一行是程序执行到某个位置时的变量状态，读表时注意三点：声明何时发生、每次赋值读的是哪个旧值、哪个变量在什么时候归零。

1. 执行前：carried 未声明，banked 未声明，木桶里 0 枚蛋。
2. `let carried = 0` 之后：carried = 0；banked 仍未声明。
3. 每收一枚蛋并执行 `carried = carried + 1` 之后：carried 依次变成 1、2、3、4。
4. `golem.deposit("egg", barrel, carried)` 之后：木桶里 4 枚蛋，carried 仍是 4。
5. `let banked = carried` 之后：banked = 4，carried 仍是 4。注意这是「读出 carried 的值，绑定给 banked」，两个名字各自绑定 4，而不是共享同一个值。
6. `carried = 0` 之后：carried = 0，banked 仍是 4。
7. 第二趟每收一枚并自增之后：carried 依次变成 1、2。
8. `const remaining = need - banked` 之后：remaining = 6 - 4 = 2，carried 仍是 2。
9. `golem.deposit("egg", barrel, remaining)` 之后：木桶里 4 + 2 = 6 枚蛋。
10. `banked = banked + remaining` 之后：banked = 6，与木桶里的实际数量一致。

再看一个更小的跟踪，专门验证「赋值不是等式」与「两个名字各自绑定」。下面三行程序的执行结果，可以逐步写出。

```ts caption:[照抄] 两个名字各自绑定：修改一个不影响另一个
let carried = 4
let banked = carried
carried = 1
```

1. `let carried = 4` 之后：carried = 4。
2. `let banked = carried` 之后：banked = 4，carried 仍是 4；这是读出值再绑定，不是把名字借给另一个名字。
3. `carried = 1` 之后：carried = 1，banked 仍为 4。
4. 结论：两个名字各自绑定自己的值，修改一个不影响另一个。

这个跟踪很小，却澄清了两个常见误会：赋值不是数学等式；`let banked = carried` 不是共享，而是复制一份值。

这张表值得反复读。它精确回答了三个问题：为什么第一趟倒蛋可以写 `carried` 而不是写 4（因为 carried 此刻就是 4）；为什么 `let banked = carried` 之后要把 carried 归零（因为第二趟重新开始记账）；为什么第二趟倒蛋写的是 remaining 而不是 carried（因为此刻 carried 只记了第二趟收的 2 枚，而这一趟要倒的也是 2 枚——这里两者恰好相等，但语义不同：remaining 是「还差多少」，carried 是「这一趟收了多少」）。变量名承载语义，读代码的人靠名字区分这两种数量。

`let` 的命名也值得花几句。变量名是写给人看的注释，最好用能读出意义的英文或约定俗成的简称：`carried`（这一趟收了几枚）、`banked`（已经倒进桶里几枚）、`remaining`（还差几枚）。这些名字读起来像一句话，程序意图就清楚了。反过来，`a`、`b`、`c`、`n1`、`n2` 或者拼音缩写 `ys`、`yd` 会让读代码的人重新推导每一行的含义，维护成本立刻上升。名字还应当避免和命名点重名：关卡已经用了 `perch1`、`barrel` 这些名字指位置，自己再声明一个同名的 `let barrel` 会覆盖位置名字，引发难以察觉的错误。

`let` 之后的值也不是永远只能加一。加减乘除都可以写进赋值：`carried = carried - 1` 表示少一件，`total = total + 4` 表示累计加四，`remaining = need - banked` 表示剩余量。只要保持「右边先算、左边后写」的顺序，你就可以自由组合这些运算。注意不要把「自增」和「比较」混在一起：本章还没有比较运算，所有 `=` 都是赋值。

`let` 的最后一个要点是：它不是「声明一次就拥有记忆」的魔法，变量只在一次运行中存在。每次点击运行，程序重新开始，`let carried = 0` 重新执行，变量重新绑定 0。世界里的方块和容器会保留（除非重置关卡），但程序内部的变量不会跨运行保留。理解这一点，就不会指望「上一次运行记住的数」这一次还在——程序要重新读世界，重新计算。

写 `let` 有三个可以立刻用上的习惯。第一是就近声明：名字在第一次使用之前不远处声明，读代码的人不必向上翻很远去找它的来历。第二是立刻初始化：会参与计算的名字在声明时给初值，避免 `undefined` 顺着一串计算扩散成 `NaN`。第三是别过早声明：如果一个名字只在一个小段里用，就把声明放在那一小段前面，用完即止；提前一屏声明一堆变量，读者会分不清哪些已经用过、哪些还在等。三个习惯都不需要额外工具，写的时候多停一秒就能做到。

还有一个与 `let` 关系密切的用法：把世界里的读数存进变量。`let carried = golem.count("egg")` 之后，carried 绑定的是本次读取得到的数字；之后再读世界，carried 不会自动更新，需要重新赋值。这个特点常被误解成「变量会跟着世界变」——不会。变量是程序的小本子，抄下来的数字只在抄的那一刻准确；想知道最新情况，就再读一次。把「读数」与「记住」分开写，程序的行为才可预测。

选择 `let` 还是 `const`，在报数这个场景里有一个具体判断。木桶里的数量是每次现读的，读一次之后在本段程序里不再变化，用 `const inBarrel = world.container(barrel).count("egg")` 就够；而 `carried` 会随着每一枚蛋改变，必须用 `let`。同一段程序里两种声明并存，不是风格不一致，而是两种数据的生命周期不同：看到 `const`，读者知道它不会变；看到 `let`，读者知道要跟踪它的更新。这个区分让代码的「可读性」不再依赖注释，而是由声明本身表达出来。

如果只记住一句话，请记住：`let` 后面跟的是一个会变的名字，`=` 后面是它此刻的值，之后的语句负责改它。读一段带 `let` 的代码时，按「声明在哪儿、哪几行改过它、此刻值是多少」三个问题走一遍，跟踪表就自然写出来了；写一段带 `let` 的代码时，按同样的三个问题自查一遍，漏改、多改、改错变量都能提前发现。

### 3.2 第一趟：从零开始记账

把上面讲的机制落到第一趟收蛋上。声明四个常量和变量，每收一枚就自增一次。注意每收一枚蛋要两行：先走，再收；第三行才是记账。这种「动作 + 记账」的配对结构会反复出现。

```ts caption:[照抄] 第一趟：收 4 枚、倒一次、记下已倒数量
const eggsPerTrip = 4
const need = 6
let carried = 0
golem.moveTo(perch1)
golem.collect("egg", perch1)
carried = carried + 1
golem.moveTo(perch2)
golem.collect("egg", perch2)
carried = carried + 1
golem.moveTo(perch3)
golem.collect("egg", perch3)
carried = carried + 1
golem.moveTo(perch4)
golem.collect("egg", perch4)
carried = carried + 1
golem.moveTo(barrel)
golem.deposit("egg", barrel, carried)
let banked = carried
carried = 0
```

运行后世界会看到：灰崽依次走到四个蛋窝收蛋，背包里四枚；走到木桶边把四枚倒进桶里；木桶里变成 4 枚。程序内部，carried 在四次自增后是 4，倒蛋时用这个数；banked 记下已倒总量 4；carried 归零，为第二趟做准备。

这段程序里出现了一个容易忽略的细节：倒蛋用的是 `carried`，不是写死的 4。现在 carried 恰好也是 4，区别看不出来；但如果第一趟只收到 3 枚（比如某个窝临时没蛋），`carried` 会自动是 3，程序倒 3 枚，而写死 4 的程序会出错。这就是「让程序自己记」与「让人替程序猜」的差别。

`eggsPerTrip` 在这段程序里声明了却没有被使用。它能用在哪里？可以写 `golem.deposit("egg", barrel, eggsPerTrip)`，把「一次倒多少」表达成「一趟最多装多少」；也可以在外层判断「还没满一趟」时使用。当前写法把「收 4 枚」硬编码进了四组动作，所以这个常量暂时没有用武之地——这是参考解的一个小瑕疵，教材这里给一个干净版：要么删掉不用的常量，要么在语义合适的位置真的使用它。下一节会把干净版完整写出来。

### 3.3 第二趟与剩余量：`remaining` 的来历

第二趟要回答两个问题：还差几枚？这一趟实际收几枚？还差几枚可以算出来：总需求减去已经倒进桶里的数量，就是 `const remaining = need - banked`。这个表达式里，need 是常量 6，banked 是第一趟倒进去的 4，结果是 2。之后第二趟收 2 枚、倒 2 枚。

```ts caption:[改写] 第二趟：算出剩余量，收完再倒一次
const remaining = need - banked
golem.moveTo(perch5)
golem.collect("egg", perch5)
carried = carried + 1
golem.moveTo(perch6)
golem.collect("egg", perch6)
carried = carried + 1
golem.moveTo(barrel)
golem.deposit("egg", barrel, remaining)
banked = banked + remaining
```

运行后世界会看到：木桶里的蛋从 4 枚变成 6 枚；程序内部，remaining 是 2，banked 从 4 变成 6，carried 是 2。接在上一段程序后面运行时，这段代码就是完整的两趟流程。

请特别注意 `banked = banked + remaining` 这一行右边的表达式。banked 此刻是 4，remaining 是 2，右边算出 6，写回 banked，banked 变成 6。这一行之后，程序里的 banked 与木桶里的实际蛋数一致。如果第二趟没有把 banked 更新，后面任何依赖它的计算都会出错——这类「忘了更新」是变量记账中最常见的漏洞之一，调试时可以用「程序里的数」与「世界里的数」对照来发现。

### 3.4 干净版：让每个变量都有用途

现在把两趟合并成一段完整、可照抄的程序，并顺手修掉上一节提到的 `eggsPerTrip` 问题。干净版的原则是：每个声明出来的名字都要被使用，每个被使用的名字都要有清楚的含义。如果某个名字从头到尾没有被读过，它不是抽象，只是噪音，应当删掉；如果一趟搬运的「一趟最多装几枚」需要表达，就在倒蛋或判断里真的使用它。

```ts caption:[照抄] 干净版：分两趟收 6 枚蛋，报数时现查木桶
const eggsPerTrip = 4
const need = 6
let carried = 0
let banked = 0
golem.moveTo(perch1)
golem.collect("egg", perch1)
golem.moveTo(perch2)
golem.collect("egg", perch2)
golem.moveTo(perch3)
golem.collect("egg", perch3)
golem.moveTo(perch4)
golem.collect("egg", perch4)
carried = eggsPerTrip
golem.moveTo(barrel)
golem.deposit("egg", barrel, carried)
banked = banked + carried
carried = 0
const remaining = need - banked
golem.moveTo(perch5)
golem.collect("egg", perch5)
carried = carried + 1
golem.moveTo(perch6)
golem.collect("egg", perch6)
carried = carried + 1
golem.moveTo(barrel)
golem.deposit("egg", barrel, remaining)
banked = banked + remaining
golem.moveTo(eira)
const inBarrel = world.container(barrel).count("egg")
golem.say(`木桶里有 ${inBarrel} 枚蛋`)
```

运行后世界会看到：6 枚蛋全部进了木桶，灰崽回到艾拉身边，报出木桶里的真实数量。程序内部，`eggsPerTrip` 用来表示第一趟收满 4 枚，`banked` 累计已倒总量，`remaining` 表示第二趟还差多少，`inBarrel` 是从容器里现查的最终数字。

这段程序里有两处设计值得说明。第一处是第一趟的 `carried = eggsPerTrip`：四组动作之后，筐里确实有 4 枚，但程序没有逐步自增，而是在收完后一次性把 carried 设成「一趟的容量」。两种写法都可以，前提是四组动作确实把筐装满了；如果实际收蛋数量可能不足，逐步自增更稳妥。第二处是报数前的 `const inBarrel = world.container(barrel).count("egg")`：它没有使用程序里的 banked，而是重新从世界读取。为什么？因为任务要求「报出木桶里的数量」，世界里的容器才是事实；程序里的 banked 是辅助记忆，可能与事实不一致（比如倒蛋失败、或者被别的动作影响）。报数用现查值，是让程序对世界负责。

### 3.5 从世界读数：`golem.count` 与 `world.container`

两个读数接口解决两个问题。`golem.count("egg")` 读灰崽背包里现在有几枚蛋；`world.container(barrel).count("egg")` 读木桶这个容器里有几枚蛋。前者适合回答「我这趟收了多少」，后者适合回答「桶里现在有多少」。

```ts caption:[照抄] 先分清背包与木桶：两个读数接口
const inBag = golem.count("egg")
const inBarrel = world.container(barrel).count("egg")
golem.moveTo(eira)
golem.say(`背包 ${inBag} 枚，木桶 ${inBarrel} 枚`)
```

运行后世界会看到：灰崽说出一句包含两个数字的话。数字不是写死的，而是运行时从背包与容器里读出来的；如果前面的程序少收了蛋，这句话会自动变短，暴露问题。

读数字时要注意时机。同样的 `world.container(barrel).count("egg")`，在倒蛋之前读和倒蛋之后读，结果不同。程序是按顺序执行的，读数只是「在那一行读取当时的快照」，不会在你需要时自动更新。想拿到最新数字，就在使用之前重新读一次。这个规则与变量一致：谁在什么时候读，决定了拿到哪个值。

## 4 常见错误

### 错误一：把 `=` 当成「等于」

现象：读代码时以为 `carried = carried + 1` 不可能成立，或者写程序时想表达「判断是否相等」，却写成了 `=`。原因：数学的等号与程序的赋值号形式相同、含义相反。程序里 `=` 是「把右边算出来，绑定给左边」，所以「自己加一」完全成立；判断相等是另一类运算符，第 3 章才讲。改法：读 `=` 时念成「变成」，读右边先算；写代码时明确自己要做的是「存值」还是「比较」，两类操作不要混在一起。

### 错误二：用 `const` 声明后又赋值

现象：运行时报错，提示不能给常量赋值。原因：`const eggsPerTrip = 4` 之后又写 `eggsPerTrip = 5`，语言禁止改绑常量。改法：判断这个值在运行中是否真的需要改变；需要就改用 `let`，不需要就删掉赋值语句。不要为了「省事」把所有名字都写成 `let`——`const` 传递的是「这个值不变」的信息，对读代码的人有用。

### 错误三：声明之前就使用，或者忘记声明

现象：运行时报错，提示名字未定义。原因：赋值语句写在 `let` 声明之前，或者根本忘了声明就直接写 `carried = carried + 1`。顺序执行意味着名字从声明那一行起才存在；`let` 之前使用、或者漏写 `let`，程序都找不到这个名字。改法：把声明和初始化放在程序开头，集中写清楚；每用一个名字，先确认它在前面被声明过。

### 错误四：声明了变量却没有初始化

现象：程序能运行，但数字变成 `NaN`，后面的报数或计算全部异常。原因：`let carried` 没有初始值，绑定到 `undefined`；`undefined + 1` 得到 `NaN`，之后每一个与它有关的计算都带上这个坏值。改法：声明时就给初始值，`let carried = 0`；如果初值需要计算得到，也要在第一次使用前完成赋值。

### 错误五：数字与字符串混淆

现象：程序给出的结果是 `41` 而不是 `5`，或者倒蛋时报「数量不合法」。原因：本该用数字的地方写了字符串，比如 `const four = "4"`，`four + 1` 变成文字拼接；或者 `deposit` 的第三个参数给了字符串。改法：参与计算的数字不要加引号；引号只用来包文字（物品名、对话内容）。发现结果奇怪时，先检查参与运算的值是数字还是字符串。

### 错误六：变量名含糊，或者和命名点重名

现象：代码能运行，但读不懂，或者若干行之后出现莫名其妙的结果。原因：名字起成 `a`、`b`、`n1`、`ys`，读代码的人（包括三天后的你）无法从名字看出含义；或者声明了 `let barrel = 3` 之类的名字，遮蔽了关卡给的位置命名点 `barrel`，后续 `golem.deposit("egg", barrel, ...)` 拿到的就不是位置了。改法：按用途命名（`carried`、`banked`、`remaining`），并在声明前扫一眼关卡的命名点清单，避免重名。

## 5 与关卡的关系

回到 L02 的主任务：让灰崽收 6 枚蛋，分两趟倒进木桶；不碰 3 个带玻璃罩的孵蛋窝；回艾拉身边报数。三条要求分别检验本章的三种能力：用变量记账、按名字区分对象、从世界读数并报告。

第一条要求「分两趟」。小筐一趟最多 4 枚，这个约束不是靠写死 4 实现的，而是靠「第一趟收满 4 枚、倒掉、清空记账、第二趟收剩下的」这个流程实现的。程序里的 `carried` 负责一趟之内的计数，`banked` 负责跨趟的累计，`remaining` 负责推算还差多少。三个名字各管一段时间，合起来才是完整的记忆结构。写代码前先在纸上画一张记账表，把「每一趟开始时 carried 是多少、结束时是多少、banked 怎么变」填清楚，再落到代码里，比边写边想可靠得多。

第二条要求「不碰孵蛋窝」。三个带玻璃罩的窝（`hatch1` 到 `hatch3`）是留给母鸡孵小鸡的，一个都不能收。这条要求检验的是「按名字区分对象」：蛋窝的名字是 `perch1` 到 `perch6`，孵蛋窝的名字是 `hatch1` 到 `hatch3`，程序只对前者写 `collect`。命名点让「收错对象」变成可以肉眼检查的错误：扫一遍代码里的名字，就能知道有没有碰到不该碰的窝。

第三条要求「报数」。报数不是随便说一句「收好了」，而是要把木桶里的真实数量报给艾拉。任务文案写得很清楚：用 `world.container(barrel).count("egg")` 现数，再说出来。参考解用模板字符串把数字嵌进句子，这样即使数量变化，句子也自动正确。报数这一条同时检验「从世界读数」与「类型」两个知识点：数字要参与计算（现数），句子要显示数字（模板字符串），两者分工不同。

本关的加练「一趟搬完」要求 6 枚蛋一口气收完、只倒一次。它把两趟流程改成一趟，变量结构也随之简化：不需要分趟清空 carried，也不需要 remaining。这类「同一任务、不同约束」的变体，正是检验你是否真的理解变量用途的好题：如果只是背下了参考解的行号顺序，换一个约束就会卡住；如果理解每个变量的职责，改写起来只是删掉或合并几行。

玩家节拍是喂鸡催下最后一枚蛋、把最后一只蛋糕放上蛋糕塔。这一步与代码里的变量无关，但它在任务结构上与 L01 的第 4 盏灯同类：有些步骤由玩家亲手完成，程序只负责它擅长的部分。工作台的目标面板会分条显示三条目标，哪一条没勾就去对应位置检查：蛋没收完、窝被碰了、或者没有报数，面板上都能看出来。

## 6 小结与练习

本章的要点收成六条。

- 变量是名字与值的绑定；声明让名字出现，初始化给第一个值，赋值让名字改绑到新值。
- `let` 声明可改绑的变量，`const` 声明不可改绑的常量；按「运行中是否需要改绑」来选择。
- 赋值不是数学等式：先求值右边，再把结果绑定给左边，所以 `carried = carried + 1` 是把名字指向新值。
- `let banked = carried` 是读出值再绑定给新名字，两个名字各自独立，修改其中一个不影响另一个。
- 从世界读数字要用 `golem.count` 与 `world.container(...).count`，报数时要现查，不能拿程序里记住的旧数字冒充。
- 变量名是写给人看的说明；用 `carried`、`banked`、`remaining` 这样的名字表达职责，不要用拼音缩写或与命名点重名。

练习不计分，也不需要提交。建议先写预测，再到关卡里验证。

1. 手写跟踪表：`let n = 0`，然后连续执行三次 `n = n + 2`，每次执行后 n 是多少？把过程写成「读什么、算什么、写回什么」。
2. 把本章干净版程序的第一趟改成只收 3 枚（删掉 perch4 的两行），其余不变。程序还能完成 6 枚蛋的任务吗？如果不能，剩下几枚要从哪里补？变量需要怎么改？
3. 下面两行程序，第二行执行后 banked 是多少？为什么？`let carried = 4`、`let banked = carried`、`carried = 1`。
4. 写一段程序，收 2 枚蛋、倒进木桶、再报出木桶里的数量。只用本章讲过的语法，并在纸上写出每个变量的跟踪表。
5. 判断对错并说明理由：`const need = 6` 之后写 `need = 7` 表示「把总需求改成 7」。如果真的要支持总需求变化，应该怎么声明？

## 7 延伸

变量是「存储程序」思想在语言层面的入口。早期计算机的程序与数据放在同一片存储里，计算就是不断读取、修改存储单元；高级语言把存储单元包装成有名字的变量，程序员不必再面对编号。今天你写的 `let carried = 0`，背后是内存里的一块位置；语言替你管理位置，你只需要管理名字和值的含义。理解这层对应关系，后面学习数组和记录时就不会觉得它们是凭空出现的新东西——它们只是组织多个存储单元的更复杂的方式。

真实语言里，变量声明的写法各不相同，但核心概念一致。Python 不需要声明，直接赋值就创建名字；JavaScript 用 `let` 与 `const`，与本章的语法基本一致；C 语言要写类型，如 `int carried = 0`；Rust 用 `let` 声明、用 `let mut` 表示可改。类型写不写、可不可改，是不同语言的设计选择，但「名字绑定值、值随时间变化」这个模型是共同的。

变量也带来代价。状态越多，程序越难推理：每一个 `let` 都是一条会被改写的记录，改写的时机和顺序都可能出错。本章只有两三个变量，还能在纸上跟踪；真实程序里状态成百上千，所以现代语言提供了很多限制状态的手段（常量、不可变数据、纯函数），后面的章节会陆续见到。第 10 章还会遇到更难的问题：当两个执行者同时修改共享状态时，谁先谁后都会影响结果。现在先把单个程序的记账写对，这是所有后续讨论的地基。

## 术语

- 变量（variable）— 一个名字与一个值之间的绑定，值可以在运行中改绑；示例：`let carried = 0`。
- 绑定（binding）— 名字与值之间的对应关系；赋值会改变绑定，而不是改变值本身。
- 声明（declaration）— 让一个名字开始存在的语句；`let`、`const` 都是声明。
- 初始化（initialization）— 声明时给名字绑定第一个值；示例：`let carried = 0` 里的 `= 0`。
- 赋值（assignment）— 把右边求值的结果绑定给左边的名字；示例：`carried = carried + 1`。
- 常量（constant）— 用 `const` 声明、之后不能改绑的名字；示例：`const need = 6`。
- 表达式（expression）— 能算出一个值的写法；示例：`need - banked`、`carried + 1`。
- 求值顺序（evaluation order）— 计算表达式时先算什么、后算什么的规则；赋值总是先算右边再写左边。
- 字符串（string）— 用引号或反引号包起来的文字值；示例：`"egg"`、`"木桶里有 6 枚蛋"`。
- 模板字符串（template string）— 用反引号包住、可在 `${}` 里嵌入表达式的字符串；示例：`` `木桶里有 ${inBarrel} 枚蛋` ``。
- 类型（type）— 一个值属于哪一类，决定它能参与哪些运算；数字做算术，字符串做拼接。
- 作用域（scope）— 一个名字在程序里有效的范围；在代码块内声明的名字只在块内可见。
