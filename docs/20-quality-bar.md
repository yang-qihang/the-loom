# 20 — 最终质量门（用户验收标准的可执行版）

> 状态：v1｜负责人：Lead｜最后更新：2026-10-31
> 用户原话：**美观、精致、逻辑 coherent、层层递进、精彩、震撼；界面易用、文字清晰、没有很重的 AI 味和看不懂的汉语。**
> 本文把这句话拆成能打勾的门禁；任何一条不过，不叫「完成」。
> 现行文件（2026-11-01 复核）：质量门定义仍有效；当前 gate 状态见 `qa/README.md` §6（G-FRESH-READER 仍 tracked fail）。
> 上游：BRIEF.md §1、docs/19-art-direction.md、docs/22-copy-deck.md

## 1. 八个验收维度

| # | 维度 | 可执行判据 | 谁验 |
|---|---|---|---|
| Q1 | 美观 | 每 Act ≥3 张固定机位截图通过 docs/19 §6 的 5 条判据（焦点/层次/对比/无空乱/地道）；关卡选择有插画地图 | 人类看截图 / 视觉 agent 复核 |
| Q2 | 精致 | 没有「空房间/秃地面/悬空方块」；每关 ≥8 个非功能装饰点；音效+粒子+字幕至少各 1 次；无 TBD 文案 | art pass checklist |
| Q3 | coherent | 同一世界地图；角色/道具/术语跨关一致；前一关的世界变化在下一关可见；世界观规则不漂移（织偶字面执行） | 14/14b 类评审 |
| Q4 | 层层递进 | docs/05 依赖图成立；盲测 solver 每关 ≤2 级提示、≤时限；相邻关难度/时长比 ≤1.8；无「越级 API」 | 盲测 + validator |
| Q5 | 精彩/震撼 | 4 个 S 级 showpiece（灯河/麦田/破晓/合龙桥）各有一个 5–10 秒「值得截图」的演出；demo 彩排时至少 2 个能让观众抬头 | 彩排 |
| Q6 | 易用 | 一个界面完成「看目标→改代码→运行→看结果」；Run/Stop/Reset 永远可见；目标 ≤3 条；首次进入 10 秒内知道做什么；键盘可完成主流程 | Playwright + 5 人走查 |
| Q7 | 文字清晰 | 教练单条 ≤45 字、目标 ≤3 条、按钮动词开头、错误=「哪里错+怎么改」；术语一致；无「AI 味」禁用词 | copy review（Vale + 人工） |
| Q8 | 汉语可读 | 单句 ≤40 字、无翻译腔、无生造词；每段 ≤5 句；9 年级可读；不中英混杂（除 API 名） | copy review |

## 2. 「AI 味」禁用词表（Vale 自定义词表 + 人工）

赋能、闭环、抓手、生态位、一站式、助力、打造、极致、深度、颠覆、革命性、显著提升、众所周知、底层逻辑、顶层设计、全链路、组合拳、心智、范式、沉浸式、丝滑、惊艳（用于自我夸奖时）。

**自检反例**：
- ❌「我们深度赋能了关卡创作流程，显著提升了整体体验。」
- ✅「一关的提示从 12 条降到 9 条；盲测平均提示从 3 次降到 1.8 次（n=6）。」

## 3. UI 文案规则（所有字符串）

1. 按钮 = 动词：`运行`、`停止`、`重置`、`提示`、`下一步`（不要「确定/提交/开始体验」这类空词）。
2. 目标 = 「做什么 + 做到什么程度」，≤20 字/条，最多 3 条。
3. 错误 = ①哪一行 ②哪里错 ③怎么改，≤2 句；不出现 JSON/堆栈/RPC 名。
4. 教练 = 具体事实（「1 号灯还没亮」），不空夸、不说教、不卖萌过度。
5. 术语首现给一句人话解释（「变量：给一个值起名字」），之后统一用该词。
6. 不用「您」，不用感叹号堆情绪；不写「让我们一起来……」。
7. 中文标点用全角；中英之间加空格；API 名保持英文且用等宽字体。
8. 每个字符串必须能回答：玩家现在该做什么？下一步点哪里？

## 3b. UI 语言门禁：干净的纯中文

**硬规则：玩家在界面上读到的每一句叙述，必须是地道中文。** 代码本身、必须引用的接口名、按键名只能以「代码引用」形式出现，且不得构成叙述的骨架。

| 允许 | 不允许 |
|---|---|
| 代码编辑器里的英文标识符（`golem.moveTo`） | 叙述句里夹英文术语（"用 moveTo 走到灯下" → "让灰崽走到灯下"） |
| 极少量专有名词：Minecraft / TypeScript（首次出现给中文解释；在游戏内界面优先写「我的世界」「这门语言」） | 界面标签用英文：Run / Stop / Reset / Level / Objective / Coach / Result / Mock |
| 按键名（回车、空格、Esc） | "Ctrl + Enter 运行" 这类把英文键名当文案主语的写法；优先「回车运行」 |
| 代码引用、行号、文件名 | 翻译腔：「让我们来…」「这是一个…的过程」「通过…来实现…」 |

**改写示例**：
- ❌「点击 Run 运行程序，查看 Result 面板的 Objective 完成情况。」
- ✅「按「运行」，看右侧目标有没有全部点亮。」
- ❌「使用 golem.moveTo 移动到 1 号灯柱，再调用 golem.place 放置灯笼。」
- ✅「让灰崽走到 1 号灯下，再点亮它。」
- ❌「本关引入了 closure 与 higher-order function。」
- ✅「这一关，灰崽会记住你交给它的做事方法，并把它带到别处用。」

**术语处理**：叙述里不出现「变量/函数/闭包/接口/异步」等词；这些词只出现在（a）代码注释（b）织典页（c）UI 的「术语小注」——且首次必须用世界观里的说法解释（见 docs/23 §8）。

**检查方式**：`scripts/check-copy.mjs --pure-zh` 扫描 UI 文案层（`apps/studio/src/copy/*.json`、content 的 UI 字段、level-spec 的 check.text / task 文案），对叙述串里的连续拉丁字母报错（代码引用/白名单除外）；人工再按上表复核一遍。

## 3b2. 引导不能省（见 docs/25）

每关必须写满「世界状态 / 任务 / 为什么是你」三句开场；序章 6–8 屏、每幕开场 2–3 屏、Esc 旅途手记可回看。只给一句任务的关卡直接打回。文本预算按 docs/25 §5（教练 ≤60 字、每关对话 ≤14 条、每关叙事 ≤600 字）。

## 3b2. 语言节奏：不要「电报体」，也不要啰嗦

**过度简洁也是 AI 味。** 玩家读到的每一句，必须是完整、有人称、有节奏的中文；宁可比原来多五六个字，也不要让人猜「它/这/那」指什么。

| 必须 | 禁止 |
|---|---|
| 指令/错误/解释有明确主语（你 / 灰崽 / 灯 / 艾拉） | 省略主语的电报体：「点灯。回村。」「坐标不对。」 |
| 一个句子只说一件事；主句 + 至多一个从句 | 名词堆叠、箭头链：「过去→收→回来→倒→记账」 |
| 代词前必须有先行词；「它/这/那」指代唯一 | 「把它放那儿」「这个再调一下」 |
| 节奏有长有短；读出声来像人说话 | 每句都 6–10 字的机械短句；或一句 50 字不断 |
| 允许为了清楚多写 5–10 个字 | 为了「简洁」牺牲指代与主谓宾 |

**改写示例**：
- ❌「照抄第一盏，只改括号里的坐标。」
- ✅「照着第一盏的写法再写一遍，只把括号里的坐标换成第二盏的。」
- ❌「过去、收、回来、倒进桶。」
- ✅「灰崽先走到鸡窝旁收蛋，再回到木桶边把蛋倒进去。」
- ❌「点灯。回村。」
- ✅「把这四盏灯点亮，然后回到艾拉身边。」
- ❌「它没更新。」
- ✅「你忘了把新数字写回数量里，所以桶里还是旧数。」

艾拉的台词可以偶尔短，但**任务、错误、目标、按钮说明一律用完整句**。

## 3b2b. 顶栏/控件不得重叠（自动检查）

- 顶栏采用**对称三列网格**：左返回、中标题、右状态；标题严格对齐全屏中线，不随右侧按钮宽度漂移。
- 右侧按钮/状态区允许换行，但不能与标题相交；窄屏（伴玩 420px）标题用绝对中线并限制宽度。
- Playwright 断言：任一顶栏按钮、状态胶囊与 `[data-ui-title]` 的 boundingBox 不得相交；同时保留「标题中心偏差 ≤2px」。
- 用户截图审计：每次 UI 改动后检查 `workbench-v33` 等证据图，按钮压标题即打回。

## 3b3. 视觉对齐与细节（UI 小样检查）

> 用户补充：标题部分要沿中线对齐；界面细节不能「看起来差不多」。

**对齐规则**：
1. **页面主标题 / 幕标题 / 关卡标题 / 面板标题：水平居中**，与页面中心轴对齐（误差 ≤2px）；标题下方的副标题/说明同样沿中心轴。
2. **正文左对齐**；数字、状态、计数在各自容器内右对齐；按钮组在容器内左对齐（主按钮在最左或最右，但同一页面保持一致）。
3. **图标与文字按垂直中线对齐**（不是顶端对齐）；同一行内字号/行高一致。
4. **面板标题栏**统一高度（建议 44px）、统一内边距（20px）、标题居中；面板内第一行内容与标题栏底边留 12px。
5. **网格**：8px 栅格；页面左右安全边距一致；卡片圆角/描边/阴影全站同一套 token。
6. **截断**：任何标题不许换行成两行（超出用省略号并在 hover/详情里给全名）；按钮文字不换行。
7. **禁止**：标题左对齐和居中混用、用不同字号表示同级标题、图标与文字错位、只靠颜色表达状态。

**机器检查（Studio Playwright，至少 3 屏）**：
- 每屏的 `data-ui-title` 元素 boundingBox 中心 x 与视口中心差 ≤2px；
- 同级面板标题字号/字重相同；
- 主标题不换行（高度 ≤ 单行行高 + 4px）；
- 无横向滚动（`scrollWidth <= clientWidth`）；
- 图标容器与文字行高差 ≤2px（抽样）。
不通过不允许进入下一幕。

## 3c. 关卡体量与挑战下限（反「秀气」）

> 用户反馈：不能每关只有一丁点东西、写几行就结束。**每关必须是一段真活**，而不是一个演示。

| 指标 | Act I | Act II | Act III |
|---|---|---|---|
| 参考解代码行数（不含注释/空行） | **≥ 25 行**（L01 教学例外 ≥ 10 行，但需有加练） | **≥ 50 行** | **≥ 60 行** |
| 阶段数（玩家可见的目标阶段） | 2–3 | 3 | 2–3 |
| 隐藏变体 | ≥ 2（换位置/换尺寸/换情形） | ≥ 2（换数据形状/换规则组合） | ≥ 2（换预算/换时序/换材料） |
| 加练挑战（可跳过、不计星，但必须有） | 每关 1 个：约束更紧/步数更少/额外情形 | 每关 1 个：新规则组合或性能约束 | 每关 1 个：死锁规避/预算极限 |
| 目标时长 | 12–18 分钟 | 15–25 分钟 | 18–25 分钟 |
| 代码增量（reference − starter） | ≥ 15 行 | ≥ 30 行 | ≥ 35 行 |

**判定**：spec 的 `referenceSolution` 去注释后行数、`starterCode` 与 `referenceSolution` 的差、`hiddenTests` 数量、`challenge` 字段（新增）会被 validator 机器检查；低于下限直接打回。**L01 是唯一允许「小」的关**，因为它教第一句符文；但它仍必须有一个「少走路/一次点亮」的加练。

**叙事检查**：每关必须能通过 docs/23 §7 的三个问题；新名词必须已在 world bible 中定义且首次出现有解释。

## 4. 评审与门禁

- **Copy Review**：每关文案（目标/教练/提示/错误/按钮）由第二 agent 按 §3 逐条检查；任何一条「读不懂/像 AI 写的」→ 打回。
- **UX 走查**：5 个新用户（或 5 个 fresh agent 模拟）在无解释情况下完成 L1；记录第一次点击前的犹豫时间、误点次数、求助点。
- **Art Review**：每 Act 3 张截图 + 1 张插画地图；不达标不允许进入下一 Act。
- **Demo Review**：完整 7 分钟彩排 2 次；每次记录「观众抬头/困惑」时间点；彩排不过不允许冻结。
- 以上任一条不过，`STATUS.md` 不得写「完成」。

## 3b4. 字体策略（全平台统一）

- **代码/等宽区域**：`Departure Mono`（拉丁、数字、符号，像素等宽）+ `Zpix`（中文 fallback）。两者都随 Studio 以 woff2 打进 `dist/assets`，Monaco、织典代码块、试符台输出共用 `--mono` 栈。
- **正文/界面**：保持中文无衬线正文，不把正文换成像素字体；代码字号保持 16px，优先可读性。
- **禁止依赖系统 font fallback 来“看起来一致”**：桌面 App 与浏览器必须吃同一份打包字体；e2e 断言 `.monaco-editor .view-lines` 的 font-family 含两者，且 `document.fonts.check` 为 true。
- **验收**：真实截图确认英文代码与中文注释都清楚；像素字体不得让 0/O、1/l/I 混淆，不得裁切行高。
