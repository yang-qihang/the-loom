| 项 | 假设 |

**范围哲学（与用户 alignment）**：宁可 8 个精致关卡 + 1 个终局彩蛋，不要 12 个半成品。任何时刻，**「演示路径是否更好看、更顺」优先于「关卡数量是否更多」**。

## 1. 交付定义（什么是「完工」）

### 1.1 必须交付（P0，缺一不可）

1. **可一键启动的本地 demo**：`./scripts/demo-up.sh` 起 Paper + 插件 + 引擎 + Web UI；MC 客户端进入服务器；从关卡选择到通关全流程无人工干预。
2. **垂直切片**：L1 在真实 Minecraft 中端到端可玩（含场景、代码执行、评分、提示、演出、advancement）。
3. **Act I 完整**：L1–L4 可玩，含错误翻译、提示梯、trials、重置。
4. **Act II 至少 3/4 关可玩**：L5–L7 教学目标与评分成立；L6 或 L7 至少一关达到「值得演示」的完成度。
5. **Act II 收尾 + Act III 至少 1 关**：L8（接口/组合，属 Act II）优先于 L9（异步，Act III）；L10 作为 P2 尽力。
6. **证据包**：explore 报告、技术报告（架构 + 工作流）、3 段录屏、盲测数据、telemetry 导出、最终 demo 脚本。
7. **课程报告**（10 页内）：问题、相关工作、设计、实现、评估、局限、未来工作。
8. **无阻塞 bug**：demo 路径上不允许出现「必须重启进程才能恢复」的 bug。

### 1.2 明确不交付（写进报告的「局限」）

- 正式发行版（安装器、账号、云端同步、多人课堂管理）；
- 完整的 Act III（L10/EP/Labs 视时间，P2/P3）；
- 移动端/手柄支持；
- 多语言 UI（中文优先，英文文案可以后补）；
- 反作弊的强对抗（本项目的威胁模型是「好奇的学生」，不是恶意攻击者）。

## 8. 人类监督计划（总投入 ≤4 小时）

### Checkpoint 0（Day 0，45–60 min）：设计拍板
- 议程：① 5 个决策逐条确认/否决（语言、双通道、主题、范围、AI 工作流）② 4 个前提确认（MC 客户端、演示机器、时间、受众）③ 授权开工
- 输出：`DECISIONS.md` 签字（用户回复即可）；未决问题清单（最多 3 个）

### Checkpoint 1（T2 17:00，45–60 min）：垂直切片 + Act I 试玩
- 议程：① 亲自玩 L1–L4（25 min，不提示）② 给 5 条最强烈的感受（好玩/困惑/无聊/想跳过）③ 确认 Day3–4 范围是否按计划
- **人类不需要看代码**；只看「玩起来怎么样」。反馈由 Lead 转成 backlog。

### Checkpoint 2（T4 早上或前一天晚上，30–45 min）：终局验收
- 议程：① 看完整 demo 彩排 ② 确认报告结论/局限是否诚实 ③ 决定现场 demo 还是录屏

### 异步通道

## 14. 与 AI 工作流的衔接

本计划里的每个门禁都对应 `docs/08-ai-workflow.md` 的 Gate：
- Gate 1（spec 通过 validator + rubric）→ 才能开工实现；
- Gate 2（实现通过 CI：type/lint/unit/contract）→ 才能请求 review；
- Gate 3（reviewer 通过 + reference solution 通过）→ 才能合入；
- Gate 4（盲测 + 截图 + playtest）→ 关卡才能标「完成」；
- Gate 5（每日集成回归全绿）→ 才能过夜。
