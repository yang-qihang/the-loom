# 24 — 关卡体量与挑战审计（反「秀气」）

> 状态：v1｜负责人：Lead｜最后更新：2026-10-31
> 背景：用户指出「不要每关都太秀气——一丁点东西、写几行就结束」。本文按 `docs/20 §3c` 的新下限逐关审计，并列出补强动作。

## 3. 机器门禁（已写入 docs/06 §6.1 #15）

validator 对每个 `*.level.ts` 检查：
1. `referenceSolution` 有效行数 ≥ 该幕下限（L01 例外，但必须 ≥8 且有 `challenge`）；
2. `starterCode` 与 `referenceSolution` 的有效行差 ≥ 下限的 1/2；
3. `task.phases`（新增字段）≥2（L01 允许 1 + challenge）；
4. `task.challenge` 必须存在且 `tested: true`（有对应测试）；
5. `hiddenTests` ≥2（L01 允许 1，但 challenge 必须另有测试）。

## 4. 补强顺序

1. **L02–L04**（进行中，task-27）：加 Phase B + challenge + 测试，达到 25 行。
2. **L01**（Lead/内容线）：补「报数」与「最短路线」加练，达到 8 行；这是唯一允许偏小的关。
3. **L05–L10**：在实现前先把 spec 的参考解扩到下限（Act II 50 / Act III 60），否则实现线会照着「薄设计」做出薄关卡。
4. 报告/演示时用「每关 2 阶段 + 加练」回应「太小」的质疑，并给出实际行数。

## 5. 与「叙事」的关系

「秀气」的另一半是**叙事没有分量**：如果一关只有一个小任务，故事也撑不起来。每一关必须对应 world bible（docs/23）里的一个**世界状态变化**（灯河亮起、夜巡守住、商人离开、工坊重启…），而不是「完成一个练习」。这条与体量门禁一起审。
