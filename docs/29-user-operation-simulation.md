# 29 — 用户操作模拟（UOS）：AI 主导项目的「真人点击」替代

> 状态：v1 冻结（docs/28 的 G-UX-SIM 门禁）｜负责人：Lead｜最后更新：2026-10-31
> 原则：**后端测试通过 ≠ 玩家能用。** AI 主导开发时，必须用浏览器/桌面壳的自动化操作模拟真实用户，覆盖「第一次打开、不知道点哪、点错、断线、重置」这些路径。
> 现行文件（2026-11-01 复核）：UOS 流程仍有效；当前结果 UOS 4/4（`qa/evidence/`）。
> 上游：docs/28-change-control-quality.md

---

## 1. 六层用户操作测试

| 层 | 名称 | 做什么 | 工具/产物 |
|---|---|---|---|
| U1 | UI 契约 | 关键元素存在、文案正确、纯中文、标题中线对齐、无横向滚动、无 console error | Playwright DOM 断言 + 截图 |
| U2 | Happy E2E | 每关完整路径：选关→序章/开场→编辑→运行→玩家节拍→3 星→重置；试符台：一句→结果→重置 | Playwright，每关 1 条 |
| U3 | 错误/恢复 | 语法错误、类型错误、超时、Stop、断线、连续重置、刷新页面 | Playwright，每类 1 条 |
| U4 | **Fresh-user 盲操作** | agent 只读**屏幕上真实可见文字**（不含 spec/代码注释），回答五问并尝试完成 L01：记录犹豫点、误点、提示使用 | 独立 agent + Playwright 驱动；报告 |
| U5 | 桌面 E2E | Tauri App 启动、无浏览器、置顶/伴玩、快捷键、退出清理、首启向导 | Xvfb/WebDriver + 截图/日志 |
| U6 | 视觉回归 | 固定机位截图 hash/diff（地图墙/工作台/结果/序章/手记/试符台） | 截图 + sha256 manifest |

**每新增一个 UI 功能，必须同时加 U1 + U2 + U3 各至少 1 条；涉及新页面再加 U6 截图。**

## 2. 必须覆盖的用户路径（T2–T4）

### 首次用户
- 打开 App → 序章 8 屏（可跳过）→ 第一幕开场 2 屏 → L01 开场 3 句 → 目标面板 → 运行 starter（失败，看错误）→ 改代码 → 运行 → 玩家节拍 → 3 星 → 回地图墙。
- 在任意界面 Esc → 旅途手记 → 看到「世界怎么了 / 我是谁 / 织偶解释」→ 关闭回到原界面（进度不丢）。

### 每关（L01–L04 优先）
- 选关 → 开场 3 句 → 编辑器加载 starter → 「运行」→ 结果面板逐条打勾 → 「重置」→ 再运行同一代码仍正确。
- 代码写错（语法错/类型错/坐标错）→ 错误提示：第 N 行 + 中文人话 + 不扣星；修复后可继续。
- 运行中「停止」→ 状态可读；重置后恢复；断线（engine 停）→ 中文提示 + 可重试。

### 试符台（REPL）
- 地图墙 → 试符台 → 执行 `golem.pos` 看到坐标 → 执行错误行看到中文错误 → 执行 `golem.moveTo` 世界反应 → 重置 → 历史清空。
- 不影响关卡进度：从试符台返回工作台，关卡仍是原状态。

### 桌面（T3–T4）
- 启动 App（Xvfb）→ 无浏览器窗口/地址栏 → 窗口标题「织界」→ 首启向导（Java/Prism/Paper 检测）→ 置顶开关 → 伴玩/展开 → 快捷键 → 退出后无 engine/Paper/bot 残留。

## 3. Fresh-user 盲操作（U4）协议

1. 启动 Fresh agent，只给它：截图/可访问树 + 屏幕文字，**不给 spec、不给 docs、不给 starter 注释以外的解释**。
2. 让它回答五问：我是谁/世界怎么了/织偶是什么/现在做什么/做错会怎样；答不上 → 记「引导缺口」。
3. 让它用键盘/鼠标点击完成 L01；记录：第一次点击前犹豫时间、误点次数、需要提示次数、卡住位置。
4. 判定：五问 ≥4/5 正确、L01 在 ≤15 分钟/≤2 级提示内完成、无死局；否则打回文案/UX。
5. 产物：`qa/evidence/ux-fresh-L01.json` + 截图 + 文字记录；不需要人类。

## 4. 自动化与证据

- 运行：`qa/ux-sim.mjs --suite happy|error|fresh|desktop`，内部用 Playwright（系统 Chrome）驱动 `apps/studio`（mock 或真实 engine），失败保存 trace/screenshot。
- 证据：`qa/evidence/ux-*.json`、`apps/studio/evidence/*.png`；每次合并新增/更新对应的截图 hash（U6）。
- 频率：每个 UI 功能合入前跑 U1–U3；每 2 小时/每日跑全量；T4 彩排前跑 U4 + U5。
- Flaky：禁止「重跑通过」；不稳定用例进 quarantine 并写到期日；同一用例 2 次 flaky 即视为 bug。
- 环境：系统 Chrome（`channel: chrome`）；无网络依赖；每个 suite 从干净存档/世界开始；串行 workers=1。
- 控制台：任何 `console.error` / 未捕获异常 = 失败（允许白名单的已知警告，需登记）。

## 5. 与质量门的关系

- **G-UX-SIM** = U1–U6 的汇总门禁；在 `qa/verify` 的 l3/专项层运行。
- 新功能不得以「后端测试绿」为由跳过 U1–U3；桌面功能必须过 U5。
- 通过标准：全场景绿 + Fresh-user 达标 + 截图存档 + 无 console error + 无 flaky。
- 若与实现冲突：先改实现/文案，再改测试；改测试必须 Reviewer 签字（docs/28 FAP）。
